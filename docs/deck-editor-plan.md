# 로컬 덱 에디터 — 설계 메모

> 2026-09-19 구현. 덱은 로컬 파일이므로 온라인 저장이나 DB 없이, dev 서버가 원본 파일을
> 직접 고치는 에디터로 만들었다.

## 쓰는 법

```bash
npm run dev            # 에디터는 dev 서버에서만 뜬다
```

- `/?app=edit` — 덱 고르기 (웹앱 덱 34개)
- `/?app=edit&deck=<id>` — 바로 그 덱 열기
- 허브(`/hub`) 카드의 **✎ 편집** 링크로도 들어간다 (dev에서만 보인다)

**웹앱 덱(deck.tsx)만 다룬다.** 레거시 HTML 덱은 편집 대상이 아니다(2026-09-19 결정).

작업 화면은 왼쪽 슬라이드 목록, 가운데 미리보기, 오른쪽 패널(문구 · 문항)이다.
미리보기에는 두 모드가 있다.

- **✎ 고치기** — 화면의 글자를 누르면 그 문구의 원본 위치를 찾아 오른쪽 패널에 띄운다.
  덱의 클릭은 막힌다.
- **☝ 눌러 보기** — 덱을 평소처럼 조작한다(빌드·버튼·링크).

`Ctrl+Enter`로 저장하고, 상단 **↶ 되돌리기**로 직전 저장을 무른다.

슬라이드 조작은 왼쪽 목록에서 한 줄을 고르면 그 아래에 나타나는 도구로 한다.
숨긴 슬라이드도 자리를 지키므로 다시 고를 수 있다.

| 도구 | 하는 일 |
|---|---|
| ↑ ↓ | 순서 바꾸기 |
| ◌ / ◉ | 숨기기 / 다시 보이기 — 지우지 않고 화면에서만 뺀다 |
| ＋ | 이 아래에 빈 슬라이드 추가 (자리만 잡는다) |
| ⧉ | 복제 |
| ✕ | 삭제 |

오른쪽 패널에서는 문구, **자리·크기**, 문항을 고친다.

## 핵심 결정과 근거

1. **저장 경로는 Vite dev 서버 플러그인**(`scripts/deck-editor-api.mjs`, `apply: 'serve'`).
   브라우저가 `/__edit/*`를 호출하면 서버가 `data/` 아래 원본을 고친다. dev 서버에만 붙으므로
   프로덕션 번들에서 완전히 빠지고(빌드 산출물에 `__edit`·`EditorPage` 문자열이 없다),
   `build-static.mjs`의 TARGETS도 손댈 필요가 없다.

2. **문구는 구조 편집을 하지 않는다.** deck.tsx 34개는 자유 TSX이고 문구가 JSX 본문·props
   문자열·상수 배열·SVG `<text>`로 흩어져 있어서 일반화된 폼을 만들 수 없다. 그래서 **보이는
   글자를 눌러 그 문구만 교체**한다. 눌린 요소의 소스 위치는 후보 순위를 정하는 단서로만 쓰고,
   실제 탐색은 수업 폴더 전체(하위 1단계까지)에서 공백 차이를 무시하고 찾는 문자열 검색이다.
   그래서 상수 배열처럼 소스 위치와 문구의 자리가 다른 경우에도 찾아낸다.

2-1. **슬라이드는 구조 편집을 한다.** 슬라이드 경계만큼은 컴파일러가 이미 알려 준다 —
   덱의 최상위 자식마다 `element._source`(파일·줄·열)가 붙어 있다. 34개 덱 전부에서 이 좌표가
   한 파일 안에 순서대로 놓인 것을 확인하고, 그 줄을 경계로 원본을 토막 내 다시 붙이는 방식을
   택했다. JSX 파서를 새로 만들지 않는다. 토막은 **절대 다시 들여쓰지 않는다** — 여러 덱이
   `code={\`…\`}` 템플릿 리터럴을 품고 있어서 들여쓰기를 손대면 화면의 코드가 바뀐다.

   한 가지 함정이 있다. `@vitejs/plugin-react`가 모듈 앞에 Fast Refresh 준비 코드를 17줄쯤
   덧붙이기 때문에, 화면이 알려 주는 줄 번호는 원본보다 그만큼 **뒤로 밀려 있다**. 밀린 양은
   파일 전체에 대해 하나뿐이므로, 서버가 "모든 슬라이드가 동시에 여는 꺾쇠에 떨어지는 값"을
   찾아 되돌린다(들여쓰기까지 같은 값을 우선하고, 후보가 둘 이상이면 손대지 않는다). 한 번
   알아낸 값은 파일별로 기억해 둔다.

3. **quiz.json만 폼 편집기**다. 형식이 일정하기 때문이다. 편집기가 모르는 필드
   (`misconceptions`·`tests` 등)는 건드리지 않고 보존하고, 그 사실을 문항 카드에 적어 준다.

4. **엔진(`src/deck/`)은 수정하지 않는다.** 슬라이드 이동은 엔진이 이미 듣고 있는 URL 해시로
   하고, 슬라이드 목록·발표자 노트·수업 폴더 경로는 iframe 안의 React fiber에서 읽는다.

5. **미리보기는 iframe으로 격리**한다. 덱 테마는 `App.tsx`가 문서 루트에 직접 주입하므로 같은
   문서에 렌더하면 도구 화면이 덱 색으로 물든다. iframe은 1600×900으로 고정 렌더한 뒤 CSS
   `scale`로 줄여서 발표 때와 같은 구도를 유지한다.

## 저장하면 남는 편집 기록 — `edits.md`

저장할 때마다 수업 폴더의 `edits.md`에 무엇을 어떻게 고쳤는지 덧붙인다. `prompts.md`와 같은
자리, 같은 취지다. 세션 기록은 지워지지만 자료 옆의 이 파일은 자료와 함께 남는다.

```markdown
## 2026-09-19 11:08 · 문구 · `deck.tsx` 161번째 줄

- 이전: `고등학교 정보 · 파이썬`
- 이후: `고등학교 정보 · 파이썬 기초`

## 2026-09-19 11:08 · 문항 · `quiz.json`

- 수정 · `warmup-if` — prompt
  - 질문: `오늘 하루 겪은 '만약 ~라면'을 한 단어로 적어보세요!` → `오늘 하루 겪은 만약을 한 단어로`
- 추가 · ox · 6쪽 — `else는 조건을 쓴다`
- 삭제 · `q-colon` — `if 문에서 조건 뒤의 콜론(:)과 …`
```

요약하지 않고 이전과 이후를 같이 남긴다. 무엇이 바뀌었는지 모르면 기록이 쓸모가 없다.
되돌리기도 기록한다. 앞 항목을 지우면 무엇을 시도했다가 물렀는지가 사라지기 때문이다.

이 파일의 머리글에는 **상위 원본과 어긋나 있다**는 경고가 들어간다. 일부 덱은 `plan.md`나
`scene-plan.json`이 원본이라고 선언하는데, 에디터로 고친 문구는 그쪽에 반영되지 않기 때문이다.
같은 취지의 규칙을 `CLAUDE.md`의 「편집 기록」 절에 적어 두어서, 다음에 이 저장소를 여는
사람이나 인공지능이 자료를 다시 뽑기 전에 이 파일을 읽도록 했다.

## 슬라이드 추가는 자리만 잡는다

＋로 넣는 것은 **빈 자리 하나**다. 내용은 만들지 않는다. 대신 "여기에 무엇을 담고 싶은지"를
자유롭게 적으면, 그 글이 수업 폴더의 `slides-plan.md`에 그대로 쌓인다. 형태(씬·디오라마·
화이트보드 등)나 구성은 여기서 정하지 않는다. 그것은 나중에 `lesson-deck-planner`가 판단할
일이다(2026-09-19 결정).

덱에는 자리표시 슬라이드가 들어가고, 그 위에 `{/* TODO(계획) plan-xxxxx */}` 표시가 붙는다.
계획 파일의 항목과 이 표시가 같은 id로 이어지므로, 나중에 인공지능이 둘을 맞춰 보고 저작한 뒤
양쪽을 함께 지우면 된다.

```markdown
## plan-sae8f · 4번째 자리 · 조건이 여러 개일 때

> 2026-09-19 11:44에 적음. 아직 비어 있다.

elif를 왜 쓰는지 학생이 스스로 말하게 하고 싶다. 시험 점수로 등급 나누는 예시가 좋겠다.
```

## 슬라이드 숨기기

지우지 않고 화면에서만 뺀다. 원본에서는 `{/* 숨김(에디터) */ false && ( … )}`로 감싼다.
주석으로 막지 않는 이유는 슬라이드 안에 또 주석이 있으면 깨지기 때문이다.

숨긴 슬라이드는 화면에 없으므로 미리보기에서는 읽을 수 없다. 그래서 서버가 원본에서 이
표시를 찾아 목록에 함께 돌려주고, 왼쪽 목록이 자리를 지킨 채 흐리게 보여 준다. 그러지 않으면
한 번 숨긴 슬라이드를 다시 꺼낼 방법이 없다.

## 슬라이드가 움직이면 따라 움직이는 것

한 번의 조작이 파일 셋을 함께 고치고, **되돌리기 한 번에 셋이 같이 물러난다**.

| 무엇 | 언제 |
|---|---|
| `quiz.json`의 쪽 번호 | 순서·삭제·숨김·추가. 문항이 붙어 있던 쪽이 사라지면 지우지 않고 앞 쪽으로 옮긴 뒤 기록에 ⚠로 남긴다 |
| `registry.tsx`의 `slides` 수 | 화면에 보이는 장수가 바뀔 때 |
| `edits.md` · `slides-plan.md` | 언제나 |

복제만은 문항을 건드리지 않는다. 같은 쪽이 둘이 되므로 문항을 어느 쪽에 붙일지 알 수 없다.

## 안전장치

| 무엇 | 어떻게 |
|---|---|
| 다른 기기·다른 사이트의 요청 | localhost에서 온 요청만 받고 Origin도 검사한다 |
| 엉뚱한 파일 | `data/` 아래 + 허용 확장자(tsx·ts·html·json)만 |
| 그사이 바뀐 파일 | 바꾸기 전 원문(`expect`)이 그 자리에 그대로일 때만 교체한다 |
| 문법이 깨지는 저장 | tsx·ts는 저장 전에 esbuild로 구문 검사, 실패하면 쓰지 않는다 |
| 이스케이프 | 들어갈 자리(문자열·템플릿·HTML 본문)에 맞춰 인코딩하고, JSX 본문의 `{ } < >`는 거부한다 |
| 낡은 되돌리기 | 우리가 쓴 내용이 그대로 남아 있을 때만 되돌린다(밖에서 고친 내용을 덮지 않는다) |
| 반만 되돌리기 | 한 조작이 파일 여럿을 고쳐도 한 항목으로 묶어 함께 물러난다 |

되돌리기 스택은 서버 메모리에 50건까지 쌓이고, dev 서버를 다시 켜면 사라진다. 그 위의 안전망은
git이다.

html과 json은 Vite가 전체 리로드를 걸기 때문에, 쓰는 동안 감시를 잠깐 떼고 에디터가 iframe만
새로 고친다. tsx는 HMR이 미리보기를 갱신하도록 감시를 그대로 둔다.

## 검증

```bash
npm run dev -- --port 5199
node test/edit-e2e.mjs        # 65항목 (워크스루 재측정 때문에 4분쯤 걸린다)
```

실제 수업 파일을 고치고 git으로 되돌리는 테스트이며, 성격이 다른 덱 둘을 본다.

- `파이썬-조건문-웹앱덱` — 한 파일짜리 덱. 문구 저장·되돌리기, 깨지는 저장의 거부, 슬라이드
  순서·복제·숨김·추가·삭제와 그때마다의 `quiz.json`·`registry.tsx` 반영, 편집 기록과 계획 파일
  생성, 덱 테마가 도구 화면을 덮지 않는지.
- `인공지능은-어떻게-배울까-v2` — 24장에 씬·빌드·walkthrough가 섞인 3,580줄짜리 덱.
  이스케이프된 따옴표가 든 노트 찾기, 같은 문구가 여러 곳일 때, 씬의 장면 멈춤,
  창을 옮겼을 때 포인터가 자동으로 다시 재어지는지.

## 하지 않기로 한 것

- **레거시 HTML 덱 편집** — 필요 없다고 정했다(2026-09-19).
- **자리표시 슬라이드의 내용 생성** — 에디터는 자리와 맥락까지만 맡는다. 내용은 계획을 읽고
  기획·저작 스킬이 만든다.
- **pages.json·registry 메타 편집, 컴포지트 덱(deck.json) 편집** — 컴포지트 덱은 1개뿐이라
  뒤로 미뤘다. deck.json은 스키마가 명세되어 있어 붙이기는 쉽다.
- **상위 원본(plan.md) 자동 동기화** — `edits.md`로 어긋난 자리를 드러내는 선에서 멈췄다.

## 자리·크기 — 통째로만 옮긴다

씬이나 워크스루의 구체적인 값을 다 열어 주는 것은 무리다. 그래서 **글자를 고치는 것**과
**요소를 통째로 옮기고 키우는 것**만 연다(2026-09-19 결정). 이 저장소의 덱은 자리를 두
가지 꼴로만 적는다.

| 꼴 | 예 | 쓰이는 곳 |
|---|---|---|
| `abs(x, y, w, h)` | `abs(110, 56)` | 덱 4개에 515곳 |
| 이름 붙인 상자 | `const WIN1 = { x: 60, y: 208, w: 640, h: 420 };` | 워크스루 창 등 |

미리보기에서 글자를 누르면, 그 요소부터 위로 올라가며 만난 자리들을 후보로 모은다. 글자를
눌렀어도 옮기고 싶은 것은 그 글자를 담은 상자나 창일 때가 많기 때문이다. 워크스루 창 안의
글자를 누르면 `WIN1 — 이름 붙인 상자`가 잡힌다.

계산해서 만든 좌표는 다루지 않는다. 숫자 리터럴이 있는 자리만 고칠 수 있다.

## 워크스루 포인터는 자동으로 다시 잰다

포인터가 찍는 자리(`TG21` 등)는 계산값이 아니라 브라우저에서 한 번 재서 적어 둔 값이다.
창을 옮기거나 키우면 **화면은 멀쩡한데 마우스만 옛 자리를 가리킨다.** 조용히 틀리는 고장이라
사람이 알아채기 어렵다. 그래서 자리를 저장할 때마다 다시 재서 같이 고친다.

어느 시각에 어느 대상을 찍는지는 소스를 뜯지 않고 알아낸다.

1. 고치기 **전에** 한 번 재서, 화살촉이 대상 중심에 닿는 (시각, 대상) 짝을 기억한다.
   대상 하나당 **가장 정확히 겨눈 순간 하나만** 남긴다. 창이 움직이는 도중에도 우연히
   가까워지는 순간이 있어서, 그것까지 세면 엉뚱한 값을 집어 온다.
2. 자리를 고쳐 쓴다.
3. 같은 시각에 그 대상의 새 중심을 읽어 `TG*.<열쇠>`에 넣는다. 대상은 창을 따라 움직이지만
   어느 대상을 찍으려 했는지는 변하지 않는다.
4. **다시 재서 실제로 닿는지 확인한다.** 그래도 빗나가는 자리가 있으면 화면과 기록에
   경고로 남긴다. 고쳐 놓고 끝내면 이 기능을 만든 이유가 사라진다.

재는 일은 walkthrough 스킬의 `measure_pointer.mjs`에 맡긴다. 같은 자를 쓰기 위해서다.
한 번 저장에 1분 가까이 걸리고, 창·포인터·기록이 **되돌리기 한 번에 함께** 물러난다.

## 씬(타임라인) 슬라이드

글자가 움직이는 동안에는 겨냥하기 어려우므로, 씬이 있는 쪽에서는 상단에 **⏸ 장면 멈춤**이
나타난다. 엔진이 이미 듣고 있는 `deck-scene-control` 이벤트를 쏘는 것이라 엔진은 건드리지
않는다. 움직임이 멎은 뒤에는 씬 안의 글자도 보통 슬라이드와 똑같이 집힌다.

다만 **씬이 계산해서 만든 글자는 찾을 수 없다.** 예를 들어 과녁 씬의 「오차 0.30」은 t에서
계산한 값이라 원본 어디에도 그런 글자가 없다. 이때는 후보가 0곳으로 나오고, 화면이 그렇게
알려 준다. 고치려면 그 숫자를 만드는 식을 직접 손봐야 한다.

## 같은 글자가 여러 곳에 있을 때

이 저장소의 덱은 같은 문구를 두세 곳에 적어 둔다. 슬라이드 제목이 `<Head title=…>`에 한 번,
레일 이름 `<Page nav=…>`에 한 번, 구역 주석에 한 번 들어가는 식이다. 한쪽만 고치면 화면과
레일이 어긋나므로, 화면은 세 가지를 한다.

1. **찾은 자리를 모두 보여 준다.** 파일과 줄 번호, 그 줄의 원문을 함께 띄운다.
2. **어느 것이 방금 누른 자리인지 표시한다.** 누른 요소부터 위로 올라가며 만난 소스 자리를
   전부 힌트로 쓴다. 글자를 그리는 컴포넌트 정의가 아니라 그 컴포넌트를 **부르는 쪽**에
   문구가 적혀 있기 때문이다. 슬라이드 감싸개까지 조상이라 여러 곳이 걸리므로, 표시는 가장
   가까운 한 곳에만 남긴다.
3. **한꺼번에 바꿀 수 있다.** 같은 파일에서 글자가 똑같은 자리가 둘 이상이면 「N곳 모두」
   단추가 나온다. 기본은 고른 한 곳만 바꾸는 것이다. 여러 자리를 바꿀 때는 **뒤에서부터**
   고쳐 앞의 위치가 밀리지 않게 하고, 자리마다 문법이 달라서(문자열 안인지 JSX 본문인지)
   이스케이프도 따로 한다. 되돌리기는 한 번에 전부 물러난다.

## 화면 글자와 원본이 어긋나는 세 자리

문구 찾기가 그냥은 안 되는 자리가 셋 있어서 서버가 보정한다.

1. **이스케이프된 따옴표** — `notes.ts`처럼 문자열 리터럴 안에 든 글은 소스에서 `\"`다.
   찾을 때 역슬래시를 넘기고, 편집 상자에는 이스케이프를 푼 꼴을 보여 준 뒤 저장할 때 다시
   씌운다. 그래서 상자에 보이는 것과 화면에 나오는 것이 같다.
2. **여러 조각을 이어 붙인 글자** — 소스에서는 `{앞} ({가운데}) · {뒤}`인데 화면에서는 한
   덩어리로 보인다. 통째로 못 찾으면 앞의 8·5·3·2·1 낱말로 좁혀 가며 다시 찾고, 몇 낱말로
   잡았는지 화면에 적어 준다. **바뀌는 것은 잡힌 그 조각뿐이다.**

   좁혀 찾을 때는 **앞뒤에 글자가 더 붙어 있으면 다른 낱말로 본다.** 이 울타리가 없으면
   `첫 명령`이 `첫 명령을` 안쪽에 걸려서, 바꾸고 나면 `첫 명령이다을`이 된다. 실제로 겪은
   일이라 시험에 그 자리를 그대로 남겨 두었다(2026-09-19).
3. **줄 번호 밀림** — 위의 2-1 참고.

## 알아 둘 것

- 슬라이드 둘이 한 줄에 있는 덱은 조작을 거부한다(경계를 가를 수 없다). 34개 덱 중에는 없다.
- 순서를 바꿔도 `{/* 1 — 도입 */}` 같은 번호 주석은 그대로다. 주석은 슬라이드를 따라 움직일 뿐
  번호가 다시 매겨지지 않는다.
- 복제본은 문구와 발표자 노트가 원본과 같다. 바꾸는 것은 사람 몫이다.
