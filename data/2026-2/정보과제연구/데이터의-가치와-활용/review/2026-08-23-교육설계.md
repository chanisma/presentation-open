# 동료 교사 심사 의견

## 1. 시간 배분

### 1-1. 1차시 11장은 45분 안에 소화되지 않는다

(원문 인용) → “전원 제출 대기 → 분포 공개 → ‘3번 고른 사람, 왜 그렇게 생각했어요?’ 한 명 지목”, “분포 공개 → 정답(예측)”, 사례 ①~④와 네 렌즈 설명까지 슬라이드 11장.  
(무엇이 문제인가) → 슬라이드당 평균 4분뿐인데, 투표 2회에 접속·제출·분포 해석·학생 발언까지 하면 최소 10~15분이 든다. 남은 30분으로 Reddit 계약, 올빼미버스, 부동산·화장품 서비스, 표준주소실록, AlphaFold, 네 렌즈를 다루면 사례당 2~4분에 그쳐 개념 설명이 아니라 정보 나열이 된다.  
(구체적 수정안) → 1차시를 ‘올빼미버스–네 렌즈–분류 논쟁’ 중심으로 줄이고, Reddit과 AlphaFold 중 하나는 읽기 자료로 돌려라. 슬라이드별 목표 시간을 명시해 `도입 4분–사례 15분–렌즈 12분–분류 활동 9분–정리 5분`으로 다시 설계하라.

### 1-2. 슬라이드 빌드와 외부 사이트가 숨은 시간을 잡아먹는다

(원문 인용) → “클릭 1~4”, “gjdong.vercel.app/facility 열기 ↗”, “공공데이터포털 ↗”, “서울 열린데이터광장 ↗”, “학교알리미 ↗”.  
(무엇이 문제인가) → 클릭 빌드, 사이트 접속, 로그인·로딩, 팝업, 모바일 화면 차이까지 시간표에 포함되지 않았다. 특히 공공데이터 사이트는 검색 결과와 상세 페이지 구조가 복잡해 10분 활동이 사이트 탐색만 하다 끝날 가능성이 높다.  
(구체적 수정안) → 외부 탐색을 자유 검색으로 두지 말고 교사가 검증한 데이터 링크 8~12개와 컬럼 미리보기 카드를 제공하라. 사이트 시연은 1개만 하고, 빌드 클릭 횟수도 최소화하라.

### 1-3. 2차시의 `10+10+10+10+5분`은 수업 운영 시간을 0분으로 계산한 계획이다

(원문 인용) → “1단계 ⏱ 10분”, “2단계 ⏱ 10분”, “3단계 ⏱ 10분”, “4단계 ⏱ 10분”, “5단계 ⏱ 5분”.  
(무엇이 문제인가) → 합계가 정확히 45분이라 출석, 기기 열기, 활동지 로그인, 단계 설명, 질문, 단계 전환, 저장 오류, 제출 확인 시간이 전혀 없다. 한 단계가 2분만 밀려도 마지막 자가 검증이 삭제된다. 가장 사고가 필요한 3~4단계가 앞 단계의 지연을 떠안는다.  
(구체적 수정안) → 실제 학생 작업 시간을 `6+8+10+9+5=38분`으로 줄이고, 도입·전환 4분과 제출 3분을 확보하라. 또는 1단계 데이터 사냥을 사전 과제로 옮기고 수업은 데이터 검증부터 시작하라.

### 1-4. 종료·제출·과제 지시가 서로 충돌한다

(원문 인용) → “마감: 수업 종료 5분 전”, “5단계 · 자가 검증 ⏱ 05:00”, “접근 경로 과제 — 다음 시간까지”.  
(무엇이 문제인가) → 5단계가 수업의 마지막 5분인데 제출 마감도 종료 5분 전이면 학생은 5단계를 시작하는 순간 이미 제출해야 한다. 더구나 ⓑ는 지금 답해야 하는 필수 칸인 동시에 다음 시간까지 수행할 과제로 제시된다.  
(구체적 수정안) → 수업 중 제출본에는 ⓑ를 “확인 예정 경로”로 받고, 다음 차시 전 수정 제출을 별도로 열어라. 마감은 종료 시점으로 바꾸고 마지막 3분은 저장·제출에만 배정하라.

### 1-5. 시간이 밀리면 핵심 목표가 아니라 표면 작업만 남는다

(원문 인용) → “세 개에서 막히는 게 정상 — 네 번째부터 진짜 아이디어가 나온다”, “네 가지를 다 그려 보고”, “하나라도 답이 안 나오면 기획서를 고친다.”  
(무엇이 문제인가) → 발산 5개, 렌즈별 4개, 기획서 작성, 반박 후 수정까지 반복을 요구하면서 각 단계에 10분만 준다. 실제로는 학생이 막힐 시간을 인정하면서도 막힘을 해소할 시간은 주지 않는다. 결과적으로 뒤 단계는 예시 복사와 빈칸 채우기로 끝난다.  
(구체적 수정안) → 질문은 우선 3개만 만들게 하고, 교사 피드백을 받은 학생만 5개로 확장하라. 렌즈도 4개 강제가 아니라 2개 비교 후 1개 선택으로 줄여 수정 시간을 확보하라.

## 2. 네 렌즈 분류의 논리적 결함

### 2-1. 네 렌즈는 같은 분류 기준에 놓여 있지 않다

(원문 인용) → “결합 — 상관없어 보이는 두 데이터를 붙이면?”, “변환 — 아무나 읽을 수 있게 바꾸면?”, “예측 — 과거 데이터로 앞을 말하면?”, “개방 — 내가 만든 결과를 남이 쓰게 하면?”  
(무엇이 문제인가) → 결합은 입력 데이터 구성 방식, 변환은 표현·처리 방식, 예측은 분석 목적, 개방은 배포·거버넌스 방식이다. 서로 배타적인 네 종류가 아니라 한 서비스의 서로 다른 단계이므로 ‘어떤 렌즈인가’라는 단일정답 분류가 성립하지 않는다.  
(구체적 수정안) → 네 항목을 분류가 아닌 설계 축으로 다시 정의하라. `입력: 결합 여부–처리: 요약/변환/예측–출력: 공개 범위`처럼 층위를 나누고 한 서비스에 여러 축이 동시에 적용된다고 명시하라.

### 2-2. ‘변환’의 범위가 지나치게 넓다

(원문 인용) → “이 데이터를 아무나 읽을 수 있게 바꾸면?”, “실거래가 → 지도 · 성분표 → 등급”, “시간표 옆에 오늘 메뉴 잔반 예보를 띄운다.”  
(무엇이 문제인가) → 지도화, 등급화, 요약, 시각화, 예보를 전부 변환으로 묶는다. 그런데 ‘잔반 예보’는 미래값 추정이라 예측이고, 성분 안전도 등급은 규칙 기반 분류 또는 평가이며, 지도는 시각화다. 학생은 결과를 화면에 표시하기만 하면 모든 서비스를 변환으로 주장할 수 있다.  
(구체적 수정안) → 변환을 “동일한 사실을 사람이 읽기 쉬운 표현으로 바꾸되 새로운 미래값을 만들지 않는다”로 제한하라. 시각화·요약·분류·예측의 차이를 반례와 함께 제시하라.

### 2-3. ‘개방’은 서비스 아이디어 생성 렌즈라기보다 사후 배포 선택이다

(원문 인용) → “내가 만든 결과를 남이 쓰게 하면?”, “급식실이 쓰게 공개”, “주간 잔반 리포트를 급식실·영양교사에게 연다.”  
(무엇이 문제인가) → 특정 부서에 리포트를 전달하는 것은 일반적으로 ‘개방’이 아니다. 개방은 접근 권한, 라이선스, 개인정보 처리, API·다운로드 형식 같은 조건을 포함해야 하는데 여기서는 단순 공유와 동일시된다. 따라서 결합·변환·예측과 같은 아이디어 생성 기능도 하지 못한다.  
(구체적 수정안) → ‘개방’을 “누구에게 어떤 권한과 형식으로 재사용하게 할 것인가”로 정의하고 공개·기관 내부 공유·개인화 제공을 구분하라. 아니면 렌즈에서 빼고 마지막 ‘배포 전략’ 단계로 이동하라.

### 2-4. 분류에 빠진 핵심 영역이 많다

(원문 인용) → “네 사례를 네 질문으로”, “같은 데이터 하나에 렌즈 넷 — 질문이 넷 나온다.”  
(무엇이 문제인가) → 기술적으로 흔한 탐색·검색, 집계·요약, 이상 탐지, 분류, 최적화, 추천, 인과 추론, 자동화가 네 렌즈 어디에도 안정적으로 들어가지 않는다. 이를 모두 변환이나 예측에 밀어 넣으면 분류가 설명력을 잃는다.  
(구체적 수정안) → 완전한 분류라고 주장하지 말고 “아이디어를 여는 네 가지 질문”이라고 한정하라. 추천·최적화·이상 탐지 같은 미포함 사례는 ‘기타 처리 방식’으로 명시하라.

### 2-5. 사례 ② 올빼미버스는 단순 ‘결합’만으로 설명되지 않는다

(원문 인용) → “렌즈 ① 결합”, “통화 × 택시 → GIS 유동인구 지도 → 노선·배차·정류장 확정”.  
(무엇이 문제인가) → 서로 다른 데이터를 겹친 것은 결합이 맞지만, 유동인구를 추정하고 노선·배차를 정한 것은 공간 변환, 수요 추정, 최적화까지 포함한다. ‘붙이자 밤에 사람이 보였다’는 설명은 결합만 하면 결론이 자동으로 나온다는 오해를 만든다.  
(구체적 수정안) → `결합 → 위치·시간 단위 정렬 → 수요 추정 → 노선 최적화` 과정을 분리해 보여라. 결합은 출발점이지 최종 가치 창출 방식이 아니라고 명시하라.

### 2-6. 사례 ③의 ‘변환+예측’ 판정은 세 회사를 한 덩어리로 묶은 오류다

(원문 인용) → “렌즈 ② 변환”, “렌즈 ③ 예측”, “호갱노노”, “직방 — 시세 예측”, “화해 — 주의 성분 2 · 지성 피부 적합”.  
(무엇이 문제인가) → 직방의 시세 추정은 예측일 수 있지만, 실거래가 표시와 성분 등급은 주로 결합·정제·규칙 기반 분류·시각화다. 세 사례 전체가 변환과 예측을 모두 쓴다고 읽히며, 서비스별 판정 근거가 분리되어 있지 않다.  
(구체적 수정안) → 회사별로 `입력 데이터–처리–출력–해당 렌즈` 표를 만들고, 호갱노노는 결합·시각화, 직방의 특정 기능만 예측, 화해는 규칙 기반 분류라고 구분하라.

### 2-7. 사례 ③의 “새로 수집한 데이터 0건”은 수업 논지를 위해 과장된 단정이다

(원문 인용) → “세 회사 모두, 새로 수집한 데이터 0건.”  
(무엇이 문제인가) → 서비스 운영 과정에서 사용자 행동, 리뷰, 관심 단지, 검색, 매물, 가격 수정 등 자체 데이터가 생긴다. 초기 구축을 공공데이터로 했다는 주장과 현재 서비스 전체가 새 데이터를 전혀 수집하지 않는다는 주장은 다르다. 반례 하나로 사례의 신뢰도가 무너진다.  
(구체적 수정안) → “초기 핵심 기능은 기존 공개데이터만으로도 시작할 수 있었다”처럼 범위를 한정하고, 공공데이터와 자체 수집 데이터가 각각 어떤 기능에 쓰이는지 구분하라.

### 2-8. 표준주소실록의 ‘변환’ 판정도 근거가 부족하다

(원문 인용) → “시설관리 대시보드 · 표준주소실록”, “렌즈 ② 변환”, “흩어진 데이터를 한 화면으로.”  
(무엇이 문제인가) → ‘흩어진 데이터’를 모았다면 먼저 결합·통합이다. 지도와 표로 보이는 것은 시각화다. 어떤 원자료가 어떤 규칙으로 변환되었는지 제시하지 않아 ‘변환’ 판정은 결과 화면의 외형만 본 분류다.  
(구체적 수정안) → 사용한 데이터셋 수, 공통 키, 정제 규칙, 지도 변환 과정을 제시하고 `결합+변환`으로 표시하라. 단일 렌즈 표기를 유지하려면 왜 결합보다 변환이 핵심인지 판정 기준을 써라.

### 2-9. AlphaFold를 ‘개방’ 사례로만 놓으면 핵심 연산이 사라진다

(원문 인용) → “렌즈 ④ 개방”, “PDB · 50년치 실험 데이터 → AlphaFold → 세계의 연구실”, “2억 개를 예측했고, 팔지 않고 풀었습니다.”  
(무엇이 문제인가) → AlphaFold의 핵심은 실험 구조를 학습해 미지의 구조를 예측한 것이며, 데이터베이스 공개는 그 결과의 배포 방식이다. 슬라이드 10에서는 다시 “구조 예측”을 예측 사례로 써서 같은 덱 안에서도 판정이 흔들린다.  
(구체적 수정안) → AlphaFold를 `결합 가능성–예측 생성–표준 형식 변환–개방 배포`의 복합 사례로 제시하라. 퀴즈에서도 복수 선택이 가능하다는 근거 사례로 사용하라.

## 3. 실시간 문항의 타당성

### 3-1. 첫 투표는 소유권과 경제적 가치를 한 문항에 섞었다

(원문 인용) → “어제 하루 내가 남긴 데이터는 누구 것이고, 얼마짜리일까?”, “정답은 없다.”  
(무엇이 문제인가) → ‘누구 것인가’는 개인정보보호, 플랫폼 약관, 저작권, 통제권의 문제이고 ‘얼마짜리인가’는 시장·집계 규모·사용 목적의 문제다. 하나의 선택지로 두 질문에 동시에 답할 수 없고, 선택지들도 서로 같은 기준에 있지 않다.  
(구체적 수정안) → 문항을 두 개로 나눠라. 첫째는 “누가 저장·통제할 수 있는가”, 둘째는 “개별 기록과 집계 데이터의 가치는 어떻게 달라지는가”로 묻고 토론 근거도 별도로 받아라.

### 3-2. 첫 투표의 선택지가 논쟁을 왜곡한다

(원문 인용) → “0원 — 그냥 사라진다”, “값을 매길 수 없다 — 모이면 다른 것이 된다”, “내 것이니까 내가 값을 정한다.”  
(무엇이 문제인가) → 데이터가 ‘0원’인 것과 ‘사라지는 것’은 별개이며, 집계되면 가치가 생긴다는 사실도 ‘값을 매길 수 없다’와 모순된다. 본인에 관한 데이터라는 사실만으로 개인이 거래가격을 결정할 수 있다는 선택지도 법적 소유권을 오해하게 한다.  
(구체적 수정안) → 선택지를 `개별 기록의 직접 거래가치`, `여러 기록과 결합된 분석 가치`, `개인에게 발생하는 위험`, `플랫폼의 통제권`처럼 비교 가능한 주장으로 다시 쓰고 선택 이유를 짧게 입력하게 하라.

### 3-3. 도서 추천 문항의 정답을 ‘예측’ 하나로 고정할 수 없다

(원문 인용) → “도서관 대출 기록으로 ‘이 책 빌린 사람이 다음에 빌릴 책’을 추천했다. 어떤 렌즈일까?”, 정답 “예측”.  
(무엇이 문제인가) → 다음 대출을 맞히는 확률 모델이라면 예측이지만, ‘이 책을 빌린 사람들이 함께 빌린 책’의 연관 규칙을 추천 목록으로 변환한 것일 수도 있다. 이용자·도서·대출 기록을 결합한 협업 필터링으로 설명할 수도 있으므로 구현 정보 없이 단일정답은 부당하다.  
(구체적 수정안) → “과거 대출 순서를 학습해 각 학생이 다음에 빌릴 책의 확률을 계산했다”라고 조건을 추가하면 예측이 된다. 현재 문장을 유지하려면 복수 응답 후 학생이 처리 방식을 근거로 판정하게 하라.

### 3-4. 오답 피드백이 스스로 문항의 단일정답성을 무너뜨린다

(원문 인용) → “정답 외 선택은 틀린 게 아니라 ‘다른 서비스’임을 짚고”, “틀린 게 아니라 다른 서비스예요.”  
(무엇이 문제인가) → 퀴즈에는 `answer: 2`가 설정되어 정오를 판정하면서 교사는 다른 답이 틀린 것이 아니라고 말한다. 평가 시스템과 수업 메시지가 충돌해 학생은 렌즈가 분류인지 발상 도구인지 알 수 없다.  
(구체적 수정안) → 정답형이 아니라 진단형 문항으로 바꾸고, “이 문장만으로 가장 직접적으로 드러난 렌즈”와 “추가 조건에 따라 가능한 렌즈”를 구분하라.

## 4. 활동에서 학생의 손이 멈추는 지점

### 4-1. 1단계에서는 컬럼 이름만으로 데이터의 가능성과 접근성을 판단할 수 없다

(원문 인용) → “내용은 안 봐도 된다 — 컬럼 이름만 본다. 컬럼 이름이 곧 ‘이 데이터가 아는 것’.”  
(무엇이 문제인가) → 컬럼 이름은 단위, 기간, 누락률, 갱신 주기, 공간 해상도, 값의 범주, 개인정보 여부를 알려주지 않는다. 예를 들어 ‘위치’가 주소인지 행정동인지 좌표인지에 따라 가능한 서비스가 완전히 달라진다. 학생은 이름만 보고 실제로 답할 수 없는 질문을 만든다.  
(구체적 수정안) → 최소 확인 항목을 `컬럼명–예시값 3행–단위–기간–갱신 주기–접근 방식`으로 바꿔라. 10분을 유지하려면 교사가 메타데이터 카드를 미리 제공하라.

### 4-2. 학교 데이터 목록은 ‘존재’와 ‘접근 가능’을 혼동시킨다

(원문 인용) → “우리 학교가 이미 가진 데이터”, “도서관 대출 이력”, “매점 판매”, “결석 · 조퇴”, “학교 데이터를 고르는 사람은 제가 컬럼 이름을 말해 줄게요.”  
(무엇이 문제인가) → 학교가 보유한다는 사실은 학생 프로젝트에 제공할 수 있다는 뜻이 아니다. 대출·판매·출결 데이터는 개인 식별, 내부 승인, 보유 시스템의 추출 가능성 문제가 있다. 컬럼만 알려주면 학생은 접근 가능하다고 오인한다.  
(구체적 수정안) → 목록을 `즉시 제공 가능–익명화 후 가능–협의 필요–사용 불가`로 등급화하고 실제 제공 가능한 표본 파일만 선택지로 제시하라.

### 4-3. 2단계의 질문 5개 강제는 다양성보다 문장 복제를 만든다

(원문 인용) → “그 목적 말고, 이 데이터가 답할 수 있는 질문 5개”, “억지로라도 5개”, “네 번째부터 진짜가 나온다.”  
(무엇이 문제인가) → 데이터의 범위가 좁으면 타당한 질문이 5개 나오지 않을 수 있다. 학생은 질문의 대상이나 표현만 바꾼 유사 문장을 채우거나, 데이터에 없는 변수를 상상해 억지 질문을 만든다. ‘많이 쓰면 창의적이 된다’는 근거도 제시되지 않는다.  
(구체적 수정안) → 3개를 필수로 하고 각 질문에 “어떤 컬럼으로 답하는가”를 쓰게 하라. 추가 2개는 확장 과제로 두고, 서로 다른 질문 유형이라는 조건을 붙여라.

### 4-4. 3단계에서 카드 B의 역할이 렌즈마다 일관되지 않는다

(원문 인용) → “이 둘을 어떻게 이을지를 렌즈마다 하나씩 적는다”, “변환 — 이 데이터를 아무나 읽을 수 있게 바꾸면?”, “개방 — 내가 만든 결과를 남이 쓰게 하면?”  
(무엇이 문제인가) → 결합에는 A와 B가 필요하지만 변환·예측·개방은 반드시 두 데이터를 연결하는 방식이 아니다. 예시의 변환과 개방에서는 시간표 데이터가 어떻게 쓰이는지 불분명하다. 학생은 네 칸에 같은 아이디어를 말만 바꿔 적는다.  
(구체적 수정안) → 3단계를 `A+B로 만들 수 있는 처리 2개`와 `그 결과의 표현·공개 방식`으로 분리하라. 모든 칸에 두 데이터가 필요하다고 강제하지 말고, 사용하지 않는 데이터는 삭제하도록 허용하라.

### 4-5. 3단계의 “멀어 보이는 둘”은 결합 가능한 공통 키를 무시한다

(원문 인용) → “멀어 보이는 둘일수록 남이 못 본 연결이 나온다.”  
(무엇이 문제인가) → 서로 흥미롭게 보인다고 결합할 수 있는 것은 아니다. 날짜, 위치, 학번, 시간대 같은 공통 연결 키와 동일한 집계 수준이 없으면 두 데이터는 기술적으로 연결되지 않는다. 학생은 의미 없는 상관관계를 발명할 가능성이 높다.  
(구체적 수정안) → 카드 B 선택 전에 “무엇으로 연결할 것인가: 날짜/시간/장소/개체 ID”를 필수로 쓰게 하라. 공통 키가 없으면 다른 데이터를 고르도록 판정 규칙을 제시하라.

### 4-6. 4단계의 여섯 칸은 데이터 기반 기획의 핵심 조건을 담지 못한다

(원문 인용) → “[누가] [어떤 상황] [문제] [데이터 A+B] [렌즈] [무엇]”, “여섯 칸이 채워지면 끝.”  
(무엇이 문제인가) → 산출값, 사용자 행동, 성공 기준, 데이터 갱신 주기, 개인정보 위험이 없다. 문법상 빈칸만 채우면 “학생의 불편을 데이터로 앱으로 해결한다” 같은 검증 불가능한 문장이 통과한다. 이 문장을 그대로 코딩 프롬프트로 쓰기에도 기능 명세가 부족하다.  
(구체적 수정안) → 최소한 `[어떤 값을 계산·표시하는가]`, `[사용자가 그 결과로 무엇을 하는가]`, `[성공 여부를 무엇으로 판단하는가]`를 추가하라. 한 문장을 고수한다면 보조 체크리스트로 분리하라.

### 4-7. 예시 기획서 자체가 ‘결합’의 가치를 증명하지 못한다

(원문 인용) → “시간표 + 시내버스 도착 정보”, “결합”, “하교 시각 맞춤 버스 알림판.”  
(무엇이 문제인가) → 야간자율학습 학생이 모두 밤 9시에 하교한다면 시간표 데이터 없이 고정 시각과 버스 API만으로 구현할 수 있다. 불필요한 데이터 하나를 억지로 더한 예시라 학생도 ‘A+B’ 형식을 맞추기 위해 장식용 데이터를 붙이게 된다.  
(구체적 수정안) → 학생별 실제 종료 시각이 요일·수업에 따라 달라지고, 시간표 데이터가 알림 시각을 변경한다는 조건을 넣어라. 각 데이터가 결과에 어떤 값을 제공하는지도 쓰게 하라.

### 4-8. 5단계는 검증이 아니라 자기보고에 그친다

(원문 인용) → “하나라도 답이 안 나오면 4단계로 돌아가 고친다”, “그 데이터, 진짜로 존재하고 내가 접근할 수 있나?”  
(무엇이 문제인가) → 학생은 시간이 없으므로 “API 있음”, “교무실 협조”라고 추측해 쓰고 통과할 수 있다. 링크, 샘플 응답, 담당자 확인이 없어도 사실 여부를 판정할 장치가 없다. 자기 아이디어를 스스로 죽이라는 요구도 확인 편향 때문에 제대로 작동하지 않는다.  
(구체적 수정안) → 짝과 기획서를 교환해 상대가 반박하게 하고, ⓑ에는 URL·파일 미리보기·담당자 확인 중 하나를 증거로 첨부하게 하라. 증거가 없으면 ‘미검증’으로 표시하고 다음 차시 코딩 대상에서 제외하라.

### 4-9. 5분 안에 검증 후 4단계로 돌아가 수정하는 것은 불가능하다

(원문 인용) → “⏱ 5분”, “하나라도 답이 안 나오면 4단계로 돌아가 고친다.”  
(무엇이 문제인가) → 세 질문에 답하고, 접근 경로를 확인하고, 문제가 있으면 데이터와 기획을 다시 선택하는 반복을 5분 안에 할 수 없다. 학생은 수정 대신 모든 질문에 형식적인 긍정 답변을 적게 된다.  
(구체적 수정안) → 자가 검증을 최소 10분으로 늘리고 4단계 시간을 줄여라. 또는 검증을 다음 차시의 첫 관문으로 옮겨 증거 확인 후 구현 여부를 결정하라.

## 5. 두 가지 이상으로 해석되는 활동 지시

### 5-1. 2단계에서 처리할 데이터 개수가 슬라이드와 활동지에서 다르다

(원문 인용) → 슬라이드 14 “데이터마다 두 칸을 채운다”, 활동지 “셋 중 주력 데이터 하나를 고르고 두 칸을 채운다.”  
(무엇이 문제인가) → 학생은 데이터 3개 모두에 원래 목적과 질문 5개를 써야 하는지, 주력 데이터 1개만 써야 하는지 다르게 해석할 수 있다. 전자라면 질문 15개를 10분에 써야 하므로 사실상 불가능하다.  
(구체적 수정안) → 양쪽 모두 “세 데이터 중 하나를 주력으로 고르고, 그 하나에 대해서만 두 칸을 채운다”로 통일하라.

### 5-2. “내용은 안 봐도 된다”의 ‘내용’이 무엇인지 불분명하다

(원문 인용) → “데이터셋 3개를 고른다. 내용은 안 봐도 된다 — 컬럼 이름만 본다.”  
(무엇이 문제인가) → 실제 행 값을 보지 말라는 뜻인지, 데이터 설명·수집 범위·갱신 주기까지 보지 말라는 뜻인지 모호하다. 학생에 따라 메타데이터 확인 수준이 달라지고 결과물의 타당성이 달라진다.  
(구체적 수정안) → “전체 데이터를 분석하지는 않는다. 단, 설명, 기간, 갱신 주기, 컬럼 정의와 예시 3행은 확인한다”로 바꿔라.

### 5-3. “이 데이터가 답할 수 있는 질문”의 증거 기준이 없다

(원문 인용) → “그 목적 말고 답할 수 있는 질문 5개.”  
(무엇이 문제인가) → 데이터만으로 직접 답해야 하는지, 다른 데이터를 추가해 답해도 되는지, 상관관계 수준이면 되는지, 원인을 설명해야 하는지 알 수 없다. 예시의 “관광객은 어디로 움직이나?”도 통화 기록만으로 관광객을 식별할 수 있는지가 불명확하다.  
(구체적 수정안) → “현재 컬럼만으로 계산 가능한 질문”과 “추가 데이터가 있어야 가능한 질문”을 구분해 표시하게 하고, 질문마다 사용 컬럼을 적게 하라.

### 5-4. “렌즈마다 연결 하나씩”에서 ‘연결’의 뜻이 바뀐다

(원문 인용) → “이 둘을 어떻게 이을지를 렌즈마다 하나씩 적는다”, “네 렌즈, 네 가지 연결.”  
(무엇이 문제인가) → 결합에서는 데이터 간 연결을 뜻하지만, 변환에서는 표현 변경, 예측에서는 미래값 생성, 개방에서는 사용자에게 배포하는 것을 뜻한다. 같은 단어가 데이터 관계와 서비스 처리·배포를 모두 가리킨다.  
(구체적 수정안) → “연결” 대신 “두 데이터로 시도할 아이디어”라고 쓰고, 각 칸에 `입력–처리–출력`을 따로 적게 하라.

### 5-5. 카드 B 선택 범위가 확정되지 않았다

(원문 인용) → “1단계 ①②③ 중 하나 — 직접 써도 된다.”  
(무엇이 문제인가) → “직접 써도 된다”가 1단계에서 고르지 않은 새 데이터도 허용한다는 뜻인지, 데이터 이름을 선택 메뉴 대신 직접 입력하라는 뜻인지 모호하다. 새 데이터를 허용하면 1단계의 실재·출처 확인 절차를 우회한다.  
(구체적 수정안) → “카드 B는 1단계의 나머지 두 데이터 중 하나만 선택한다. 새 데이터는 교사 확인 후 추가할 수 있다”로 제한하라.

### 5-6. ‘개방’의 대상과 범위가 모호하다

(원문 인용) → “내가 만든 결과를 남이 쓰게 하면?”, “급식실·영양교사에게 주간 리포트 공개.”  
(무엇이 문제인가) → 특정 담당자에게 보내는 것, 학교 내부에서 공유하는 것, 인터넷에 공개하는 것, API로 재사용하게 하는 것이 모두 같은 말처럼 취급된다. 개인정보가 있는 데이터에서는 이 차이가 치명적이다.  
(구체적 수정안) → 대상·범위·형식을 각각 쓰게 하라: `[누구에게] [원자료/집계 결과 중 무엇을] [화면/파일/API로] [어떤 권한으로] 제공한다`.

### 5-7. ⓑ가 현재 필수 답변인지 숙제인지 불분명하다

(원문 인용) → “그 데이터, 진짜로 존재하고 내가 접근할 수 있나? *”, “접근 경로 과제 — 다음 시간까지.”  
(무엇이 문제인가) → 별표는 지금 반드시 작성해야 한다는 뜻인데 접근 경로는 다음 시간까지 찾으라고 한다. 학생은 추측을 적어야 하는지, 빈칸 제출이 가능한지 판단할 수 없다.  
(구체적 수정안) → 수업 중에는 `확인됨/확인 필요/접근 불가`를 선택하게 하고, ‘확인 필요’ 학생만 다음 시간까지 증거 링크나 담당자 확인을 추가하게 하라.

## 6. 교사 개입이 없을 때 망가지는 실패 시나리오

### 6-1. 존재하지 않는 학교 데이터로 그럴듯한 앱을 기획한다

(원문 인용) → “우리 학교가 이미 가진 데이터”, “학교 데이터를 고르는 사람은 제가 컬럼 이름을 말해 줄게요”, “API · 다운로드 · 학교 협조 — 셋 중 무엇으로?”  
(무엇이 문제인가) → 학생은 ‘도서관 대출 이력+결석 기록’을 골라 개인별 학습 추천을 기획하지만 실제 데이터는 개인정보 때문에 받을 수 없다. ⓑ에는 “담당 교사 협조”라고 적고 제출한 뒤 3차시에서 데이터 없이 가짜 화면만 만든다.  
(구체적 수정안) → 수업 전에 제공 가능 여부를 확정한 데이터만 카드로 배포하고, 접근 증거가 없는 기획서는 구현 단계로 넘기지 마라.

### 6-2. 공통 키가 없는 데이터를 억지로 결합해 허위 상관관계를 만든다

(원문 인용) → “멀어 보이는 둘일수록 남이 못 본 연결이 나온다”, “잔반량 × 시간표.”  
(무엇이 문제인가) → 학생은 ‘분실물 데이터+학교 주변 사고 지점’을 선택하고 “사고가 많은 날 분실물이 늘어난다” 같은 이야기를 만든다. 기간·위치 단위가 다르거나 표본이 적어 결합할 수 없는데도 신선한 아이디어처럼 포장된다.  
(구체적 수정안) → 결합 전에 공통 키, 기간 중첩, 관측 단위, 최소 표본 수를 확인하는 기술적 관문을 넣고 하나라도 없으면 데이터 조합을 바꾸게 하라.

### 6-3. 예시의 문법만 복사한 ‘알림판/대시보드’가 양산된다

(원문 인용) → “오늘 메뉴 잔반 예보 전광판”, “하교 시각 맞춤 버스 알림판”, “한 지역구의 공공 시설 데이터를 지도·표 대시보드로.”  
(무엇이 문제인가) → 학생은 문제와 사용자 검증 없이 모든 결과를 “맞춤 알림 앱”, “지도 대시보드”, “주간 리포트”로 끝낸다. 여섯 칸은 채워지지만 데이터가 어떤 계산을 하고 사용자의 어떤 결정을 바꾸는지는 비어 있다.  
(구체적 수정안) → 산출물 유형을 평가하지 말고 “서비스가 보여 주는 정확한 값”과 “그 값 때문에 사용자가 바꾸는 행동”을 필수로 쓰게 하라. 같은 유형의 산출물이 반복되면 다른 처리 방식을 요구하라.

## 7. 고등학생 눈높이에서 어려운 개념·어휘

### 7-1. 기술·사업 용어가 설명 없이 연속해서 나온다

(원문 인용) → “API 한 줄”, “GIS 유동인구 지도”, “법정동 코드”, “공공 API”, “바이브코딩.”  
(무엇이 문제인가) → 학생은 API를 데이터 자체, GIS를 지도 그림, 법정동 코드를 우편번호 정도로 오해할 수 있다. ‘바이브코딩’은 비공식적 유행어라 수행 과제의 정확한 범위를 알려 주지 못한다.  
(구체적 수정안) → 각 용어를 한 문장으로 정의하고 실제 입력·출력 예를 붙여라. “바이브코딩”은 “AI에게 요구사항을 주고 코드를 생성·검토·수정하는 작업”처럼 수행 행동으로 풀어 써라.

### 7-2. 분석 개념의 경계가 고등학생에게 설명되지 않는다

(원문 인용) → “예측”, “추천”, “시세 예측”, “상관없어 보이는 두 데이터를 붙이면?”  
(무엇이 문제인가) → 추천과 예측의 차이, 결합과 상관관계의 차이, 상관관계와 인과관계의 차이가 없다. 학생은 두 데이터를 붙인 뒤 함께 변하는 패턴만 있으면 원인과 해결책까지 입증했다고 오해할 수 있다.  
(구체적 수정안) → `결합=표를 연결함`, `상관=함께 변함`, `예측=모르는 값 추정`, `인과=하나가 다른 하나를 변화시킴`, `추천=선택 후보의 순위를 정함`을 짧은 반례와 함께 가르쳐라.

### 7-3. 경제적 가치 설명이 기업 가치·매출·계약액을 뒤섞는다

(원문 인용) → “연 6천만 달러”, “하루 · 30억 달러”, “계약은 연매출의 1.4%짜리였다”, “시장에 값을 매긴 건…”.  
(무엇이 문제인가) → 계약액, 연매출 비율, 주가 하락에 따른 시가총액 변화는 서로 다른 개념이다. 학생은 데이터 계약이 실제로 30억 달러의 현금 손실을 발생시킨 것으로 오해할 수 있다.  
(구체적 수정안) → 계약액·매출·시가총액을 각각 정의하고 “30억 달러는 실제 지출이 아니라 주식시장에서 평가된 기업가치 감소”라고 명시하라.

### 7-4. 개인정보·윤리 개념이 가치 창출 서사에서 빠져 있다

(원문 인용) → “통화 기록”, “도서관 대출 이력”, “결석 · 조퇴”, “데이터의 가치는 ‘무엇에 쓸 수 있나’에서 나온다.”  
(무엇이 문제인가) → 학생에게 목적 외 이용을 창의성으로 장려하면서 동의, 익명화, 최소 수집, 재식별 위험, 목적 제한을 다루지 않는다. 특히 학교 데이터는 민감한 개인 행동을 포함할 수 있어 “원래 목적 밖에서 쓰기”가 그대로는 위험한 지시다.  
(구체적 수정안) → 모든 아이디어에 `법적으로 가능한가–개인을 식별할 필요가 있는가–집계 데이터로 대체 가능한가`를 검토하는 개인정보 렌즈를 추가하라. 목적 외 활용은 공익성과 안전조치가 있을 때만 허용된다고 제한하라.

# 치명적 3가지

## 1순위 — 2차시 시간표가 구조적으로 성립하지 않는다

(원문 인용) → “10분+10분+10분+10분+5분”, “마감: 수업 종료 5분 전.”  
(무엇이 문제인가) → 활동 시간만으로 45분을 모두 쓰며 마지막 검증 시간과 제출 마감이 충돌한다. 수업은 높은 확률로 3단계 이후 급조되고, 가장 중요한 검증과 수정이 사라진다.  
(구체적 수정안) → 데이터 사냥을 사전 과제로 전환하고, 2차시는 `검증된 데이터 선택–질문 생성–두 축 비교–기획–상호 검증–제출`에 집중하라.

## 2순위 — 네 렌즈가 서로 배타적인 분류가 아닌데 단일정답처럼 가르친다

(원문 인용) → “어떤 렌즈일까?”, 정답 “예측”, “렌즈 ④ 개방” AlphaFold.  
(무엇이 문제인가) → 입력 결합, 처리 변환·예측, 배포 개방을 같은 층위에 두면서 하나만 고르게 한다. 사례 판정과 퀴즈 정답이 계속 반론에 노출되어 수업의 핵심 도구 자체가 신뢰를 잃는다.  
(구체적 수정안) → 네 렌즈를 복수 적용 가능한 설계 축으로 재구성하고 단일선택 퀴즈를 복수선택·근거 설명형으로 바꿔라.

## 3순위 — 데이터의 ‘실재’만 확인하고 실제 결합·접근 가능성은 확인하지 않는다

(원문 인용) → “컬럼 이름만 본다”, “멀어 보이는 둘일수록”, “학교 협조.”  
(무엇이 문제인가) → 예시값·단위·기간·공통 키·권한을 보지 않은 채 아이디어부터 만들게 한다. 그 결과 3차시에는 접근 불가능하거나 서로 연결되지 않는 데이터를 전제로 한 가짜 서비스만 남는다.  
(구체적 수정안) → 1단계에서 예시 행, 기간, 갱신 주기, 접근 증거를 확인하고 3단계에서 공통 키를 필수로 검증하라. 이 두 관문을 통과하지 못한 데이터는 기획서에 사용할 수 없게 하라.
