## 정식 용어

| 용어 | 화면과 설명에서 사용할 의미 |
|---|---|
| 바이브코딩 | 자연어로 원하는 동작을 설명하고 AI가 생성·수정한 프로그램을 실행하며 결과를 다듬는 개발 방식. 이 수업에서는 이를 문제 해결의 도구로 사용한다. |
| 문제 발견 | 누가 어떤 상황에서 무엇 때문에 어려운지 구체적으로 알아내는 과정. |
| 문제 분해 | 넓거나 복잡한 문제를 구체적인 상황·과정·작은 문제로 나누는 것. |
| 핵심 문제 | 해결되면 사용자의 어려움이 실제로 줄어드는 중요한 문제. 오늘 고른 것은 관찰과 사용으로 확인할 후보이다. |
| 해결 아이디어 | 발견한 문제를 줄이기 위해 제안하는 방법. 문제 문장과 구분한다. |
| 성공 기준 | 도구를 사용한 뒤 문제가 줄었는지 확인할 수 있는 관찰 가능한 기준. |
| 브레인스토밍 | 평가를 잠시 미루고 여러 아이디어를 낸 뒤, 서로의 생각을 연결하고 발전시키는 활동. |
| 인공지능 에이전트 | 목표와 지시를 받아 여러 작업 단계를 수행하는 AI 도구. 구체적인 사용법은 다음 시간에 배운다. |
| 프로젝트 기획 문서 | 누구의 어떤 문제를 어떤 기능으로 해결하고 어떻게 확인할지 정리한 문서. 다음 시간에 AI와 작성한다. |

정의·화면 라벨·댓글 양식에는 위 용어를 사용한다. 바이브코딩의 역사적 명명이나 통계, 특정 제품의 성능은 이번 수업 범위에 넣지 않는다.

## Slide 1 — 최근에 “이건 좀 편해졌으면” 했던 순간
- form: static
- 시간: 2분

**핵심 메시지:** 내가 겪은 구체적인 불편이 이 수업의 출발점이다.

**핵심 내용:**
- 수업 제목: 2026-2 바이브코딩 오리엔테이션.
- 큰 질문: “최근에 귀찮았거나, 자꾸 헷갈렸거나, 반복해서 했던 일은?”
- 예시 한 줄: “수행평가 준비물을 확인하려고 여러 공지를 다시 찾았다.”

**형태 설계:** 좌측 상단 작은 수업명, 좌측 70%에 질문을 크게 배치하는 타이포 구도. 우측 하단에 짧은 경험 문장 하나만 둔다. 컴포넌트 제안: Heading + Quote. 정지 화면이며 빌드 없음. 장식 아이콘·앱 로고 없음.

**발표자 노트:** “오늘은 여러분이 해결하고 싶은 문제를 찾는 시간입니다. 최근에 불편했던 순간을 하나 떠올려 보세요.” 혼자 생각할 시간을 짧게 주고 자원자 1~2명의 말을 듣는다. 아이디어가 바로 안 떠올라도 뒤의 예제와 친구의 댓글을 통해 시작할 수 있다고 안내한다.

## Slide 2 — AI와 프로그램을 만들고, 문제를 해결한다
- form: build
- 시간: 3분

**핵심 메시지:** 바이브코딩은 AI의 코드 생성 능력을 활용해 내가 필요한 해결 도구를 만드는 방법이다.

**핵심 내용:**
- 정의: “원하는 동작을 말로 설명하고, AI가 만든 프로그램을 실행하며 결과를 다듬는 개발 방식.”
- AI에게 맡기는 작업: 코드 초안 생성·수정, 오류 해결 방안 제안.
- 내가 해야 하는 판단: 무엇을 해결할지 정하기, 요구를 구체화하기, 직접 써 보고 도움이 되는지 확인하기.
- 수업의 관점: “문제 해결을 위해 바이브코딩을 사용한다.”

**형태 설계:** 정의를 화면 상단의 큰 문장으로 고정. 아래 좌측에는 ‘AI가 수행할 작업’을 짧게, 우측 넓은 영역에는 ‘내가 판단할 것’을 실제 동사로 배치. 컴포넌트 제안: 비대칭 Split + Build. at=1 정의, at=2 AI 작업, at=3 사람의 판단, at=4 수업의 관점. 마지막 문장을 가장 강하게 강조한다.

**발표자 노트:** “코드를 만드는 과정에 AI의 도움을 받습니다. 그렇지만 무엇을 만들어야 도움이 되는지, 정말 문제가 줄었는지는 우리가 판단해야 합니다. 이 수업에서 연습할 것은 그 전체 과정입니다.” ‘AI에게 한 번 말하면 자동으로 완성된다’는 기대를 여기서 바로잡는다.

## Slide 3 — 문제를 찾고, 나누고, 만들어 확인한다
- form: scene
- scene: metaphor: 작업 기록 위에서 같은 문제 문장이 관찰·분해·제작·확인을 거치며 고쳐지는 순환 | emotion: 주도감 | intent: 코드 생성 전후의 판단과 반복까지가 수업의 목표임을 보여 준다
- 시간: 3분

**핵심 메시지:** 수업의 목표는 문제 발견부터 AI를 활용한 제작과 확인까지 직접 해 보는 것이다.

**핵심 내용:**
- 해결하고 싶은 문제 제시 → 작은 문제로 나누기 → 핵심 문제 후보 선택.
- AI와 작은 도구 만들기 → 직접 사용해 확인하기 → 문제나 방법 수정하기.
- 오늘의 범위: 문제 제시·분해·핵심 문제 후보 발견.

**형태 설계:** 좌측의 큰 ‘문제 문장’과 우측으로 이어지는 작업 경로를 둔다. t=0–2초 문제 제시, 2–4초 구체 상황과 핵심 문제 후보 표시, 4–6초 작은 도구와 사용 결과 표시, 6–8초 결과에서 원래 문제 문장으로 수정 선이 돌아간다. 오늘 맡는 앞부분은 코발트 괄호로 묶고 이후 제작은 옅게 둔다. 컴퓨터나 인물 삽화 없이 문장·선·상태 변화로 표현. 정지 최종 화면에서도 전체 흐름이 읽혀야 한다.

**발표자 노트:** “처음 떠올린 문제가 끝까지 그대로일 필요는 없습니다. 작게 만들고 사용해 보다가 더 중요한 문제를 발견할 수도 있어요. 오늘은 그 출발점인 문제 후보를 함께 찾아봅니다.”

## Slide 4 — “학교생활을 편하게”를 어디까지 나눌까?
- form: build
- 시간: 4분

**핵심 메시지:** 큰 주제를 구체적인 사람·상황·막히는 과정으로 나누면 해결할 문제를 발견할 수 있다.

**핵심 내용:**
- 큰 범주: 학교생활을 편하게 하고 싶다.
- 상황 선택: 수행평가를 준비할 때.
- 과정 분해: 공지 찾기 / 마감 확인 / 준비물 확인 / 준비 완료 확인.
- 구체적인 불편: 준비물 정보가 여러 공지에 흩어져 있어 확인할 때마다 다시 찾는다.
- 핵심 문제 후보: “수행평가를 준비하는 학생이 흩어진 준비물 정보를 한 번에 확인하기 어렵다.”

**형태 설계:** 화면 좌측 상단 큰 범주에서 시작해 오른쪽 아래의 구체 문장으로 좁혀지는 문제 분해도. 컴포넌트 제안: 텍스트 트리 + Build. at=1 범주, at=2 상황, at=3 네 과정의 분기, at=4 준비물 확인 분기 강조, at=5 핵심 문제 후보를 하단의 큰 문장으로 공개. 나머지 분기도 읽을 수 있게 남겨 여러 선택지가 가능함을 보여 준다.

**발표자 노트:** “학교생활 전체를 해결하려 하면 너무 큽니다. 언제, 어떤 일을 하다가 막히는지 나눠 봅시다. 이 예에서는 준비물 확인을 골랐지만 여러분에게는 마감 확인이 더 중요한 문제일 수도 있습니다.” 가상 예제임을 밝히고 모든 학생에게 같은 불편이 있다고 가정하지 않는다. 핵심 문제는 작게 나누었다는 이유만으로 확정되는 것이 아니라 실제 불편을 확인해야 하는 후보임을 덧붙인다.

## Slide 5 — 진로에서 시작해도, 내 일상에서 시작해도 좋다
- form: static
- 시간: 2분

**핵심 메시지:** 진로와 연결된 문제도, 내가 필요한 작은 도구도 충분히 의미 있는 출발점이다.

**핵심 내용:**
- 진로·관심사 예: 교육에 관심 → 친구에게 설명할 때 어떤 개념을 어려워하는지 기억하기 어렵다 → 어려웠던 개념을 기록하는 도구.
- 생활 예: 동아리 활동 → 빌린 물품을 어디서 반납해야 하는지 자꾸 다시 묻는다 → 물품별 반납 장소를 찾는 도구.
- 개인적 필요 예: 책 읽기 → 예전에 적은 문장이 어느 책에 있었는지 찾기 어렵다 → 문장과 책을 함께 검색하는 도구.
- 선택 기준: “누가 언제 불편한지 구체적으로 말할 수 있는가?”

**형태 설계:** 넓은 좌측에 생활·개인 필요 두 사례를 서로 다른 길이의 문장으로 배치하고, 우측 좁은 칼럼에 진로 연결 사례를 둔다. 각 사례에서 ‘불편’에 동일한 강조선을 사용한다. 하단 선택 기준을 크게 둔다. 컴포넌트 제안: 비대칭 Split + 짧은 사례 목록. 빌드 없음. 세 사례를 동일 크기 카드로 만들지 않는다.

**발표자 노트:** “진로와 연결하고 싶은 문제가 있다면 좋습니다. 아직 그런 고민을 하지 않았어도 괜찮아요. 내가 계속 쓰고 싶은 작은 도구를 만드는 것도 좋은 프로젝트입니다.” 여기의 도구는 정답 목록이 아니라 문제에서 해결 아이디어로 넘어가는 예시라고 설명한다.

## Slide 6 — 첫 도구는 핵심 문제 하나부터
- form: scene
- scene: metaphor: 기능 명세에서 곁가지가 접히고 입력·출력·사용 확인만 남는 첫 도구의 축소 모형 | emotion: 해볼 만함 | intent: 문제를 작은 구현 단위와 확인 가능한 기준으로 연결한다
- 시간: 3분

**핵심 메시지:** 핵심 문제 하나를 해결하는 작은 기능부터 만들고 실제 도움이 되는지 확인한다.

**핵심 내용:**
- 선택한 문제: 흩어진 준비물 정보를 한 번에 확인하기 어렵다.
- 첫 기능: 과목·날짜·준비물을 직접 입력하면 날짜별 준비물 목록으로 보여 준다.
- 나중 후보: 자동 공지 수집·알림·친구 공유. 지금 필요한지는 사용 후 판단한다.
- 성공 기준: 입력한 수행평가 사례의 준비물을 원래 공지를 다시 찾지 않고 목록에서 정확히 확인할 수 있다.

**형태 설계:** 오른쪽 큰 영역에 첫 도구의 ‘입력→목록’ 변화를 배치하고 왼쪽 여백에 후보 기능이 접히며 보류되는 짧은 명세를 둔다. t=0–2초 여러 기능 후보, 2–4초 첫 기능만 남김, 4–6초 예시 입력 ‘과학 / 9월 15일 / 색연필’이 목록에 표시, 6–8초 원래 입력과 목록을 대조하여 확인 표시. 임의 날짜는 가상 예시로 표기. 마지막 화면에 성공 기준을 함께 유지. 실제 실행 앱으로 오인하지 않도록 ‘첫 도구 예시’ 라벨 사용.

**발표자 노트:** “먼저 직접 입력하는 목록만으로 도움이 되는지 볼 수 있습니다. 목록을 써도 불편이 그대로라면 중요한 문제가 다른 데 있었을 수 있어요. 이때 기능을 더 붙이기 전에 문제부터 다시 봅니다.” 오늘 구현이나 자동 수집을 요구하지 않는다.

## Slide 7 — 수업 시간은 시도와 질문을 나누는 시간
- form: static
- 시간: 2분

**핵심 메시지:** 직접 제작하며 능력을 기르고, 수업 시간에는 시도에서 생긴 질문을 함께 해결한다.

**핵심 내용:**
- 학생: 직접 시도하고 만들기 → 막힌 지점 기록 → 질문 → 다시 시도.
- 교사: 필요한 개념과 바이브코딩 팁 제공, 질문과 피드백 지원.
- “질문은 수업 시간에만 하는 것이 아닙니다. 언제든 찾아와 질문해도 됩니다.”

**형태 설계:** 화면 중앙보다 왼쪽에 학생의 행동 순서를 큰 한 줄로 배치한다. 교사의 지원은 그 아래 좁은 주석 띠로 연결한다. 우측 하단에 질문 가능 안내를 별도로 둔다. 컴포넌트 제안: Process + Callout. 빌드 없음. 주차별 강의 목차나 일방적인 수강 규칙 목록으로 확장하지 않는다.

**발표자 노트:** “팁과 필요한 설명은 나눠 드리지만 실제 제작은 여러분이 직접 합니다. 수업 시간을 여러분이 해 본 것을 가져와 질문하고 다시 시도하는 시간으로 생각해 주세요. 수업 밖에서도 언제든 찾아와 질문할 수 있습니다.”

## Slide 8 — 좋은 질문에는 내가 해 본 일이 담긴다
- form: build
- 시간: 3분

**핵심 메시지:** 목표·시도·기대 결과·실제 결과를 보여 주면 함께 다음 시도를 찾기 쉽다.

**핵심 내용:**
- 질문 틀: “___을 하려고, ___을 해 봤습니다. ___을 기대했는데 실제로는 ___입니다. ___을 함께 확인하고 싶습니다.”
- 예시: “준비물을 날짜순으로 보려고 AI에게 정렬을 요청했어요. 9월 2일이 먼저 나올 줄 알았는데 9월 15일이 먼저 나와요. 입력과 결과를 함께 봐 주세요.”
- 시작 자체가 막혔다면: “이 문제를 나눠 봤지만 무엇부터 시도해야 할지 모르겠어요.”도 질문이다.

**형태 설계:** 좌측 좁은 영역에 목표·시도·기대·실제·도움의 라벨을 두고, 우측 큰 영역에서 한 학생의 질문 문장이 순서대로 완성되게 한다. 컴포넌트 제안: Quote + Build. at=1 목표와 시도, at=2 기대와 실제, at=3 도움 요청, at=4 시작이 막힌 경우의 질문을 하단에 작게 공개. 질문 형식을 채점표처럼 표현하지 않는다.

**발표자 노트:** “스스로 해 본 일이 있어야 무엇이 어려운지 구체적으로 보입니다. 그렇다고 오래 혼자 버티거나 완벽한 질문을 만들어야 찾아올 수 있다는 뜻은 아니에요. 시작이 막히면 어디까지 생각했는지를 보여 주세요.” 오류 원인을 미리 단정하지 않고 입력과 결과부터 함께 살펴본다.

## Slide 9 — 먼저 넓게 내고, 그다음 작게 좁힌다
- form: build
- 시간: 3분

**핵심 메시지:** 브레인스토밍에서는 아이디어를 충분히 낸 뒤, 구체적인 문제 하나로 좁힌다.

**핵심 내용:**
- 발산: 당장 만들 수 있는지 평가하기보다 불편했던 상황을 여러 개 적는다.
- 연결: 친구의 아이디어에 “누가?”, “언제?”, “어떤 단계에서?”를 더한다.
- 수렴: 내가 겪거나 확인할 수 있고, 작은 도구로 먼저 시도할 수 있는 문제 후보를 고른다.
- 아이디어 댓글 틀: “[아이디어] ___가 ___할 때 ___ 때문에 불편하다. ___할 수 있으면 좋겠다.”
- 보완 댓글 틀: “[보완: 아이디어 첫 구절] 이런 상황도 있나요? / 이 과정 중 ___부터 나눠 보면 어떨까요?”

**형태 설계:** 상단은 ‘발산→연결→수렴’의 길이가 다른 세 구간으로 표현하고 하단의 넓은 댓글 예시를 주인공으로 둔다. 컴포넌트 제안: Process + CommentPreview + Build. at=1 평가를 미루고 아이디어 내기, at=2 서로의 생각 확장, at=3 하나 좁히기, at=4 댓글 양식. ‘수행평가 준비물’ 예시를 한 번 채워 보여 준다. 아직 외부 활동 화면을 열지 않는다.

**발표자 노트:** “처음에는 여러 개를 냅니다. 진로가 달라도, 비슷한 아이디어가 있어도 괜찮습니다. 친구의 생각을 평가하기보다 상황을 더 구체적으로 만드는 댓글을 달아 주세요. 마지막에는 하나를 골라 작게 나눕니다.” 권장량은 아이디어 2개 이상·보완 댓글 1개이나 개수보다 구체적인 상황을 우선한다. 댓글 기능에 대댓글이 없어도 참조 구절로 연결하도록 안내한다.

3. 노트 내용 개념 창 × 학생이 해당 제목의 노트 열기 × 공통 안내와 댓글 작성 영역 확인.
4. 댓글 입력 개념 창 × 학생이 아이디어 한 개 입력 후 게시 × 게시한 문장이 댓글 목록에 나타나는지 확인.

**공용 노트 본문 초안:**

>
> 1. [아이디어] 누가 / 언제 / 무엇 때문에 불편한가 / 어떤 도움이 필요한가. 아이디어 하나당 댓글 하나.
> 2. [보완: 아이디어 첫 구절] 친구의 상황을 구체화하는 질문이나 추가 아이디어.
> 3. [정리] 큰 주제 → 나눈 작은 문제들 → 먼저 확인할 핵심 문제 후보 / 첫 도구 아이디어 / 도움이 되는지 확인할 방법 / 다음에 할 시도.
>
> 처음에는 평가를 미루고 여러 생각을 냅니다. 마지막에 문제 하나를 고릅니다. 오늘의 선택은 이후 시도하면서 바꿀 수 있습니다.

**발표자 노트:** 실제 접속과 노트 열기는 설명을 마친 Slide 11에서 시작한다. 비로그인 브라우저에서는 SPACEKIJUN의 ‘구글로 로그인’ 화면이 확인되었다. 교사는 수업 전에 접근 가능 여부와 노트 생성·댓글 작성 권한을 확인한다. 로그인 이후 계정 절차는 실제 화면에 맞춰 안내한다. 장애가 발생하면 같은 양식으로 임시 메모하고 접속 복구 후 공용 노트에 옮기도록 하여 브레인스토밍 시간을 지킨다.

## Slide 11 — 브레인스토밍: 내 문제를 쓰고, 서로 확장하기
- form: activity
- activity: 외부 collab 공용 노트의 댓글 · 별도 활동지 제작 없음
- 시간: 18분

**핵심 메시지:** 아이디어를 나누고 작은 문제로 나눈 기록을 남겨 핵심 문제 후보 하나를 발견한다.

**핵심 내용:**
- ① 혼자 떠올리기 → ② 아이디어 댓글 → ③ 친구 생각 보완 → ④ 내 문제 좁히기.
- 계속 보이는 질문: “누가, 언제, 어떤 일을 하다가 막히는가?”
- 정리 댓글: “[정리] 큰 주제 → 작은 문제들 → 핵심 문제 후보 / 첫 도구 / 확인 방법 / 다음 시도”.
- [브레인스토밍 참여하기](https://spacekijun.lovable.app/collab/28fa5003-3201-4d6f-aea9-eda51c1f6489).

**형태 설계:** 왼쪽 상단에 질문을 크게, 그 아래 넓은 정리 댓글 양식을 둔다. 오른쪽에는 네 단계의 짧은 안내와 클릭 가능한 참여 링크. QR을 함께 넣는 경우에도 클릭 링크를 유지한다. 한 화면을 활동 내내 유지할 수 있게 설계하고 중간 설명 슬라이드를 끼우지 않는다. 시간은 교사 노트에만 기록한다.

**발표자 노트 — 활동 운영:**
- 0–3분: 링크를 열어 공용 노트를 확인한 뒤 각자 경험을 떠올리고 메모한다. 교사는 안내한 제목으로 노트를 생성한다(이미 수업 전에 준비했다면 해당 노트를 안내). 학생이 접속하는 동안 혼자 생각할 수 있게 한다.
- 3–9분: 아이디어 하나당 댓글 하나로 여러 생각을 올린다. 진로 질문에 막힌 학생에게는 “최근 같은 일을 두 번 했던 순간”이나 “다시 찾아본 정보”를 떠올리게 한다.
- 9–13분: 친구의 댓글을 읽고 상황을 더 구체화하는 보완 댓글을 남긴다. 대댓글 가능 여부와 관계없이 대상 아이디어의 첫 구절을 적는다.
- 13–18분: 관심 있는 아이디어 하나를 골라 작은 문제 2~3개로 나눈 뒤 핵심 문제 후보 하나를 정리 댓글로 남긴다. 이미 쓴 댓글을 편집해야 한다는 전제 없이 새 댓글로 기록한다.

**교사 순회 발문:** “누가 실제로 겪나요?”, “어느 순간에 가장 불편한가요?”, “그 일을 하는 과정을 나누면 무엇이 있나요?”, “하나만 편해져도 도움이 되는 부분은?”, “만든 뒤 무엇을 보면 도움이 됐다고 할 수 있나요?” 원인을 학생 대신 확정하거나 구현 기능을 일괄 지정하지 않는다.

**정리 댓글 예시:**
> [정리] 학교생활 → 공지 찾기·마감 확인·준비물 확인 → 수행평가를 준비하는 학생이 흩어진 준비물 정보를 한 번에 확인하기 어렵다. / 첫 도구: 과목·날짜·준비물을 입력하는 목록 / 확인: 입력한 사례의 준비물을 원래 공지 없이 정확히 찾는가 / 다음 시도: 최근 공지 몇 개를 살펴보고 실제로 어떤 정보가 흩어져 있는지 확인하기.

**활동 완료 기준:** 정리 댓글에서 구체적인 사람·상황·불편, 작은 문제로 나눈 과정, 핵심 문제 후보, 다음 시도를 확인할 수 있다. 첫 도구와 확인 방법은 초안이면 충분하고 프로젝트 최종 확정이나 코드 제출은 요구하지 않는다.

## Slide 12 — 처음 생각보다 무엇이 구체적이 되었나?
- form: build
- 시간: 3분

**핵심 메시지:** 오늘의 성과는 큰 주제 속에서 직접 확인하고 해결할 작은 문제를 발견한 것이다.

**핵심 내용:**
- 돌아보기: “처음 주제 → 나눈 작은 문제들 → 지금의 핵심 문제 후보”.
- 확인 질문: “누구의 어떤 불편이 줄어드는가?”, “다음에 무엇을 확인하거나 시도할 것인가?”
- 친구의 질문으로 생각이 바뀌었다면 그 변화도 발견의 일부다.

**형태 설계:** 좌측 좁은 영역에 ‘처음 주제’, 오른쪽 넓은 영역에 ‘구체화된 문제’를 두고 중간에 학생이 나눈 작은 문제들을 연결한다. 컴포넌트 제안: 비대칭 BeforeAfter + Build. at=1 시작 문장, at=2 분해 과정, at=3 핵심 문제 후보와 다음 시도. 실제 학생 댓글은 수업 중 교사가 collab에서 선택해 보여 준다. 덱 기본 화면은 Slide 4 예제와 빈 설명 틀로 두며 존재하지 않는 학생 답변을 만들지 않는다.

**발표자 노트:** 자원자 1~2명이 30초씩 발견을 설명한다. 교사는 기능 개수나 구현 난도 대신 구체화된 상황과 다음 시도를 피드백한다. 형성평가는 새 제출 없이 Slide 11의 정리 댓글로 확인한다. ‘학습 앱 만들기’만 남은 학생에게는 ‘학습 중 어느 순간, 어떤 어려움인가’를 되물어 다음 시도까지 연결한다.

## Slide 13 — 다음 시간, 이 문제를 첫 프로젝트로
- form: static
- 시간: 2분

**핵심 메시지:** 다음 시간에는 프로그램과 AI 에이전트를 준비하고 오늘의 문제 후보를 프로젝트 기획 문서로 구체화한다.

**핵심 내용:**
- 오늘의 한 줄: “문제를 찾고 → 작게 나누고 → 핵심 문제를 발견한다.”
- 다음 시간: 바이브코딩 프로그램 설치 → 인공지능 에이전트 사용 방법 → AI와 프로젝트 기획 문서 작성.
- 연결할 자료: 오늘의 정리 댓글·다음 시도·떠오른 질문.
- 수업의 방식: “직접 해 보고, 질문하고, 다시 시도합니다. 질문은 언제든 환영합니다.”

**형태 설계:** 화면 왼쪽 큰 영역에 오늘의 핵심 문제 후보를 담는 한 문장 틀, 오른쪽 좁은 영역에 다음 시간의 세 단계를 세로로 배치한다. 컴포넌트 제안: 비대칭 Split + Process. 하단에는 시도와 질문 안내를 한 줄로 둔다. 빌드 없음. 특정 프로그램 로고나 사전 설치 과제를 추가하지 않는다.

**발표자 노트:** “다음 시간에는 설치부터 함께 시작합니다. AI 에이전트를 사용하는 방법을 배우고, 오늘 댓글로 정리한 문제를 AI와 프로젝트 기획 문서로 만들 겁니다. 그 사이에 실제 불편한 상황을 한 번 더 살펴보면 도움이 됩니다. 떠오르는 질문은 언제든 가져오세요.” 사전 설치를 필수 준비로 요구하지 않는다.

## 렌더러 전달 사항

- 본문의 공통 핵심 메시지·형태 설계·발표자 노트를 기준으로 저작한다. 전체 문서를 슬라이드 본문으로 복사하지 않는다.
- 운영 가정은 공용 노트 1개이며 학생별 노트 생성이나 다른 제출 서비스로 바꾸지 않는다.
- Slide 10은 현재 개념 목업 설계이다. 실제 UI를 재현하려면 먼저 접근과 동선을 확인해야 하며, 확인되지 않으면 명시된 개념 목업을 유지한다.
- scene 저작 시 `.claude/rules/scene-grammar.md`를 읽고 정지·중간·최종 상태를 검수한다. 불필요한 인물·로봇·장식 자산을 추가하지 않는다.
- 2026-09-08 사용자 승인 후 `vibe-coding-orientation`으로 저작·허브 등록. 배포와 collab 게시 여부는 별개이며 실제 외부 게시는 수행하지 않는다.
- 좁은 화면에서는 기존 덱 엔진의 가로 캔버스 축소를 따른다. 슬라이드 내부 크기는 컨테이너 단위(cqw/cqh)로 계산해 축소 시 겹침을 방지한다.
