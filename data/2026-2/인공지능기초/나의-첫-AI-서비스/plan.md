## Slide 6 — API: 프로그램의 접수 창구
- form: build
- 변경 이력(2026-08-26): 처음에는 whiteboard(종이 판서)로 저작했으나, 다크 작업실
  테마 한가운데 밝은 종이 한 장이 이질적이라는 사용자 판단으로 **덱의 시각 언어를
  그대로 쓰는 build 다이어그램**으로 전환. 내용·비유(가게의 두 통로)는 유지

**핵심 메시지:** API는 프로그램이 프로그램에게 기능을 요청하는, 형식이 약속된 창구다.

**핵심 내용:**
- 서비스에는 통로가 두 개다 — **사람**이 쓰는 화면(UI), 그리고 **프로그램**이 쓰는 접수 창구(**API**)
- 우리 서비스는 두 역할을 동시에 한다: 사용자에게는 화면을 열고, 자신은 **Solar의 API 창구에 요청을 내는 프로그램(클라이언트)**이 된다
- 정해진 형식의 요청을 보내면 정해진 형식의 응답이 돌아온다 — 가장 기본적인 API 호출은 요청 하나에 응답 하나
- 세상 서비스는 남의 기능을 API로 빌려 조립된다: 지도 API(길찾기), 결제 API(온라인 결제), 날씨 API(예보)
- **LLM API = "말을 다루는 능력"을 빌려주는 창구** — S5의 우체통이 바로 이것
- 발전소를 짓지 않고 콘센트에 꽂는다 — 모델을 만드는 큰 비용(지난 시간 뉴스의 5,300억 원은 여러 팀을 지원하는 국가 프로젝트 규모였다)은 만든 쪽이 감당하고, 우리는 쓴 만큼 값을 치르며 창구를 쓴다

**형태 설계:** 좌우 비대칭 두 카드 + 중앙 왕복 화살표. 우측 dominant에 Solar
카드 — 안에 두 통로 행: [화면(UI) — 사람 손님용]과 [API — 프로그램용 접수 창구,
민트 형광 테두리 + 「정해진 형식」 앰버 배지]. 좌측에 우리 프로그램(클라이언트)
카드 — "우리도 사람 손님용 화면(UI)을 연다" 한 줄. 두 카드 사이를 요청(→)·응답(←)
왕복 화살표가 가로축 중앙을 통과해 잇고 가운데 「API 호출」 라벨. Build at=1:
Solar 카드와 두 통로(무엇이 다른가). at=2: 우리 프로그램 카드 + 왕복 화살표 +
정의 한 줄. at=3: 하단 띠 — 지도 API(길찾기)·결제 API(온라인 결제)·날씨 API(예보)
칩 + "LLM API = 말을 다루는 능력을 빌려주는 창구" 문장.

**발표자 노트:** "여러분이 만들 서비스에는 통로가 두 개 있습니다. 사용자가 들어오는 화면이 하나. 그리고 여러분의 프로그램 자신은 Solar 가게의 접수 창구에 요청서를 내러 가는 손님이 됩니다. 이 프로그램 전용 창구가 API예요. 다른 앱들도 이렇게 카카오모빌리티의 길찾기 API를 빌려 경로 기능을 넣고, 온라인 상점은 토스페이먼츠 같은 결제 API를 연결해 결제 기능을 넣습니다. 오늘 여러분도 창구 하나를 씁니다."

## Slide 7 — LLM API 요청: 먼저 읽는 네 곳
- form: build (+ 라이브 문항 연결)
- 문항 통합(2026-08-26 심야): 구 S7 개념 체크 **전용 슬라이드를 없애고** 문항만 이 슬라이드에 연결했다 — 요청 구조를 방금 본 화면 그대로 두고 물어야 확인이 되고, 슬라이드 한 장을 아낀다

**핵심 메시지:** API 요청의 네 곳만 읽으면 LLM API가 보인다 — 그리고 요금은 토큰으로 센다.

**핵심 내용:**
- API 요청(요청 본문)의 뼈대는 **model + messages** 두 가지 — messages 안에 system 줄과 user 줄이 들어가고, temperature는 선택 항목이다. 오늘 먼저 읽을 네 요소:
  - `model: solar-pro3` — 요청을 처리할 모델을 지정한다
  - `system: …` (messages 안) — **개발자의 지시(시스템 프롬프트)가 앉는 자리**. 화면에는 드러나지 않지만, 코드에 넣으면 소스 보기로 읽힌다 — 비밀 금고가 아니다 (우리 데모는 일부러 [내부 보기]로 공개한다)
  - `user: …` (messages 안) — **조립된 사용자 메시지가 앉는 자리**
  - `temperature: 0.7` — 지난 시간 그 **온도 손잡이**가 여기 한 줄로 있다
- 응답의 실물: 돌아온 API 응답에서 답 문장(`content`)만 꺼내 화면에 붙인다 — 서비스가 하는 마지막 일
- **요금은 입력 토큰×단가 + 출력 토큰×단가로 계산된다 (단가는 서로 다르다)** — 지난 시간 "한국어는 조각이 많아 손해"의 그 조각(토큰). 불필요하게 긴 프롬프트를 줄이면 입력 토큰 비용이 준다
- Solar Pro 3 = 지난 시간 국가대표 AI 뉴스의 업스테이지, 그리고 여러분 글을 채점하던 그 모델 — **오늘은 여러분이 요청을 쓴다** · 자체 실측 배지: 응답 약 0.5초(1회 측정)

**형태 설계:** 중앙 dominant에 **주문표 스큐어모피즘 카드**(비유는 시각 연출로만
— 카드 제목 라벨은 「API 요청」) — model 줄 아래 messages 괄호 안에 system·user
두 줄이 들여쓰기로 앉아 실제 구조를 그대로 보인다. Build at=1: 요청 카드 등장,
system·user 줄에 형광 라벨(개발자의 자리 / 사용자의 자리) + system 라벨 옆에
"비밀 아님 — 소스 보기로 보인다" 각주. at=2: 우측에서 응답 봉투(라벨: API 응답)가
도착, content 한 줄만 형광펜으로 뽑혀 나와 미니 화면 목업에 붙는다(요청→응답
왕복의 완결). at=3: 카드 하단에 영수증 합계처럼 **토큰 계수 띠**(지난 시간 토큰 칩
모양 재등장 — 입력·출력 토큰 수 × 단가) + 회수 배지 2개(온도 손잡이 · 채점자→
부리는 쪽) + 실측 배지.

**연결된 라이브 문항 (체크포인트 ② — quiz.json `api-where`, slide 6):**
- kind: choice(단수) · **정답 있음** — 이 슬라이드를 띄운 채 라이브 미니바로 연다
- prompt: "내 서비스에서, 사용자가 입력 칸에 쓴 값은 API 요청의 어디에 들어갈까요?"
- 선지: ["model", "system 역할 메시지", "user 역할 메시지", "temperature"] · 정답: ③ user 역할 메시지
- 오답 해설(misconceptions): model = 모델 지정 자리 / system = 개발자의 시스템 프롬프트 자리(C1·C2 구분의 씨앗) / temperature = 변화 정도

**발표자 노트:** "API 요청은 음식점 주문서 같은 겁니다 — 적을 항목이 정해져 있어요. 이 네 요소만 읽을 줄 알면 LLM API는 보인 겁니다. 하나만 더 — 이거 공짜가 아니에요. 토큰 수만큼 값을 냅니다. 지난 시간에 한국어가 조각이 많아서 손해라고 했죠? 오늘부터 그게 진짜 돈 얘기가 됩니다. 그리고 이 모델, 여러분 글 채점하던 걔예요. 오늘은 입장이 바뀝니다. (여기서 라이브 문항 하나 — 사용자가 쓴 값은 이 요청의 어디에 들어갈까요? 공개 후) system을 고른 사람이 꽤 있죠. system은 개발자의 시스템 프롬프트 자리입니다. 사용자 입력은 프롬프트 템플릿에 끼워져 user 역할 메시지로 들어가요. 이 구분이 이따 활동지 C1과 C2의 구분이 됩니다."

# 2부 — 설계: 만들기 전에 정한다 (S9~S11)

## Slide 9 — 개발자의 세 질문
- form: build

**핵심 메시지:** 만들기 전에 세 가지를 정한다 — 누구의 어떤 문제인가, 무엇을 받는가, 무엇을 주는가.

**핵심 내용:**
- ① **왜**: 누가, 언제, 어떤 문제를 겪는가 — 문제 없는 서비스는 장난감이다
- ② **입력**: 그 문제를 풀려면 사용자에게 무엇을 받아야 하는가
- ③ **출력**: 무엇을, 어떤 모양으로 돌려주는가
- 나쁜 예 → 좋은 예 변환: "공부 도우미" (누가? 뭘 받아? 뭘 줘? — 셋 다 비어 있다) → "시험 전날 밤 계획이 안 서는 나에게, 과목·범위·남은 시간을 받아, 남은 시간에 맞춘 구간표를 주는 서비스" — 이게 아까 그 **벼락치기 설계사**의 설계서다
- 발문: "챗GPT가 이미 있는데 왜 따로 만들까?" → **매번 길게 설명하지 않아도 되도록 미리 좁혀 둔 것**이 서비스다

**형태 설계:** 세 질문을 좌측에 세로 스택(번호가 커지며 들여쓰기), 우측에
변환 시연 영역. Build at=1: 세 질문. at=2: 나쁜 예 카드 + 세 질문 자리가
전부 빈칸(점선)임을 표시. at=3: 좋은 예로 카드가 교체되며 세 빈칸이 채워지고,
하단에 발문 배너. "벼락치기 설계사" 이름표를 붙여 데모와 연결.

**발표자 노트:** "'공부 도우미 만들래요'는 아직 아이디어가 아닙니다. 누가, 뭘 넣어서, 뭘 받는지 정해져야 만들 수 있어요. 아까 쓴 벼락치기 설계사도 이 세 칸을 채우는 데서 시작했습니다."

## Slide 10 — 입력은 아끼고, 출력은 못 박는다
- form: build

**핵심 메시지:** 입력 칸은 1~3개로 아끼고, 출력 조건은 명확히 정한다 — 내가 정하지 않으면 기계가 확률로 정한다.

**핵심 내용:**
- **입력 규칙**: 칸은 1~3개 — 사용자는 귀찮은 것을 싫어한다. 칸마다 존재 이유를 말할 수 있어야 한다(답을 바꾸지 않는 칸은 지운다)
- **출력 규칙**: 결과의 내용·형식·길이는 반드시, 말투·금지는 필요할 때 명확히 정한다 — 지난 시간에 배웠다: **내가 정하지 않은 것은 기계가 확률로 정해 버린다**
- 금지의 실전 예: "별표·머리기호·굵은 글씨 없이" — 안 쓰면 결과 화면에 `**` 같은 기호가 그대로 찍힐 수 있다
- **temperature(온도) 선택** (셋 중 하나 — **보장이 아니라 경향이다**): 0.3 변화 적게 / 0.7 중간 / 1.1 변화 많게
- 데모 회수: 벼락치기 설계사(0.3)는 두 번 넣어도 비슷한 경향, 3줄 위로(1.1)는 크게 달라지는 경향 — 체험 미션 ②에서 분단별로 관찰한 그 차이

**형태 설계:** 좌우 비대칭 — 좌측(작게) 입력 규칙, 우측(dominant) 출력 규칙.
출력 카드 안에 다섯 항목(내용·형식·길이 = 필수 / 말투·금지 = 선택)을
체크리스트로 — 필수와 선택을 시각적으로 구분한다. Build at=1: 입력 규칙 +
"칸의 존재 이유" 한 줄. at=2: 출력 규칙 + 지난 시간 회수 배너(형광).
at=3: 하단에 temperature(온도) 3택 슬롯 + 데모 3종의 온도 값이 각 슬롯에
이름표로 붙는다(0.3 벼락치기 설계사 · 0.7 면접 리허설 코치 · 1.1 3줄 위로) +
"경향이지 보장이 아니다" 각주 한 줄.

**발표자 노트:** "아까 같은 입력을 두 번 넣었을 때 분단마다 결과가 달랐죠? 벼락치기 설계사는 비슷하게, 3줄 위로는 꽤 다르게 나왔을 겁니다. 제가 temperature를 다르게 설계했기 때문이에요. 주의 — 온도는 성격 버튼이 아니라 경향입니다. 낮다고 매번 똑같이 나온다는 보장은 없어요. 여러분 서비스의 온도도 여러분이 가설을 세워 고릅니다. 계획표라면 낮게, 위로라면 높게."

## Slide 11 — 시스템 프롬프트: 서비스의 동작 규칙
- form: build

**핵심 메시지:** 시스템 프롬프트 한 장이 서비스의 동작 규칙을 정한다 — 역할, 규칙, 출력 형식, 그리고 예외 처리.

**핵심 내용:**
- '3줄 위로'의 **실제 시스템 프롬프트 전문**을 화면에 (데모에 들어 있는 그대로 — [내부 보기]에서 이미 본 학생도 있다)
- 네 부분 해부: **[역할]** 너는 …이다 / **[규칙]** 항상·절대 / **[출력 형식]** 정확히 3줄, 각 줄의 임무 / **[예외 처리]** 고민이나 하루 이야기가 아닌, 장난이거나 위로와 상관없는 입력이 오면 부드럽게 안내
- 예외 처리 한 줄이 있는 이유: 서비스와 상관없는 말이나 장난은 반드시 들어온다 — **개발자는 사용자를 다 믿지 않는다**
- ⚠ 용어 풀이(2026-08-26 심야 사용자 지적): 화면 문구에서 "무관·장난 입력"처럼 압축된 한자어를 쓰지 않고 **"장난이거나 위로와 상관없는 입력"**으로 풀어 쓴다. 데모 '3줄 위로'의 시스템 프롬프트 원문도 같은 문장으로 맞춰 둔다(화면과 실물이 한 글자도 달라선 안 된다)
- 이 한 장이 S7 요청의 `system` 줄에 앉는다. 서비스의 몸에는 입력 틀·온도·화면도 있지만, 동작 규칙의 중심이 이 한 장이다 — 그래서 오늘은 이 종이를 서비스의 심장이라 부르자
- 여러분은 활동지 C 구역에서 바로 이 한 장(C1)과, 사용자 입력이 앉는 문장 틀(C2 — 프롬프트 템플릿)을 쓰게 된다

**형태 설계:** 중앙에 프롬프트 전문을 원고지/타자기 카드로 크게(코드가 아니라
글로 보이게). Build at=1: 전문 등장. at=2: 네 부분에 색이 다른 형광 라벨이
왼쪽 여백에 붙는다(라벨은 본문 bbox 바깥 — [역할]·[규칙]·[출력 형식]·[예외 처리]).
at=3: [예외 처리] 줄만 확대 강조 + 하단 한 줄 "여러분 프롬프트에도 예외 처리
한 줄을". 우상단에 심장 박동 아이콘 미니 배지(비유는 배지 하나로 절제 —
S15 대화 왕복 장면과 겹치지 않게).

**발표자 노트:** "이게 3줄 위로의 진짜 동작 규칙입니다. 화면도 버튼도 아니고 이 글 한 장이 서비스가 어떻게 움직일지를 정해요. 그래서 심장이라 부를 만하죠. 마지막 예외 처리 줄 보세요 — 여러분 서비스에도 엉뚱한 입력이 반드시 들어옵니다. 그때 어떻게 답할지까지가 설계입니다."

상한 걸린 임시 키 · 진짜 서비스: 서버 금고 속 키, 지난 활동지 회수 이름표).

## Slide 13 — ChatGPT에게 맡기는 절차
- form: walkthrough
- 재작성(2026-09-04): 사용자 지적 — **로그인한 계정의 ChatGPT는 코드 블록 위에 재생(▶) 버튼을 붙여 준다.** 누르면 코드로만 보이던 것이 그 자리에서 실제 화면이 된다. 파일을 내려받아 더블클릭할 이유가 사라졌으므로 **재생 4단계**로 교체하고, 다운로드·더블클릭은 "▶가 안 보일 때"의 대안으로 강등했다. 이 변경은 S15(고장 진단)를 "메모장 편집"에서 "같은 대화로 요청"으로 함께 바꾼다 — 학생 손에 파일이 없기 때문
- 재작성(2026-08-26 심야): 코드 블록 위 [복사]·[다운로드] 두 버튼 중 **다운로드**를 눌러 `.html`을 받고 더블클릭하는 4단계로 교체(메모장 저장은 대안으로 강등). 2026-09-04 개정으로 이 4단계는 다시 재생 4단계에 자리를 내줬다
- scene: metaphor: 코드가 화면으로 건너가는 순간 — 왼쪽 ChatGPT 창의 코드 블록이 오른쪽 미리보기 창에서 돌아가는 서비스가 된다 | emotion: 몰입·설렘 | intent: 처음 해 보는 절차의 불안을 창 목업 시연으로 제거하고, "코드=화면"이 한 번의 클릭임을 눈으로 보인다

**핵심 메시지:** 네 걸음이면 코드 생성 프롬프트가 내 서비스가 된다 — 파일을 받을 필요도 없다.

**절차 대본 (창 × 행동 × 확인):**
1. 브라우저 창 — `chatgpt.com`에 **로그인해서** 접속 (재생 버튼은 로그인 계정에만 붙는다) — 확인: 입력창이 보이고 계정이 로그인 상태다
2. ChatGPT 창 — 활동지 D의 [전체 복사]를 누르고 입력창에 붙여넣기 → 전송 — 확인: 코드 블록이 생성되기 시작
3. ChatGPT 창 — 코드 블록 위의 **[▶ 재생]** 클릭 — 확인: 버튼이 "재생됨 ✓"으로 바뀌고 오른쪽에 미리보기가 열린다
4. 미리보기 — 입력 칸에 값을 넣고 **[실행]** — 확인: 내 서비스가 답을 뱉는다 (여기서 나온 답이 S14 테스트·S15 개선의 재료가 된다)

**자주 막히는 문제 2가지 (창 안 하단에 카드 2장):**
- 코드가 중간에 끊기거나 여러 조각으로 나뉘었다 → **"완전한 HTML 전체를 처음부터 끝까지 하나의 코드 블록으로 다시 출력해 줘"** (조각을 이어 붙이지 않는다 — 마지막 줄이 `</html>`인지 확인)
- **[▶ 재생]이 안 보인다** → 먼저 로그인 상태 확인, 그래도 없으면 [⬇]로 `.html`을 받아 더블클릭 (구 절차가 그대로 대안으로 살아 있다)

**제출 경로 안내(창 ② 하단 한 줄):** 제출은 [복사]로 코드를 가져가거나 [⬇]로 파일을 받아 활동지 F에 낸다 — 재생만으로는 파일이 생기지 않으므로 이 줄이 없으면 F에서 막힌다.

  - 이 칸들은 `label` 바깥이라 `body`의 16px를 물려받아 다른 칸(0.92rem)보다 글씨가 컸다. 폭이 230px 남짓이라 열두어 글자에서 줄이 바뀌어 "몇 글자만 쳐도 칸이 커진다"고 느껴졌다 — 폰트를 다른 칸과 같게 맞춘다
- **하단 액션 바**(2026-08-27 신설 — 과목 내 다른 활동지와 같은 구성): 화면 아래에 고정되어 [임시저장 상태 · 이전 제출 불러오기 · 제출 현황 · 초기화 · 제출하기]를 항상 띄운다. 불러오기는 상단 '나의 정보'에 있던 것을 옮겼다 — 학생이 손을 대는 단추를 한자리에 모으면 어디를 눌러야 할지 찾지 않아도 되고, 결과 메시지도 단추 바로 옆(상태 줄)에 뜬다. 제출 버튼은 여기 하나뿐이고 F 구역에는 안내 문구만 둔다(같은 동작을 하는 버튼이 두 곳에 있으면 어느 쪽을 눌러야 하는지 학생이 묻는다). 임시저장은 조용히 저장하지 않고 「입력 중… → 임시저장됨 · 시각」으로 상태를 밝힌다. **제출 결과·경고 메시지는 잠금 플래그로 보호한다** — 마지막 칸을 채우고 곧바로 제출을 누르면 blur가 change를 일으켜 임시저장이 한 번 더 돌고, 그 결과가 "비어 있는 칸" 안내를 0.5초 만에 덮어 버린다(실측으로 잡은 결함)
- **F 제출**: 서비스 소개 한 줄 + 최종 HTML 코드 — **파일 업로드가 기본**(HTML 파일을 올리거나 코드 칸에 끌어다 놓으면 FileReader로 자동 인식, 2026-08-26 사용자 요청), 붙여넣기는 대안. 글자 수 표시(**45,000자부터 경고, 50,000자 이상은 제출 차단**) · 코드의 `up_` 키 패턴을 자동으로 `[수업용키]`로 치환해 저장 + **개발 후기(필수)** — 세 가지를 한 칸에 이어서 쓴다: ① 프롬프트를 설계하면서 어떤 점을 특히 신경 썼고 왜 그랬는지(= 내 서비스의 강점이 될 부분) ② 만들면서 뜻대로 되지 않은 것이 있었다면 무엇이고 해결했다면 어떻게 했는지 ③ 그래서 결과적으로 어떤 장점을 가진 서비스가 되었는지. **이 수업의 결론에 해당하는 문항**이다(2026-08-27 사용자 지정) — E의 테스트·개선 기록이 낱낱의 사실이라면 이 칸은 그것을 하나의 이야기로 묶는 자리이고, 평가에서 '설계 의도 → 문제 해결 → 결과'를 한눈에 읽을 수 있게 한다. 예시 답을 placeholder에 세 문장으로 넣어 분량과 짜임을 보인다 + 한 줄 소감 → 제출. **회차 구분 없음**(2026-08-26 심야 사용자 지정): 수업 안에 일단 제출하고 자정까지 몇 번이든 다시 내며, 마지막 제출본이 최종본이다. "입력이 답이 되어 돌아오기까지의 길을 한 문장으로" 필수 문항도 같은 날 삭제했다 — 같은 이해를 E의 고친 위치 선택과 D의 조립 미리보기가 이미 확인한다

## 3. 코드 생성 프롬프트 고정 기술 명세 (활동지 D에 하드코딩되는 블록의 요구 항목)

저작 시 이 항목들을 자연어 명세문으로 작성하고, **실제 ChatGPT에 1회 이상 넣어
생성물이 동작하는지 검증**한 뒤 확정한다(렌더러 체크리스트):

1. 결과물은 **완전한 단일 HTML 파일 하나** — 외부 라이브러리·CDN 없이 더블클릭 실행, `<meta charset="UTF-8">` 포함
2. **출력 규율**: 되묻지 말고 바로 완성 코드를 출력 · 코드 블록 하나만 · 마지막 줄 `</html>`
3. 파일 상단 ★ 주석 배너 + `SYSTEM_PROMPT`·`PROMPT_TEMPLATE`·`API_KEY`·`TEMPERATURE` 상수 — 프롬프트 두 상수는 **백틱 템플릿 문자열**, 학생 문장은 의미를 바꾸지 않되 문자열에 필요한 이스케이프만 허용. 배너에 "이 파일의 주인이 이 안의 **문장만** 고칩니다" 명시 (S16 전제). 활동지가 입력 단계에서 백틱·`${` 자체를 차단한다(적대 검증 반영)
4. API 호출: `POST https://api.upstage.ai/v1/chat/completions` · Bearer 키 · body `{model:"solar-pro3", messages:[system, user], temperature:(선택값), max_tokens:2000, reasoning_effort:"low", stream:false}` — reasoning_effort는 **API 필수가 아니라 수업 고정값**(응답 지연 방지)임을 명세문에 그대로 적는다
5. 자리표시자 `{칸이름}`의 **모든 등장**을 치환. 조립 후 `{…}`가 남으면 호출하지 않고 빠진 칸을 안내
6. 모든 입력값은 공백 제거 후 검사 — 하나라도 비면 호출하지 않고 그 칸을 채우라고 안내
7. UI: 서비스 이름 + 한 줄 소개 + 입력 폼 + 실행 버튼 + 로딩 표시 + 결과 영역(`white-space: pre-wrap`) + 오류 안내 영역
8. 로딩 중 버튼 잠금 · 오류 4분기 — 429: "붐빕니다, N초 뒤"(20~40초 무작위 잠금·남은 초 표시) / 401·403: 키 확인 / 네트워크: 인터넷 확인 / 기타: 오류 코드와 함께 교사에게
9. 응답은 `choices[0].message.content`만 꺼내 **반드시 textContent로** 표시 — innerHTML 금지(스크립트 삽입 방지, 적대 검증 반영). 마크다운 해석 불필요
