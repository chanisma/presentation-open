# 접근성·이해도 검토

판정은 각 슬라이드의 마지막 프레임을 기준으로 했다. 캡처 자체가 축소되어 있다는 점을 감안해도, 교실 뒷자리에서는 본문·주석 상당수가 읽히기 어렵다.

## 1. 오해 가능성

- **(s02-0-c0.jpg)** → 세 서비스가 실제로 작동하는 완성품인지, 오늘 만들 후보인지 불분명하다. 오른쪽의 `열기`도 실제 링크처럼 보여 수업 중 무엇을 눌러야 하는지 혼동할 수 있다. → 제목 아래에 `오늘 만들 수 있는 예시 3개 — 이 중 하나를 선택`을 크게 넣고, 버튼을 `예시 보기` 또는 `활동 후보`로 명확히 바꾼다.

- **(s03-1-c1.jpg)** → “챗봇이 없고 입력 칸이 정해져 있다”와 “질문을 대신 만들어 뒀다”가 연결되지 않는다. 학생은 단순한 입력 폼과 AI 서비스의 차이를 UI 차이로만 이해할 수 있다. → `사용자가 자유롭게 질문 → ChatGPT`와 `개발자가 질문 형식을 미리 설계 → 미니 서비스`를 두 개의 입력 예시로 직접 비교한다.

- **(s04-3-c0.jpg)** → `겉옷–대본–우체통` 비유에서 무엇이 데이터이고 무엇이 코드인지 불명확하다. 특히 대본이 우체통으로 들어가는지, 화면이 대본을 읽는지, 우체통이 답을 만들어 내는지 알 수 없다. → 세 요소 사이에 번호 화살표를 추가한다: `① 사용자가 화면에 입력 → ② 코드가 프롬프트를 조립 → ③ API로 전송 → ④ 응답을 화면에 표시`. 비유 라벨 옆에 실제 용어도 병기한다.

- **(s05-6-c0.jpg)** → 요청 화살표는 API 쪽을 향하지만 응답 화살표는 프로그램이 아니라 화면 아래의 빈 공간을 향한다. 응답이 어디로 돌아오는지 잘못 이해할 수 있다. 아래의 지도·결제·날씨 가게도 Solar 가게의 일부인지 별개 API인지 모호하다. → 요청과 응답을 같은 두 단말 사이의 왕복선으로 그린다. `우리 프로그램 → Solar API: 요청`, `Solar API → 우리 프로그램: 응답`이라고 양 끝에 명시한다. 다른 API 예시는 별도 영역에 `다른 API의 예`라고 분리한다.

- **(s05-6-c0.jpg)** → Solar 내부의 `사람 손님용 화면(UI)` 때문에 API도 사람이 웹 화면으로 사용하는 창구라고 오해할 수 있다. → 사람용 UI와 프로그램용 API를 상하로 나누고, `오늘 사용하는 것은 아래의 프로그램용 API`를 굵은 테두리와 문장으로 표시한다.

- **(s06-3-c3.jpg)** → 제목이 “네 요소면 읽는다”라서 학생이 `model·messages·temperature·요금` 네 가지를 외워야 한다고 받아들일 수 있다. 그러나 요금은 요청 필드가 아니며, 오른쪽의 `choices[0].message.content`는 응답 읽기 방식이다. → `보낼 때 필요한 3가지`와 `받을 때 확인할 1곳`으로 분리한다. 요금은 요청 카드 밖의 `참고` 영역으로 이동한다. 학생이 직접 수정할 항목에는 `오늘 바꿀 곳` 표시를 붙인다.

- **(s06-3-c3.jpg)** → `system`과 `user`가 코드 문법처럼 제시되어 역할 차이가 약하다. 학생이 자신의 입력을 system에 넣거나 시스템 프롬프트를 사용자 입력칸에 넣을 수 있다. → `system = 개발자가 정한 고정 규칙`, `user = 실행할 때마다 들어오는 사용자 입력`을 두 칸으로 분리하고 실제 예문을 각각 한 줄씩 보여준다.

- **(s07-1-c1.jpg)** → “LLM을 밑바닥부터 만드는 회사는 소수다” 다음에 네이버 AI 브리핑 같은 사례가 나와, 소개된 서비스가 모두 외부 모델만 호출한다고 단정할 수 있다. → `수업에서 만드는 방식`과 `실제 회사의 다양한 방식`을 분리하고, 사례별 모델 관계를 확인할 수 없다면 회사명 대신 일반 예시를 사용한다.

- **(s08-3-c3.jpg)** → 왼쪽의 세 질문과 오른쪽의 “공부 도우미” 예시가 어떤 순서로 변환되는지 분명하지 않다. `누가·입력·출력`이 서비스 설계의 충분조건이라고 오해할 수도 있다. → 가운데에 `문제 → 대상 사용자 → 입력 → 출력 → 제약/예외` 흐름을 넣고, 공부 도우미 예시를 각 항목에 맞춰 한 줄씩 대응시킨다.

- **(s09-3-c3.jpg)** → `관심 지도`와 `문제 지도`가 실제 지도 제작 활동인지, 단순 질문 두 개인지 모호하다. “단어는 아직 서비스가 아니다”와 워드클라우드 활동의 관계도 약하다. → 결과물을 `관심 분야 1개 + 해결할 구체적 문제 문장 1개`로 명시하고, 변환 전후 예시를 넣는다: `공부 → 시험 전날 범위를 못 나누는 학생`.

- **(s10-3-c3.jpg)** → temperature의 `0.3=변화 적게`, `1.1=변화 많게`가 정확성이나 품질 조절기로 오해될 수 있다. “경험이지 보장이 아니다”는 너무 작아 사실상 전달되지 않는다. → `낮음: 답이 비교적 비슷함 / 높음: 표현과 선택이 더 다양함`으로 바꾸고, `정확도를 높이는 설정이 아님`을 큰 경고문으로 표시한다.

- **(s11-2-c2.jpg)** → 시스템 프롬프트의 `[역할]·[규칙]·[출력 형식]·[예외 처리]`가 반드시 이 순서와 형식이어야 API가 동작한다고 오해할 수 있다. → `필수 API 문법이 아니라, 프롬프트를 빠뜨리지 않기 위한 수업용 틀`이라고 제목 바로 아래에 명시한다.

- **(s12-1-c1.jpg)** → A·B·C와 아래의 `C1·C2`가 한꺼번에 등장해 구조가 헷갈린다. 특히 C가 “프롬프트”인데 C1은 시스템 프롬프트, C2는 사용자 메시지 틀이라 A·B의 내용과 중복된다. → A·B는 설계 활동지, C는 API에 넣을 문장이라는 두 단계로 분리한다. C1/C2는 다음 슬라이드로 넘기거나 `고정 규칙/매번 바뀌는 입력`으로 이름을 바꾼다.

- **(s13-3-c3.jpg)** → `코드 생성 프롬프트 = 내가 쓴 것 + 받은 것`에서 “받은 것”의 출처가 모호하다. 학생이 제공된 API 키까지 ChatGPT에 붙여 넣어야 한다고 이해할 위험이 있다. → `내가 작성: 서비스 설계·프롬프트`, `교사가 제공: 코드 골격·변수 자리`로 명시하고, `API 키는 붙여 넣지 않는다`를 절차 버튼 바로 옆에 크게 배치한다.

- **(s13-3-c3.jpg)** → `수업용 임시 키`와 `진짜 서비스—키는 서버 금고에`가 작고 분리되어 있어, HTML 파일 안에 키를 넣는 방식도 일반적인 배포 방식이라고 받아들일 수 있다. → 중앙에 `오늘 방식은 교실 실습 전용이며 공개·배포 금지`를 크게 표시한다. 실서비스 구조는 `브라우저 → 내 서버 → API`의 간단한 그림으로 보여준다.

- **(s14-6-c0.jpg)** → 절차 제목은 “다섯 걸음”인데 화면에는 ①~③만 크게 보인다. 하단 체크 항목이 나머지 단계인지도 불명확하다. → 1~5를 동일한 크기의 번호 카드로 제시하고, 현재 단계만 확대한다. `복사 → 메모장 저장 → 브라우저 실행 → 입력 → 결과 확인`처럼 행동 단위로 통일한다.

- **(s14-6-c0.jpg)** → ChatGPT가 생성한 코드를 그대로 저장·실행하면 된다는 인상을 준다. 오류나 보안 문제를 확인하는 단계가 없다. → 실행 전 단계에 `API 키 위치 확인`, `개인정보·수상한 외부 주소 확인`, `교사 확인` 체크를 추가한다.

- **(s15-3-c3.jpg)** → 제목은 “기본 두 가지 입력”인데 세 번째 `확장 ③ 경계·누락 입력`도 같은 줄에 있어 기본 테스트가 두 개인지 세 개인지 혼란스럽다. → 기본 테스트 2개와 확장 테스트를 공간적으로 분리하고, 실행 순서를 `필수 ① → 필수 ② → 시간이 남으면 ③`으로 번호화한다.

- **(s16-3-c0.jpg)** → 두 갈래가 “답이 이상하면 프롬프트, 화면이 이상하면 코드”라는 이분법으로 보인다. 실제로는 API 오류, 입력 데이터, 응답 파싱 등 양쪽에 걸친 원인이 있다. → `먼저 증상을 재현하고 오류 메시지를 기록`하는 공통 1단계를 둔다. 이후 `답의 의미·말투·형식`과 `버튼·배치·실행 오류`로 분기하되 `응답이 아예 없음 → API/키/네트워크 확인`을 세 번째 분기로 추가한다.

- **(s16-3-c0.jpg)** → 좌우 “리프트”의 의미가 그림으로 드러나지 않으며, 색 이외에는 구분 단서가 약하다. 학생은 왼쪽 판과 오른쪽 노트북이 왜 다른지도 이해하기 어렵다. → 비유를 빼거나 두 갈래에 큰 아이콘과 고정 라벨을 붙인다: `A. AI 답변 문제—프롬프트 편집`, `B. 화면·동작 문제—코드 수정`. 각 갈래에 실제 증상 한 개를 넣는다.

- **(s17-1-c1.jpg)** → 선택지 ④ `아직 고치지 못했다`가 ①~③과 같은 종류의 답처럼 보이지만, 하나는 상태이고 나머지는 수정 대상이다. → `수정한 위치`와 `수정 완료 여부`를 별도 질문으로 나눈다. 복수 선택 가능 여부도 표시한다.

- **(s18-1-c1.jpg)** → `HTML 업로드 → 자동 인식+키 가림 → 제출`에서 업로드 위치와 키가 어떻게 가려지는지 설명이 없다. 학생이 원본 HTML의 키까지 자동으로 안전해진다고 오해할 수 있다. → `제출 시스템이 별도 제출본에서 키를 제거하는지`를 정확히 명시하고, 그렇지 않다면 업로드 전에 키 삭제 절차를 넣는다. `원본 파일을 외부에 공유하지 말 것`도 표시한다.

- **(s19-2-c2.jpg)** → `프롬프트는 채팅이 아니라 부품이다`라는 표현이 프롬프트가 채팅에서는 쓰이지 않는다는 뜻처럼 들릴 수 있다. → `이 프로젝트에서 프롬프트는 대화문이면서 서비스 동작을 결정하는 부품이다`로 고친다.

## 2. 가독성

- **(s01-0-c0.jpg)** → 부제, 준비물, 오른쪽 직원 카드와 1~5 단계가 교실 뒤에서 거의 읽히지 않는다. 제목 외 정보는 전달되지 않는다. → 부제를 한 줄로 줄이고 24pt 이상으로 키운다. 직원 카드와 단계 목록은 삭제하거나 다음 장으로 분리한다.

- **(s02-0-c0.jpg)** → 카드 설명, 태그, 오른쪽 체험 미션이 너무 작고 회색 대비가 낮다. → 카드당 `이름 + 입력 + 결과`만 남기고 설명을 크게 한다. 체험 미션은 별도 장으로 분리한다.

- **(s03-1-c1.jpg)** → 표 안의 네 문장과 상단 캡션이 작고, 회색 글자가 어두운 배경에 묻힌다. → 네 문장을 2×2 카드로 확대하고 상단 캡션은 제거한다. 본문은 흰색에 가깝게 올린다.

- **(s04-3-c0.jpg)** → 제목이 지나치게 커서 아래 설명 공간을 압박하는 반면, 정작 UI·대본 속 글자는 작다. → 제목을 약 25% 줄이고 세 요소의 실제 용어와 연결 화살표를 확대한다.

- **(s05-6-c0.jpg)** → 손글씨체의 작은 설명과 가는 선은 뒤에서 읽기 어렵다. 화이트보드 위 파란색·회색 글씨도 대비가 약하다. → 손글씨체를 제목에만 사용하고 본문은 굵은 고딕으로 바꾼다. 화살표를 굵게 하고 흰 바탕 글자는 검정에 가깝게 한다.

- **(s06-3-c3.jpg)** → 요청 카드의 코드, 화살표 주석, 가격 설명이 한 화면에 과밀하다. 오른쪽 응답 설명은 특히 작다. → `요청`과 `응답`을 두 장으로 나눈다. 한 장에서는 코드 4~6줄만 크게 보여주고 나머지는 말로 설명한다.

- **(s07-1-c1.jpg)** → 서비스별 설명과 오른쪽 하단 주석이 작고 대비가 낮다. → 사례 수를 2개로 줄이고 서비스 이름보다 `입력→API→응답` 구조를 크게 보여준다.

- **(s08-3-c3.jpg)** → 오른쪽 카드 내부 문장과 하단 결론이 작으며 회색이다. → 예시 문장을 절반으로 줄이고 결론을 별도의 큰 한 줄로 옮긴다.

- **(s09-3-c3.jpg)** → 카드 안 예시와 태그 글자가 작다. → 질문과 최종 산출물만 남기고 예시는 발표자가 말하거나 활동지로 옮긴다.

- **(s10-3-c3.jpg)** → 카드 설명과 temperature 하단의 서비스명·주의문이 읽히지 않는다. → 핵심 규칙 하나와 온도 비교만 남긴다. 주의문은 본문 크기로 키운다.

- **(s11-2-c2.jpg)** → 시스템 프롬프트 전문을 한 화면에 넣어 행간이 좁고, 하단 설명이 매우 작다. → 네 구역을 한 번에 보여주지 말고 한 구역씩 확대한다. 마지막에는 축약된 전체본만 보여준다.

- **(s12-1-c1.jpg)** → A·B·C 설명, 안전 원칙, 종료 기준이 모두 작다. → 활동 지시는 활동지로 보내고 슬라이드에는 `A 문제 / B 입출력 / C 프롬프트`와 종료 기준만 남긴다.

- **(s13-3-c3.jpg)** → 정보 상자 다섯 개와 긴 괄호 설명이 몰려 있다. 대부분 뒤에서 읽을 수 없다. → `내가 작성하는 것`, `제공되는 것`, `보안 주의`의 3개 영역으로 축약한다.

## 상대적으로 큰 문제가 없는 장면

- **(s02-0-c0.jpg)**의 세 후보 자체는 역할이 서로 달라 선택 활동의 소재로는 이해 가능하다. 다만 작은 설명과 버튼의 의미는 수정해야 한다.
- **(s18-1-c1.jpg)**의 `파일 업로드 → 키 가림 → 제출`이라는 큰 순서는 단순하다. 실제 키 처리 방식만 정확히 밝혀야 한다.
- 완전히 수정 불필요하다고 판단되는 슬라이드는 없다. 공통적으로 보조 설명의 글자 크기와 회색 대비가 교실 투사 환경에 부족하다.

# 학생에게 가장 위험한 오해 3가지

1. **API는 사람이 쓰는 웹 화면과 같은 창구다**  
   **(s04-3-c0.jpg, s05-6-c0.jpg)**의 비유와 사람용 UI 때문에, 프로그램이 서버의 API에 정해진 형식으로 요청한다는 핵심을 놓칠 수 있다.

2. **HTML 파일에 API 키를 넣고 저장·업로드해도 안전하다**  
   **(s13-3-c3.jpg, s14-6-c0.jpg, s18-1-c1.jpg)**에서 실습용 키와 실제 서비스 보안의 경계가 작게 처리되어 있다. 키가 자동으로 가려지는 범위도 불분명해 외부 공유로 이어질 위험이 있다.

3. **답이 이상하면 프롬프트, 화면이 이상하면 코드만 고치면 된다**  
   **(s16-3-c0.jpg)**의 이분법은 API 인증·네트워크·요청 형식·응답 파싱 같은 원인을 빠뜨린다. 학생이 오류를 잘못 분류하고 무관한 프롬프트나 코드를 반복 수정할 수 있다.
