# 완성본 적대 검토

## 1. 슬라이드 화면 문구만 보았을 때 생기는 오해

### 1-1. “같은 입력 두 번”의 관찰 기준이 없다

> “② 같은 입력을 두 번 — 얼마나 달라지나?”

→ 학생은 무엇을 비교해서 기록해야 하는지 알 수 없다. 문장 전체가 달라지면 성공인지 실패인지, 형식까지 달라지면 문제인지 구별하기 어렵다. 특히 직전 수업의 온도 개념과 연결하려는 활동인데 화면에는 온도와의 연결이 없다.

→ 다음처럼 바꾼다.

> “같은 입력을 두 번 넣고, 내용의 차이와 형식의 유지 여부를 각각 확인한다.”

### 1-2. API를 “가게”와 “접수 창구”로 동시에 비유한다

> “Solar 가게”  
> “API — 프로그램용 접수 창구”  
> “지도 가게 / 결제 가게 / 날씨 가게”

→ Solar·지도·결제·날씨 서비스 자체와 API가 같은 층위의 ‘가게’처럼 보인다. 학생은 API를 외부 서비스 그 자체로 이해할 수 있다.

→ 다음처럼 관계를 고정한다.

> “Solar 서비스에는 사람이 쓰는 화면과 프로그램이 쓰는 API 접수 창구가 있다.”  
> “지도·결제·날씨 서비스도 각자의 API 접수 창구를 제공한다.”

### 1-3. “정해진 형식”이 무엇을 가리키는지 불명확하다

> “정해진 형식!”

→ 요청 주소, 헤더, JSON 본문 중 무엇이 정해진 형식인지 화면만으로는 알 수 없다.

→ 다음처럼 구체화한다.

> “API는 주소·헤더·JSON 본문을 약속된 형식으로 보내야 한다.”

### 1-4. 실제 산업에 대한 과도한 일반화

> “대부분의 AI 기능은 남의 모델을 API로 빌려 만든다”

→ 검색 결합, 자체 모델, 온디바이스 모델, 미세조정 등 다양한 구현을 지운 과도한 일반화다. 네 사례만으로 “대부분”을 뒷받침할 수도 없다.

→ 다음처럼 범위를 낮춘다.

> “많은 AI 서비스가 이미 만들어진 모델을 API로 연결해 기능을 만든다.”

### 1-5. “문제 없는 서비스는 장난감”은 잘못된 가치 판단이다

> “문제 없는 서비스는 장난감이다”

→ 창작·놀이·예술 서비스는 실제 사용자 가치가 있어도 ‘문제 해결’ 문장으로 표현하기 어렵다. 학생이 재미·창작 분야를 선택해 놓고 자신의 아이디어를 열등하게 느낄 수 있다.

→ 다음처럼 바꾼다.

> “좋은 서비스는 사용자가 얻을 가치가 분명하다 — 불편 해결뿐 아니라 재미·표현·창작도 가치다.”

### 1-6. 입력 칸 수를 절대 규칙처럼 제시한다

> “칸은 1~3개 — 사용자는 귀찮은 걸 싫어한다”

→ 이번 프로젝트의 제작 제한과 일반적인 UX 원칙이 섞였다. 학생은 실제 서비스도 입력 칸이 세 개를 넘으면 나쁘다고 배울 수 있다.

→ 다음처럼 수업 범위를 밝힌다.

> “이번 프로젝트에서는 구현과 테스트에 집중하기 위해 입력 칸을 1~3개로 제한한다.”

### 1-7. 메모장 저장 절차가 화면만으로는 충분하지 않다

> “메모장 저장 — 모든 파일 · .html”

→ Windows 메모장에서는 파일 이름을 `.html`로 적어도 파일 형식을 잘못 선택하면 `.html.txt`가 될 수 있다. 활동지에는 UTF-8 안내가 있지만 학생이 구현 중 보는 슬라이드 14에는 없다.

→ 화면에 다음을 넣는다.

> “다른 이름으로 저장 → 파일 형식 ‘모든 파일’ → 이름 끝 `.html` → 인코딩 UTF-8”

### 1-8. 프롬프트 수정 안내가 문법 파손 위험을 숨긴다

> “★★★ 이 안의 문장만 고칩니다 ★★★”  
> “문장 고치기 → 저장 → 새로고침”  
> “따옴표·기호는 그대로!”

→ 백틱 문자열 안에서 백틱을 추가하거나 `${...}`를 쓰면 JavaScript가 깨지거나 코드로 해석될 수 있다. “따옴표·기호는 그대로”만으로는 코딩 무경험 학생이 이 위험을 알 수 없다.

→ 다음 경고를 화면에 추가한다.

> “문장 안에 백틱 기호(`)와 `${`는 새로 입력하지 않는다. 추가했다면 ChatGPT에 전체 코드 수정을 요청한다.”

## 2. 활동지 안내문·칸 구성의 결함

### 2-1. 제출 암호가 일반 비밀번호처럼 보인다

> “제출 암호 *”  
> “기억할 수 있는 것으로 정하세요.”

→ 학생이 실제로 쓰는 이메일·학교 계정 비밀번호를 재사용할 가능성이 있다. Google Sheets에 연결되는 활동지라면 특히 위험하다.

→ 명칭과 안내를 바꾼다.

> “수업용 불러오기 PIN *”  
> “학교 계정이나 다른 사이트의 비밀번호를 쓰지 말고, 이 활동에서만 사용할 숫자·문자를 정하세요.”

### 2-2. A3의 질문과 응답 방식이 맞지 않는다

> “A3. 왜 LLM이어야 하나요?”  
> “문장 만들기 / 요약·정리 / 상담·조언”

→ 질문은 ‘왜 필요한가’인데 학생이 할 수 있는 것은 능력 분류 선택뿐이다. “문장 만들기”를 고르는 것으로 LLM 필요성 설명이 끝난다. 계산기·규칙 기반 프로그램으로도 가능한 아이디어를 걸러내지 못한다.

→ 능력 선택 뒤에 필수 서술칸을 추가한다.

> “선택한 능력이 왜 필요한가요? 검색·계산·고정 규칙만으로 하기 어려운 점을 한 문장으로 쓰세요.”

### 2-3. A3는 질문상 중요하지만 D 활성화 조건에 없다

> “아직 비어 있어요: A1 문제, A2 한 문장 소개, B1 … C2 사용자 메시지 틀”

→ A3가 비어도 D가 활성화된다. 슬라이드에서는 “왜 LLM인가”를 A의 핵심으로 제시하지만 실제 완성본에서는 제출을 막지 않는 장식 칸이다.

→ D 활성화 필수값에 `A3 능력 선택 + 이유 한 줄`을 포함한다. 중요하지 않다면 A3 질문 자체를 “내 서비스가 사용할 LLM 능력”으로 낮춰 일치시킨다.

### 2-4. 입력 칸의 “이유”가 원칙과 달리 필수가 아니다

> “칸마다 존재 이유를 말할 수 있어야 한다.”  
> 활동지 placeholder: “이 칸이 필요한 이유”

→ B2 첫 입력 칸은 이름과 예시만 필수이고, 이유는 필수가 아니다. 화면 원칙을 지키지 않아도 D로 갈 수 있다.

→ 입력 칸이 추가될 때마다 `칸 이름·예시·필요한 이유` 세 항목을 한 묶음으로 필수화한다.

### 2-5. B3와 C1이 불일치해도 그대로 코드가 만들어진다

> “B3. 출력 설계”  
> “C1. 시스템 프롬프트 — … 출력 형식 …”  
> D: “출력 설계: …”  
> D: “시스템 프롬프트 … 한 글자도 고치지 말고”

→ 학생이 B3에는 “3줄”, C1에는 “5줄”이라고 써도 검출되지 않는다. 실제 API에는 C1만 들어가므로 B3는 코드 생성 프롬프트 속 참고 정보에 머문다. ChatGPT는 C1을 고칠 수 없다는 지시까지 받는다.

→ D 활성화 전에 체크박스를 둔다.

> “C1의 출력 형식에 B3의 내용·형식·길이를 모두 옮겨 썼는지 확인했습니다.”

가능하면 B3 내용을 C1 초안에 자동 삽입하거나 불일치 경고를 띄운다.

### 2-6. 자리표시자 규칙이 이름의 동일성만 요구한다

> “자리표시자 `{칸이름}`은 C2에만 씁니다.”  
> “B2의 칸 이름을 `{칸이름}`으로 끼우세요.”

→ 다음을 막지 못한다.

- 같은 입력 칸 이름을 두 번 쓰는 경우
- C2에 일부 입력 칸을 빠뜨리는 경우
- B2에 없는 자리표시자를 쓰는 경우
- 칸 이름 자체에 `{`, `}`, 백틱, `${`를 넣는 경우

→ 자동 검증을 추가한다.

> “입력 칸 이름은 서로 달라야 하며, 각 이름이 C2에 정확히 한 번 이상 등장해야 합니다. `{ }`, 백틱, `${`는 칸 이름에 사용할 수 없습니다.”

### 2-7. E의 “전 → 후” 기록이 무엇의 전후인지 모호하다

> “고친 내용 (전 → 후)”  
> placeholder: “예: ‘짧게 써라’ → ‘3줄 이내로, 별표 없이 써라’”

→ 시스템 프롬프트 문장인지 사용자 메시지 틀인지 코드인지 구분되지 않는다. 바로 위의 “고친 위치”를 고르더라도 실제 변경 위치나 변경 결과를 재현하기 어렵다.

→ 칸을 분리한다.

> “고치기 전 문장·코드”  
> “고친 뒤 문장·코드”  
> “어느 상수 또는 기능을 고쳤는가: SYSTEM_PROMPT / PROMPT_TEMPLATE / 화면·기능”

### 2-8. “서비스 소개 한 줄” 작성법이 중복을 유도한다

> “서비스 소개 한 줄 *”  
> placeholder: “B1 이름 + A2 소개를 한 줄로”

→ A2 자체가 이미 “○○을 넣으면 △△을 주는 서비스”다. 단순 연결하면 “대본 뼈대 메이커 발표 주제와 시간을 넣으면…”처럼 제목과 문장이 어색하게 붙는다.

→ 형식을 명시한다.

> “예: 대본 뼈대 메이커 — 발표 주제와 시간을 넣으면 대본 뼈대를 주는 서비스”

## 3. D의 코드 생성 프롬프트 전문 결함

### 3-1. 안전한 출력 삽입 방법이 빠졌다

> “응답에서 `choices[0].message.content` 문자열만 꺼내 결과 영역에 그대로 표시한다”

→ “그대로 표시”는 `textContent`와 `innerHTML` 두 방식으로 해석된다. ChatGPT가 `innerHTML`을 사용하면 모델 응답 속의 HTML이 실행될 수 있다. 학생이 공개하거나 친구에게 입력을 받는 순간 스크립트 삽입 위험이 생긴다.

→ 기술 명세에 다음을 추가한다.

> “모델 응답은 반드시 `textContent`로 결과 영역에 넣고, `innerHTML`은 사용하지 않는다.”

### 3-2. 백틱 안에 “한 글자도 고치지 않고” 넣으라는 지시는 항상 실행 가능하지 않다

> “한 글자도 고치지 말고 `SYSTEM_PROMPT` 상수에 넣을 것”  
> “두 프롬프트 상수는 반드시 백틱(`) 템플릿 문자열로”

→ 학생 문장에 백틱이 들어가면 그대로 넣는 순간 문자열이 닫힌다. `${...}`가 들어가면 JavaScript 표현식으로 평가된다. “한 글자도 고치지 말라”와 “유효한 백틱 문자열로 만들라”가 충돌한다.

→ 둘 중 하나로 고친다.

- 활동지 단계에서 백틱과 `${` 입력을 금지·검증한다.
- 또는 “의미와 표시 문장은 바꾸지 말되 JavaScript 문자열에 필요한 이스케이프는 적용한다”고 명시한다.

### 3-3. 자리표시자 치환의 완료 조건이 없다

> “`{칸이름}` 자리표시자에 해당 입력 칸의 값을 넣어 만든다.”

→ 첫 번째 항목만 치환할지, 같은 자리표시자가 여러 번 나오면 모두 치환할지, 남은 자리표시자를 검사할지 정하지 않았다. ChatGPT가 단순 `replace()`를 쓰면 첫 등장만 바뀔 수 있다.

→ 다음처럼 명시한다.

> “각 자리표시자의 모든 등장을 해당 값으로 치환한다. 조립 후 `{...}` 형태가 남아 있으면 API를 호출하지 말고 누락된 입력 칸을 한국어로 알려 준다.”

### 3-4. 빈 입력 방지가 기술 명세에 없다

> “위 입력 칸들 + 실행 버튼”  
> “사용자 메시지는 … 입력 칸의 값을 넣어 만든다.”

→ 입력칸에 `required`를 붙이거나 공백을 검사하라는 지시가 없다. 빈 값으로 API가 호출되어도 모델이 그럴듯한 일반 답을 내놓을 수 있어 학생은 정상 작동으로 착각한다.

→ 다음을 추가한다.

> “모든 입력값은 앞뒤 공백을 제거해 검사한다. 하나라도 비어 있으면 API를 호출하지 않고 해당 칸을 채우라는 안내를 표시한다.”

### 3-5. 오류를 모두 서버 혼잡으로 오인하게 한다

> “요청이 실패하거나 429 응답이 오면 ‘지금 서버가 붐빕니다’”

→ 인터넷 끊김, 401 키 오류, 400 요청 오류, 500 서버 오류가 모두 혼잡으로 표시된다. 학생은 잘못된 프롬프트나 코드 문제를 기다림으로 해결하려 한다.

→ 상태별 최소 분기를 둔다.

- 429: 서버 혼잡, 잠시 후 재시도
- 401/403: 수업용 키 확인 요청
- 네트워크 실패: 인터넷 연결 확인
- 그 외: 오류 코드와 함께 선생님에게 보여 줄 안내

### 3-6. 버튼 잠금 시간이 임의 범위뿐이다

> “15~40초 동안 버튼을 잠근다.”

→ 정확히 어떻게 정할지 없어 생성 코드마다 고정 15초, 고정 40초, 무작위 등 구현이 달라진다. `Retry-After` 응답도 활용하지 않는다.

→ 다음처럼 고정한다.

> “429이면 `Retry-After` 헤더가 있으면 그 시간을 사용하고, 없으면 20~40초 사이의 무작위 시간 동안 잠근다. 남은 초를 버튼에 표시한다.”

## 4. 데모 시스템 프롬프트 3종의 모범성

### 4-1. 3줄 위로: 위기 입력 처리 기준이 없다

> “의학적 진단이나 치료에 해당하는 조언은 하지 않는다.”  
> “장난이거나 무관한 입력이 오면 … 안내한다.”

→ 자해·자살·폭력 피해처럼 장난도 아니고 일반 고민도 아닌 위기 입력이 들어올 수 있다. 현재 프롬프트는 이런 입력에도 ‘다른 각도’와 ‘내일의 작은 한 걸음’을 정확히 3줄로 내게 한다. 학생이 상담형 서비스의 모범으로 삼기에는 안전 설계가 부족하다.

→ 별도 예외를 추가한다.

> “자신이나 타인을 해칠 위험, 학대·폭력 등 즉각적인 위험이 드러나면 3줄 형식을 중단하고, 혼자 해결하지 말고 지금 곁의 신뢰할 수 있는 어른이나 긴급 도움에 연락하도록 짧고 분명하게 안내한다.”

### 4-2. 면접 코치: 입력 누락과 사실 꾸며내기를 막지 않는다

> “학생의 한 줄 소개에 있는 경험을 적어도 한 질문에 연결한다.”  
> “면접 준비와 무관한 입력이 오면…”

→ `지망 분야`만 있고 자기소개가 비었거나, 자기소개가 너무 모호한 경우가 빠졌다. 또한 입력에 없는 활동·성과를 힌트에 만들어 내지 말라는 지시가 없다.

→ 다음을 추가한다.

> “두 입력 중 하나라도 비어 있으면 부족한 칸만 다시 요청한다.”  
> “학생이 제공하지 않은 경험·성과·자격을 사실처럼 만들어 내지 않는다.”

### 4-3. 벼락치기 설계사: 구간 계산 규칙이 모호하다

> “남은 시간을 3~5개 구간으로 나눈 계획표”  
> “마지막 구간 앞에는 5분 쉬는 구간을 하나 둔다.”

→ 5분 휴식이 3~5개 구간에 포함되는지 불분명하다. 남은 시간이 5분 미만이거나 매우 짧은 경우에는 규칙 자체를 만족할 수 없다. “구간의 합이 시간을 넘지 않는다”만 있고 시간을 정확히 다 쓸지, 남는 시간을 어떻게 표시할지도 없다.

→ 다음처럼 명확히 한다.

> “공부 구간과 휴식 구간을 합쳐 총 3~5개로 만든다. 총합은 남은 시간과 정확히 같게 한다. 남은 시간이 15분 미만이면 휴식 구간 규칙을 적용하지 않고 1~2개 공부 구간만 제시한다.”

### 4-4. 벼락치기 설계사: 일부 빈칸을 검사하지 않는다

> “남은 시간이 숫자가 아니거나 공부와 무관한 입력이 오면…”

→ 과목이나 시험 범위가 비어 있어도 남은 시간만 숫자면 계획을 생성할 수 있다.

→ 다음으로 바꾼다.

> “과목·시험 범위·남은 시간 중 하나라도 비어 있거나, 남은 시간이 양의 숫자가 아니면 부족하거나 잘못된 칸을 구체적으로 알려 준다.”

## 5. `quiz.json` 타당성

### 5-1. 첫 문항은 ‘하나’를 고르기 어렵다

> “가장 다른 점 하나”  
> “채팅창이 없고…” / “프롬프트를 내가 다 쓰지 않았다” / “답의 모양이 늘 비슷하다” / “한 가지 일만 한다”

→ 네 선택지는 서로 배타적이지 않다. 한 학생에게 네 가지가 모두 참일 수 있다. 정답 없는 인식 조사라 해도 “가장”의 판단 기준이 없다. 또한 “답의 모양이 늘 비슷하다”의 ‘늘’은 확률적 출력과 맞지 않는다.

→ 복수 선택 문항으로 바꾸거나 질문을 다음처럼 수정한다.

> “방금 체험하면서 가장 먼저 눈에 띈 차이는 무엇이었나요?”  
> “답의 모양이 대체로 일정하게 설계되어 있다”

### 5-2. 문제 지도는 “한 단어” 제약 때문에 핵심 맥락을 잃는다

> “귀찮음·고민을 한 단어로 적어 주세요”

→ “발표”는 발표가 귀찮다는 뜻인지, 대본 작성·불안·시간 관리가 문제인지 알 수 없다. 이후 A1의 “누가, 언제, 어떤 문제”로 확장할 근거가 약하다.

→ 15자 안팎의 짧은 구로 받는다.

> “자주 겪는 귀찮음·고민을 짧은 말로 적어 주세요. 예: 발표 대본 막힘, 급식과 저녁 메뉴 겹침”

### 5-3. 개선 위치 문항은 실제 행동을 하나로 축소한다

> “내가 고친 곳은 어디였나요?”  
> 단일 선택 4개

→ 학생은 시스템 프롬프트와 화면을 모두 고칠 수 있다. 단일 선택 결과는 실제 개선 행동의 분포를 왜곡한다.

→ 복수 선택으로 바꾸거나 다음처럼 질문한다.

> “가장 큰 효과가 있었던 첫 번째 수정은 어디였나요?”

### 5-4. 슬라이드 연결 번호

`slide`가 0-based라는 전제에서 2→슬라이드 3, 8→슬라이드 9, 16→슬라이드 17로 연결되어 있다. 이 부분에는 명백한 오류가 없다.

## 6. 교사 개입 없이 망가지는 실패 시나리오 2개

### 시나리오 1: 백틱 하나로 생성 코드가 즉시 파손된다

1. 학생이 C1에 “답은 `결론`이라는 표시 뒤에 쓴다”처럼 백틱을 입력한다.
2. D는 ChatGPT에 C1을 “한 글자도 고치지 말고” 백틱 문자열에 넣으라고 한다.
3. 생성된 `SYSTEM_PROMPT` 문자열이 중간에서 닫히며 JavaScript 구문 오류가 발생한다.
4. HTML은 열리지만 실행 버튼이 작동하지 않는다.
5. 슬라이드 16은 “따옴표·기호는 그대로”라고만 하므로 학생이 원인을 찾기 어렵다.
6. 기본 HTML로 구제해도 학생 본인의 프롬프트를 옮기는 순간 같은 오류가 재발할 수 있다.

필요한 예방은 활동지 입력 검증과 D의 이스케이프 지시다.

### 시나리오 2: 빈 입력으로도 “정상 작동한 것처럼” 보인다

1. 학생이 입력 칸을 채우지 않고 실행 버튼을 누른다.
2. D 명세에는 `required`나 공백 검사가 없으므로 생성 코드가 그대로 API를 호출한다.
3. 모델은 빈 자리표시자가 포함된 메시지에도 일반적인 답을 생성한다.
4. 학생은 오류가 뜨지 않았으므로 정상 테스트를 통과했다고 기록한다.
5. 장난 입력 테스트도 서비스와 관련된 일반 답으로 흘러갈 수 있다.
6. 빈칸 테스트는 선택 과제이므로 이 결함이 제출 전 발견되지 않는다.
7. 제출된 서비스는 실제 사용자가 값을 빠뜨릴 때마다 토큰을 쓰면서 무의미한 답을 낸다.

필요한 예방은 모든 생성물에 공백 검사와 API 호출 차단을 의무화하는 것이다.

## 7. 학생 눈높이에 비해 어려운 화면 용어

다음 용어는 화면에 남겨도 되지만 즉시 붙는 쉬운 풀이가 필요하다.

- “클라이언트” → “API를 요청하는 우리 프로그램”
- “요청 본문” → “API에 보내는 내용”
- “역할별 메시지 목록” → “개발자 지시와 사용자 요청을 구분한 목록”
- `choices[0].message.content` → “응답 JSON에서 실제 답이 들어 있는 위치”
- “단가” → “토큰 한 조각당 가격”
- “워드클라우드” → “같은 말이 많을수록 크게 보이는 단어 지도”
- “품질 보증(QA)” → “제출 전 오류와 품질을 확인하는 검사”
- “상수” → “코드 위쪽에 이름을 붙여 저장한 값”
- “백틱” → 기호를 크게 보여 주며 “작은따옴표와 다른 ` 기호”
- “템플릿 문자열” → “입력값을 끼워 넣을 수 있는 문장”
- “반응형 스타일” → “휴대전화와 PC 화면 크기에 맞춰 바뀌는 디자인”
- “CDN” → 학생이 직접 다룰 필요가 없으므로 화면용 기술 명세에서는 “외부 파일을 불러오지 않음”으로 대체 가능
- `reasoning_effort`, `stream`, `viewport`, `429` → 학생 학습 목표가 아니라 생성기용 명세이므로 접어서 보여 주거나 “고정 기술 명세”임을 더 분명히 표시해야 한다.

# 치명적 3가지

1. **모델 응답을 안전하게 표시하라는 지시가 없음**  
   `innerHTML` 생성 가능성을 막지 못한다. D에 `textContent만 사용`을 반드시 넣어야 한다.

2. **학생 프롬프트와 백틱 문자열의 충돌**  
   “한 글자도 수정 금지”와 “백틱 상수 사용”이 양립하지 않는다. 백틱·`${` 입력 검증 또는 이스케이프 지시가 필수다.

3. **빈 입력 및 자리표시자 불일치를 막는 검증이 없음**  
   서비스가 오류 없이 엉뚱한 답을 내므로 학생이 결함을 발견하지 못한 채 제출할 가능성이 높다. D 활성화 검증과 생성 코드의 실행 전 검사를 모두 넣어야 한다.
