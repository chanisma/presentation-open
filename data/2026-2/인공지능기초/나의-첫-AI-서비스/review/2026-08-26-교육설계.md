# 총평

이 계획은 100분 수업이 아니라, 모든 학생의 계정·네트워크·생성 코드가 한 번에 정상 작동한다는 가정 아래에서만 성립하는 100분짜리 시연이다. 25명이 실제로 움직이면 1차시는 설계가 미완성되고, 2차시는 저장·오류 해결 단계에서 병목이 발생해 핵심 목표인 “직접 수정→재시험”이 잘릴 가능성이 높다.

## 1. 시간 배분

### 1-1. 산술적으로만 50분이다

> 원문 인용: “1차시 … = 32′ + S12 설계 활동 18′ = 50′.”  
> 무엇이 문제인가: 로그인, 링크 전환, 라이브 접속 코드 입력, 활동지 접속, 교사 지시, 학생 질문, 자리 이동 시간이 0분이다. 수업 전환 비용을 숨긴 계산이다.  
> 구체적 수정안: 본시 내용은 최대 42분으로 다시 짜고 8분을 전환·오류 완충으로 확보하라. S7 실제 사례는 삭제하거나 활동지 읽을거리로 보내라.

### 1-2. 데모 3종 체험 6분은 불가능하다

> 원문 인용: “S2 체험 6′”, “셋 다 한 번씩 써 본다 (5분)”, “한 서비스에 같은 입력을 두 번 넣어 본다.”  
> 무엇이 문제인가: 학생 한 명당 최소 다섯 번의 API 호출이 필요하다. 링크 세 개를 열고 입력을 생각하고 결과를 읽는 데만 5분이 넘으며, 25명이면 짧은 시간에 최소 125회 호출이 몰린다.  
> 구체적 수정안: 학생별 데모 하나만 배정하고 같은 입력 2회만 실행하게 하라. 세 데모의 결과는 모둠 간 비교하거나 교사가 캡처로 제시하라.

### 1-3. 라이브 문항 시간이 응답 수집 시간보다 짧다

> 원문 인용: “S3 2′”, “S9 2′”, “S17 2′.”  
> 무엇이 문제인가: 25명이 접속·응답하고 분포를 확인한 뒤 교사가 발문까지 하기에 2분은 부족하다. 한 명의 접속 문제를 봐주는 순간 다음 활동이 밀린다.  
> 구체적 수정안: 라이브는 한 차시에 하나만 남기거나, 로그인 없는 손들기·색 카드 방식으로 바꾸고 각 3~4분을 배정하라.

### 1-4. A~C 설계 18분은 산출물 요구량과 맞지 않는다

> 원문 인용: “S12 설계 활동 18′”, “A 기획 … B 입출력 … C 시스템 프롬프트.”  
> 무엇이 문제인가: 아이디어 결정, 사용자·문제 정의, 입력 최대 3개, 출력 다섯 요소, 온도, 시스템 프롬프트, 예외까지 처음 설계한다. 코딩 경험과 무관하게 성인도 18분 안에 질 있게 끝내기 어렵다.  
> 구체적 수정안: 1차시 설명을 20분 이내로 줄이고 설계에 최소 25분을 주라. 아이디어 6종과 반완성 템플릿을 제공해 선택형 경로도 마련하라.

### 1-5. “다음 시간 5분 보충”은 완충이 아니다

> 원문 인용: “설계(A~C) 미완 학생은 2차시 앞 5분 + 쉬는 시간 보충.”  
> 무엇이 문제인가: 2차시 시작 5분은 S13~S14 설명과 겹친다. 쉬는 시간을 사실상 필수 활동 시간으로 쓰는 것도 부적절하며, 미완 학생만 이후 설명을 놓치게 된다.  
> 구체적 수정안: 1차시 종료 기준을 “D 주문서 복사 준비 완료”로 정하고 수업 안에서 달성시켜라. 미완성자는 교사가 제공한 기본 설계로 2차시에 합류하게 하라.

### 1-6. 생성부터 실행까지 12분은 성공자 기준이다

> 원문 인용: “생성 실습 12′(접속·붙여넣기·생성 대기·저장·실행).”  
> 무엇이 문제인가: ChatGPT 접속, 긴 주문서 붙여넣기, 코드 생성, 복사, 메모장 저장, 확장자 확인, 브라우저 실행을 처음 하는 학생에게 12분은 지나치게 짧다. 한 번 코드가 끊기면 즉시 초과한다.  
> 구체적 수정안: 생성·저장·첫 실행에 최소 20분을 배정하라. 교사 설명은 사전 영상이나 인쇄 체크리스트로 옮기고, 정상 동작 기본 HTML도 반드시 준비하라.

### 1-7. 테스트 5분은 API 지연을 계산하지 않았다

> 원문 인용: “테스트 실습 5′”, “정상/아슬아슬/장난 세 입력을 다 넣어 본다.”  
> 무엇이 문제인가: 세 번 호출하고 결과를 읽고 ‘입력·기대·실제’를 기록해야 한다. 호출당 30초만 걸려도 기록과 판단 시간은 거의 남지 않는다.  
> 구체적 수정안: 첫 테스트는 정상·예외 2종으로 줄이고 8~10분을 주라. 세 번째 테스트는 빠른 학생 확장 과제로 돌려라.

### 1-8. 개선 10분에는 오류 복구 시간이 없다

> 원문 인용: “개선 실습 10′”, “메모장으로 열기 → … 문장 고치기 → 저장 → 브라우저 새로고침.”  
> 무엇이 문제인가: 파일을 잘못 열거나 JavaScript 문자열을 깨뜨리면 수정이 아니라 복구가 필요하다. 코드 문제라면 ChatGPT 재생성까지 포함되어 10분 안에 끝나지 않는다.  
> 구체적 수정안: 개선 목표를 “프롬프트 문장 한 곳 수정 후 한 번 재시험”으로 제한하고 15분을 확보하라. 코드 수정은 교사 제공 복구본으로 교체하는 별도 경로로 분리하라.

### 1-9. 자정 제출은 수업 목표 달성 여부를 가린다

> 원문 인용: “제출은 당일 자정까지 허용.”  
> 무엇이 문제인가: 학교 밖에서 누구의 도움으로 완성했는지 알 수 없고, 교실에서 개선 경험을 못 한 학생도 완성 코드만 제출할 수 있다. 수업 시간 부족을 과제로 넘긴 것이다.  
> 구체적 수정안: 수업 종료 전에 미완성이라도 현재 파일과 테스트 기록을 제출하게 하고, 자정 제출은 별도의 수정본으로 받아 두 버전을 비교하라.

## 2. 학생이 멈추는 지점

### 2-1. A 구역은 아이디어가 없는 학생을 구하지 못한다

> 원문 인용: “막히면: S8 세 질문으로 돌아가기 / S9 문제 지도 다시 보기.”  
> 무엇이 문제인가: “질문을 다시 보라”는 것은 발상 지원이 아니다. 워드클라우드의 ‘발표·급식·진로’ 같은 단어는 서비스 목적과 입출력으로 자동 변환되지 않는다.  
> 구체적 수정안: ‘상황–사용자–입력–출력’이 채워진 선택형 씨앗 카드 6개를 제공하고, 학생은 하나를 골라 한 요소 이상 변형하게 하라.

### 2-2. “왜 LLM인가”는 초보자에게 지나치게 추상적이다

> 원문 인용: “A3 왜 LLM이어야 하나(검색·계산기로 안 되는 이유 한 줄).”  
> 무엇이 문제인가: 학생은 검색, 규칙 기반 프로그램, LLM의 기능 경계를 아직 판별하기 어렵다. 그럴듯하게 “AI가 더 잘해 줘서”라고 쓰고 통과할 가능성이 높다.  
> 구체적 수정안: “정답 계산/자료 찾기/문장 생성·분류·요약” 비교표를 주고, 자신의 서비스가 어느 능력을 쓰는지 근거와 함께 선택하게 하라.

### 2-3. B 구역의 요구가 지나치게 많다

> 원문 인용: “출력 설계(모양·길이·말투·반드시 포함·금지).”  
> 무엇이 문제인가: 모든 서비스에 다섯 요소가 다 필요한 것은 아니다. 학생은 의미 없는 금지 조건과 말투를 억지로 채워 프롬프트만 길게 만들 수 있다.  
> 구체적 수정안: ‘필수 3개: 결과 내용·형식·길이’와 ‘선택 2개: 말투·금지’로 나누고, 각 조건이 필요한 이유를 한 줄 쓰게 하라.

### 2-4. C 구역과 `PROMPT_TEMPLATE`의 역할이 충돌한다

> 원문 인용: “C 시스템 프롬프트 … 사용자 입력 자리는 `{칸이름}`으로 표시”, “user 메시지는 `PROMPT_TEMPLATE`의 `{칸이름}` 자리에 입력값을 끼워 조립.”  
> 무엇이 문제인가: 사용자 입력 자리의 소유자가 시스템 프롬프트인지 사용자 메시지 템플릿인지 불명확하다. 학생이 같은 변수를 양쪽에 중복하거나, 시스템 프롬프트에만 넣어 실제 사용자 메시지가 빈약해질 수 있다.  
> 구체적 수정안: C를 `SYSTEM_PROMPT`와 `USER_PROMPT_TEMPLATE` 두 칸으로 명확히 분리하라. 중괄호는 사용자 템플릿에만 쓰게 하고 완성 예시 한 세트를 제시하라.

### 2-5. ChatGPT가 질문하거나 설명만 할 경우의 절차가 없다

> 원문 인용: “붙여넣기 → 전송 — 확인: 코드 블록이 생성되기 시작.”  
> 무엇이 문제인가: 생성형 모델은 추가 질문을 하거나, 코드 앞뒤에 설명을 붙이거나, 여러 파일로 나누거나, 수정된 요구 일부를 누락할 수 있다. 계획은 곧바로 완전한 코드 블록이 나온다고 가정한다.  
> 구체적 수정안: “질문하지 말고 합리적으로 결정”, “코드 블록 하나만 출력”, “마지막 줄 `</html>` 확인”을 주문서와 학생 체크리스트에 넣어라.

### 2-6. 저장 과정의 실제 함정이 두 개 이상 빠졌다

> 원문 인용: “다른 이름으로 저장 `나의서비스.html` (파일 형식: 모든 파일, 인코딩: UTF-8).”  
> 무엇이 문제인가: 학생은 저장 위치를 잊거나, `나의서비스.html.txt`로 저장하거나, 기존 파일 대신 새 사본을 열고 수정할 수 있다. 학교 PC에서 확장자가 숨겨져 있으면 확인도 어렵다.  
> 구체적 수정안: 지정 폴더를 미리 만들고 파일명을 학번으로 통일하라. 탐색기에서 파일 형식이 “HTML 문서”인지 확인하는 화면과 ‘우클릭→연결 프로그램→메모장’ 절차까지 제공하라.

### 2-7. 메모장 직접 수정은 “코드를 몰라도” 안전하지 않다

> 원문 인용: “`SYSTEM_PROMPT` 속 문장 고치기 … 코드는 한 글자도 몰라도 된다.”  
> 무엇이 문제인가: 문자열이 따옴표·백틱·줄바꿈으로 감싸져 있으면 학생이 같은 문자를 입력하거나 백틱 하나를 지우는 순간 전체 JavaScript가 멈춘다. `SYSTEM_PROMPT`를 찾는 것과 문자열 경계를 보존하는 것도 코딩 문해력이 필요하다.  
> 구체적 수정안: HTML 화면 안에 프롬프트 편집 상자를 두고 localStorage에 저장하도록 하거나, 수정 구역을 `<script type="text/plain">` 등에 안전하게 분리하라. 최소한 교체 가능한 한 줄과 “따옴표 밖은 건드리지 않기”를 색으로 표시한 연습 파일을 먼저 제공하라.

### 2-8. 새로고침만으로 수정본을 확인하지 못할 수 있다

> 원문 인용: “저장 → 브라우저 새로고침.”  
> 무엇이 문제인가: 학생이 메모장에서 편집 중인 파일과 브라우저에서 열린 파일이 다르거나, 저장하지 않은 채 새로고침하는 일이 흔하다. 오류가 나도 개발자 도구를 못 쓰므로 원인을 알 수 없다.  
> 구체적 수정안: 화면에 현재 `SYSTEM_PROMPT` 일부와 버전 번호를 표시하라. 수정할 때 버전을 `v1→v2`로 바꾸게 해 새 파일이 반영됐는지 눈으로 확인하게 하라.

## 3. 기술 실패 시나리오와 대비책

### 3-1. 공용 키의 429 대응이 사실상 “다시 눌러라”뿐이다

> 원문 인용: “실패·429 시 ‘잠시 후 다시’ 안내.”  
> 무엇이 문제인가: 25명이 같은 안내를 보고 동시에 다시 누르면 재시도 폭주가 생긴다. 잠금은 개인의 연타만 막을 뿐 학급 전체 호출량을 조절하지 못한다.  
> 구체적 수정안: 재시도 가능 시각을 30~60초 후로 무작위 분산하고, 교사가 호출 순서를 조별로 배정하라. API 없이 테스트할 수 있는 모의 응답 모드도 넣어라.

### 3-2. 예비 키 하나는 운영 대책이 아니다

> 원문 인용: “교사 확인 항목에 예비 키를 둔다.”  
> 무엇이 문제인가: 이미 생성된 25개 HTML에는 기존 키가 평문으로 들어가 있다. 예비 키로 바꾸려면 모든 학생이 코드를 다시 생성하거나 상수를 정확히 수정해야 한다.  
> 구체적 수정안: 수업 전용 프록시가 최선이다. 직접 호출을 유지한다면 활동지에서 현재 키를 복사하는 방식과 API 키 상수만 교체하는 1쪽 복구 안내를 준비하라.

### 3-3. 키 노출의 피해 범위를 통제하지 못한다

> 원문 인용: “데모 3종·활동지 주문서·학생 결과물 HTML에 평문으로 들어간다 = 저장소·배포에 공개된다.”  
> 무엇이 문제인가: 키가 ChatGPT 대화, 학생 파일, Google Sheets, 브라우저 기록 등 여러 곳에 복제된다. 수업 종료 후 비활성화하기 전 외부 공유·자동 수집·비용 소진이 가능하다.  
> 구체적 수정안: 키 사용량·비용 상한과 모델 권한을 최소화하고 즉시 폐기 시각을 정하라. 제출본에서는 키를 자동 제거하거나 `[REMOVED]`로 치환해야 한다.

### 3-4. 게스트 제한을 확인만 하고 대안은 두지 않았다

> 원문 인용: “ChatGPT 무로그인(게스트)은 메시지 수 제한이 있다 — 계정 로그인을 권장하되 게스트로도 진행 가능.”  
> 무엇이 문제인가: 생성 한 번, 이어쓰기, 오류 수정까지 최소 2~3회 메시지가 필요하다. 게스트 한도나 학교 로그인 정책에 걸리면 핵심 활동 자체가 중단된다.  
> 구체적 수정안: 수업 전 로그인 완료를 요구하거나 학교 승인 계정을 준비하라. 동시에 주문서별 사전 생성 기본 HTML을 내려받을 수 있게 해 ChatGPT 없이도 수정·테스트 단계에는 참여시켜라.

### 3-5. “이어 써 줘”는 완전한 코드 복구법이 아니다

> 원문 인용: “코드가 중간에 끊겼다 → ‘끊긴 부분부터 이어서 써 줘’라고 답장.”  
> 무엇이 문제인가: 두 코드 블록의 경계가 태그·문자열·함수 중간일 수 있어 초보자는 어디서 이어 붙일지 판단할 수 없다. 코드 복사 버튼도 두 블록을 자동 결합하지 않는다.  
> 구체적 수정안: “처음부터 전체 HTML을 하나의 코드 블록으로 다시 출력해 줘”를 기본 복구 문장으로 사용하라. `<!doctype html>`과 `</html>` 존재 여부를 검사하는 자동 검증도 활동지에 넣어라.

### 3-6. 생성 코드가 아예 동작하지 않을 때의 하한선이 없다

> 원문 인용: “같은 ChatGPT 대화에 ‘○○이 안 됩니다. 고쳐 주세요’.”  
> 무엇이 문제인가: 학생은 “안 됩니다” 이상의 오류 설명을 못 하고, ChatGPT는 추측 수정으로 다른 기능을 망가뜨릴 수 있다. API 오류, JavaScript 오류, CORS, 잘못된 키를 구분할 수도 없다.  
> 구체적 수정안: 화면에 HTTP 상태 코드와 짧은 오류 원인을 표시하게 하라. 교사용으로 401·429·네트워크·문법 오류별 진단표와 즉시 배포 가능한 정상 기본본을 준비하라.

## 4. 개념 설명의 결함

### 4-1. API의 “두 문” 비유가 통신 방향을 오해시킨다

> 원문 인용: “앞문은 사람이 쓰는 화면(UI), 뒷문은 프로그램이 쓰는 창구(API).”  
> 무엇이 문제인가: UI와 API는 같은 서비스의 앞문·뒷문일 수도 있지만, 이 수업에서는 학생 HTML이 Solar API의 외부 이용자다. ‘우리 서비스의 뒷문’과 ‘Solar의 창구’가 한 그림에서 섞인다.  
> 구체적 수정안: “내 프로그램 → Solar가 공개한 API 창구”라는 두 주체를 분리해 그려라. UI는 내 프로그램의 입력 화면, API는 Solar가 프로그램에게 공개한 접수처라고 설명하라.

### 4-2. “왕복 한 번이 전부”는 계획 내부와도 충돌한다

> 원문 인용: “정해진 형식의 응답이 돌아온다 — 왕복 한 번이 전부.”  
> 무엇이 문제인가: 뒤에서는 실패·429·재시도를 다룬다. 실제 호출도 인증, 오류 응답, 재호출이 존재하므로 “전부”라는 단정이 오개념을 만든다.  
> 구체적 수정안: “가장 기본적인 호출은 요청 한 번과 응답 한 번으로 볼 수 있다”로 낮춰 말하라.

### 4-3. “네 줄”은 실제 자료구조와 다르다

> 원문 인용: “LLM API 주문서는 네 줄”, “model·system·user·temperature.”  
> 무엇이 문제인가: `system`과 `user`는 독립 최상위 항목이 아니라 `messages` 안의 역할이며, `temperature`는 선택값이다. 뒤의 실제 코드 구조를 본 학생에게 설명이 어긋난다.  
> 구체적 수정안: “오늘 먼저 읽을 네 요소”라고 부르고, `messages` 안에 system과 user가 들어가는 축약 구조를 보여라.

### 4-4. 시스템 프롬프트를 비밀 지시처럼 설명한다

> 원문 인용: “사용자는 볼 수 없는 지시.”  
> 무엇이 문제인가: 이 수업의 단일 HTML에서는 소스 보기로 누구나 읽을 수 있다. 바로 다음 차시에는 학생이 메모장에서 그 지시를 찾는다.  
> 구체적 수정안: “일반 사용 화면에는 드러나지 않는 개발자 지시지만, 코드 속 비밀은 아니다”로 수정하고 개인정보나 키를 넣지 말라는 원칙을 붙여라.

### 4-5. 시스템 프롬프트가 모든 것을 결정한다는 표현은 과장이다

> 원문 인용: “시스템 프롬프트 한 장이 서비스의 정체를 정한다.”  
> 무엇이 문제인가: 서비스의 행동은 시스템 지시뿐 아니라 사용자 템플릿, 모델, 온도, 입력 검증, UI 코드에도 좌우된다. S17에서 출력 형식과 입력 칸까지 모두 ‘프롬프트 계열’로 합치는 근거가 된다.  
> 구체적 수정안: “시스템 프롬프트는 서비스 행동을 정하는 핵심 부품 중 하나”로 바꾸고 각 부품의 책임을 표로 분리하라.

### 4-6. 온도 3택의 이름이 결과를 보장하는 것처럼 보인다

> 원문 인용: “0.3 한결같이 / 0.7 보통 / 1.1 다채롭게.”  
> 무엇이 문제인가: 낮은 온도도 동일 출력을 보장하지 않고, 높은 온도가 좋은 위로나 창의성을 보장하지 않는다. 프롬프트·모델과 상호작용하는 설정을 성격 버튼처럼 단순화했다.  
> 구체적 수정안: “상대적으로 변화 적음/중간/변화 많음”으로 표현하고 “같은 답 보장 아님”을 표시하라. 각 서비스에 왜 그 값을 골랐는지 가설로 쓰게 하라.

### 4-7. 초보자 어휘가 한꺼번에 너무 많이 나온다

> 원문 인용: “CORS preflight”, “reasoning_effort”, “stream”, “max_tokens”, “QA”, “시스템 프롬프트”, “템플릿.”  
> 무엇이 문제인가: 학생이 알아야 할 핵심과 교사용 구현 정보가 섞여 있다. 생소한 영어 용어가 학습 목표인 서비스 구조와 개선 판단을 압도한다.  
> 구체적 수정안: 학생 화면에는 UI·API·시스템 지시·사용자 입력·온도만 남겨라. CORS와 세부 요청 옵션은 교사용 명세로 숨기고 QA는 “출시 전 검사”라고 먼저 설명하라.

## 5. live 문항의 타당성

### 5-1. S3은 “정답 없음”이라면서 교사가 전부 맞다고 판정한다

> 원문 인용: “정답 없음(분포 공개용)”, “전부 맞습니다.”  
> 무엇이 문제인가: ‘로그인이 없다’는 데모의 운영 조건일 뿐 ChatGPT와 AI 서비스의 본질적 차이가 아니다. “질문을 내가 쓰지 않았다”도 학생이 입력을 작성했다는 반론이 가능하다.  
> 구체적 수정안: “서비스의 구조적 차이”와 “오늘 데모의 편의 기능”을 구분하게 하라. 로그인 선지는 제외하고, ‘자유 대화 대신 정해진 목적·입력·출력이 있다’를 핵심 선지로 넣어라.

### 5-2. S9의 한 단어 응답은 문제 정의가 아니다

> 원문 인용: “귀찮음·고민을 한 단어로”, “큰 글자일수록 … 사용자가 많은 서비스.”  
> 무엇이 문제인가: ‘발표’는 문제의 맥락도 사용자도 아니다. 많이 나온 단어가 실제 수요가 크거나 LLM에 적합하다는 결론도 성립하지 않는다.  
> 구체적 수정안: “누가 언제 무엇 때문에 어렵다”의 짧은 문장으로 받거나, 단어를 받은 뒤 한 사례를 문제 문장으로 변환하는 후속 문항을 추가하라.

### 5-3. S17 선지는 서로 배타적이지 않다

> 원문 인용: “시스템 프롬프트”, “출력 형식”, “입력 칸”, “화면·기능.”  
> 무엇이 문제인가: 출력 형식은 이미 시스템 프롬프트의 일부이고, 입력 칸을 바꾸면 HTML UI와 템플릿 코드도 바뀐다. 단수 선택으로는 실제 수정 내용을 정확히 분류할 수 없다.  
> 구체적 수정안: 복수 선택으로 바꾸고 “지시문 문장 / 사용자 메시지 틀 / 화면 입력 요소 / 실행 코드”처럼 위치 기준으로 분류하라.

### 5-4. S17은 원하는 결론을 데이터에 강요한다

> 원문 인용: “앞의 셋을 합쳐 보세요 — 대부분 프롬프트 계열이죠.”  
> 무엇이 문제인가: 실제 분포를 보기 전에 결론을 정해 놓았다. 화면·기능 수정이 더 많거나 개선을 못 한 학생이 많으면 발문 자체가 무너진다.  
> 구체적 수정안: ‘수정 못 함’과 ‘수정 불필요’ 선지를 추가하고, 결과에 따라 “왜 이 위치가 많이 수정됐는가”를 해석하는 열린 발문으로 바꿔라.

## 6. 활동 설계의 빈틈

### 6-1. 서비스 품질의 최소 기준이 없다

> 원문 인용: “서비스 한 문장 소개”, “시스템 프롬프트 … 한 칸에 작성.”  
> 무엇이 문제인가: 문장을 채우기만 하면 통과한다. 문제의 구체성, 입력의 필요성, 출력의 검증 가능성, 예외의 적절성을 판별할 기준이 없다.  
> 구체적 수정안: A~C에 각각 2~3개의 통과 조건을 두고 D 복사 버튼은 조건을 만족해야 활성화되게 하라.

### 6-2. 부적절하거나 위험한 주제 경계가 없다

> 원문 인용: “자기만의 문제를 써도 좋습니다.”  
> 무엇이 문제인가: 외모 평가, 연애 판정, 정신건강 진단, 자해·성적 내용, 타인 비방, 개인정보 입력 서비스로 갈 수 있다. 공용 키와 외부 API로 실제 내용이 전송된다.  
> 구체적 수정안: 금지 주제와 개인정보 금지 규칙을 활동지 첫 화면에 명시하라. 의료·법률·심리 진단과 사람 평가 서비스는 선택 불가로 하고 교사 승인 후 D를 열게 하라.

### 6-3. 장난 입력을 막으면서 장난 서비스는 막지 않는다

> 원문 인용: “장난 입력은 반드시 온다 — 개발자는 사용자를 다 믿지 않는다.”  
> 무엇이 문제인가: 사용자 입력의 장난만 문제 삼고, 개발자 역할인 학생이 처음부터 모욕·평가·괴롭힘 목적의 서비스를 설계할 가능성은 다루지 않는다.  
> 구체적 수정안: “사람을 해치거나 등급 매기지 않는다”는 서비스 설계 원칙과 주제 승인 체크를 A 구역에 넣어라.

### 6-4. 베끼기가 너무 쉽고 구별할 증거가 없다

> 원문 인용: “데모의 [내부 보기] 훔쳐보기”, “코드는 빌렸지만 … 전부 여러분이 정했다.”  
> 무엇이 문제인가: 학생은 데모 프롬프트나 옆 학생의 D 주문서를 그대로 복사해도 완성 코드상 구별되지 않는다. ‘훔쳐보기’라는 표현도 변형 없는 복사를 정당화할 수 있다.  
> 구체적 수정안: 예시를 쓸 경우 사용자·입력·출력 중 두 요소 이상을 변형하게 하고, 무엇을 참고해 무엇을 바꿨는지 제출하게 하라.

### 6-5. 활동지가 입력 형식만 검사하고 의미는 검사하지 않는다

> 원문 인용: “B2의 칸 이름과 실시간 대조 — 없는 칸을 참조하면 경고.”  
> 무엇이 문제인가: 변수명 일치만 검증한다. 입력 칸의 존재 이유가 빈약하거나 출력 조건끼리 충돌해도 D 주문서가 생성된다.  
> 구체적 수정안: 자동 검사는 빈칸·중복 변수·상충하는 길이·필수 예외 누락까지 확장하고, 의미 품질은 짝 점검 체크리스트로 보완하라.

## 7. 교사가 개입하지 않을 때의 구체적 실패 3개

### 실패 시나리오 1 — 아이디어 미완성 학생

> 원문 인용: “C까지 못 가도 괜찮지만 A는 반드시 완성하세요.”  
> 무엇이 문제인가: 학생은 A에 “학생이 공부할 때 도움받는 공부 도우미”라고 쓰고 B·C를 급히 채운다. 2차시에는 모호한 주문서로 일반 챗봇을 생성하고, 무엇을 테스트하거나 개선해야 할지 기준이 없어 그대로 제출한다.  
> 구체적 수정안: A 통과 검사를 교사가 1차시 중간에 실시하고, 실패하면 반완성 주제 카드로 즉시 전환시켜라.

### 실패 시나리오 2 — 코드가 끊기고 게스트 한도에 걸린 학생

> 원문 인용: “끊긴 부분부터 이어서 써 줘”, “게스트도 가능.”  
> 무엇이 문제인가: 첫 출력이 `</script>` 이전에서 끊기고, 이어쓰기 후 학생은 두 코드 조각을 결합하지 못한다. 추가 요청에서 게스트 한도까지 걸려 저장·테스트·개선 경험을 모두 잃고 옆 학생 코드를 복사한다.  
> 구체적 수정안: 완전한 기본 HTML을 즉시 지급해 자신의 프롬프트만 이식하게 하고, 생성 실패 학생도 핵심 학습 단계로 복귀시키는 시한을 정하라.

### 실패 시나리오 3 — 프롬프트 수정으로 파일을 망가뜨린 학생

> 원문 인용: “`SYSTEM_PROMPT` 속 문장 고치기 … 코드는 한 글자도 몰라도 된다.”  
> 무엇이 문제인가: 학생이 프롬프트에 따옴표나 줄바꿈을 추가해 JavaScript 문법 오류를 만든다. 화면 버튼이 멈추자 이를 프롬프트 품질 문제로 오인하고 ChatGPT에 전체 재생성을 요청해 원래 설계와 개선 기록이 사라진다.  
> 구체적 수정안: 안전한 화면 내 프롬프트 편집 기능을 제공하고, 수정 전 파일을 `v1.html`, 수정 후를 `v2.html`로 별도 저장하게 하라.

## 8. 평가와 제출

### 8-1. 코드 전문은 개인 학습의 증거가 약하다

> 원문 인용: “최종 HTML 코드 전체 붙여넣기.”  
> 무엇이 문제인가: 대부분의 코드는 ChatGPT가 만들었으므로 학생의 이해와 기여를 보여주지 않는다. 복사 여부, 프롬프트 설계 과정, 오류 진단 능력도 판별할 수 없다.  
> 구체적 수정안: 코드는 실행 산출물로만 받고, 평가 증거는 A~C 설계, 테스트 기대·실제, 수정 전후 프롬프트, 수정 이유, 재시험 결과로 구성하라.

### 8-2. 개선의 효과를 입증하는 항목이 없다

> 원문 인용: “고치기 전→후.”  
> 무엇이 문제인가: 문장을 바꾼 사실만 남고 같은 입력으로 결과가 나아졌는지는 남지 않는다. 임의 수정도 ‘개선’으로 인정될 수 있다.  
> 구체적 수정안: `동일한 테스트 입력 / 수정 전 결과 / 수정 후 결과 / 나아졌다고 판단한 기준` 네 칸을 필수로 하라.

### 8-3. 버전 보존이 없어 학습 과정을 검증할 수 없다

> 원문 인용: “제출한 코드가 곧 … 출시본.”  
> 무엇이 문제인가: 최종본 하나만 제출하면 최초 생성본과 학생이 수정한 부분을 비교할 수 없다. 학생의 직접 개입 여부도 사라진다.  
> 구체적 수정안: 최초 생성본 v1과 개선본 v2를 함께 제출하거나, 최소한 `SYSTEM_PROMPT` 전후와 변경 위치를 자동 추출해 저장하라.

### 8-4. 한 줄 소감은 개념 이해 평가가 아니다

> 원문 인용: “한 줄 소감.”  
> 무엇이 문제인가: “재미있었다”로 끝나도 학습 목표 ①~④의 이해를 확인할 수 없다. API 구조와 프롬프트·코드 문제 구별 능력을 평가하지 못한다.  
> 구체적 수정안: “내 입력이 화면 결과가 되기까지 네 단계를 설명하라”와 “이번 문제를 프롬프트 문제로 판단한 근거는 무엇인가”를 짧은 필수 문항으로 바꿔라.

### 8-5. Google Sheets에 키가 든 전체 코드를 저장한다

> 원문 인용: “최종 HTML 코드 전체 붙여넣기 … Google Sheets 자동 기록.”  
> 무엇이 문제인가: 공용 API 키가 학생 수만큼 시트에 복제된다. 셀 한도뿐 아니라 접근 권한·보관 기간·유출 범위 문제가 생긴다.  
> 구체적 수정안: 제출 전에 `API_KEY` 값을 자동 제거하고 코드를 저장하라. 가능하면 HTML 파일 업로드와 별도의 설계·평가 데이터 제출로 분리하라.

# 치명적 3가지

1. **2차시가 실제로 들어가지 않는다.** 생성·저장·오류 복구를 12분으로 잡은 순간 핵심 활동인 테스트와 직접 개선이 희생된다. 설명과 데모를 줄이고 생성 이후에 최소 35분을 확보해야 한다.

2. **학급 공용 키 직접 호출 구조에 운영 안전망이 없다.** 25명의 동시 호출, 429 재시도 폭주, 키 복제·유출, 예비 키 교체 문제를 “잠시 후 재시도”로 해결할 수 없다. 프록시 또는 호출 순서 제어·모의 모드·키 자동 제거가 필요하다.

3. **코딩 무경험 학생의 메모장 직접 수정이 학습 목표의 단일 실패점이다.** 따옴표 하나로 파일 전체가 망가질 수 있는데 복구 경로가 ChatGPT 재요청뿐이다. 안전한 프롬프트 편집 UI, v1/v2 보존, 정상 기본 HTML을 준비하지 않으면 “내가 프롬프트를 고쳐 서비스를 개선했다”는 목표가 다수 학생에게 성립하지 않는다.
