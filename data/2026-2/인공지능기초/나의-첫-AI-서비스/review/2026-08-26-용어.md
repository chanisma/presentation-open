## 정식 용어 대조표

‘화면 텍스트에 등장’은 계획서의 내부 연구 기록이나 교사용 기술 명세가 아니라, 학생이 실제로 보는 슬라이드·활동지 텍스트를 기준으로 판정했다.

| 정식 용어 | 화면 텍스트에 등장하는가 | 어디서 | 보완 제안 |
|---|---|---|---|
| 인공지능 서비스·AI 서비스 | 예 | S1 제목, S2 미니 서비스, 덱 전반 | ‘서비스’가 단순 HTML 파일인지, 특정 기능을 제공하는 프로그램인지 S1에서 한 문장으로 정의하면 좋다. |
| LLM | 예 | 학습 목표, S5~S7 | 화면에서 약어의 원어 또는 뜻을 직접 정의하지 않는다. S5에 “LLM(대규모 언어 모델)”을 한 번 병기한다. |
| 프롬프트 | 예 | S1, S3~S4, S7, S11 이후 | 빈번히 사용되지만 한 문장짜리 정의가 약하다. “모델이 수행할 일과 답변 조건을 글로 적은 지시”를 화면에 제시한다. |
| 프롬프트 설계 | 예 | S7, S12 | S7에서 대본 비유와 함께 나오지만 무엇을 정하는 활동인지 정의되지 않는다. 역할·규칙·출력 형식·예외를 정하는 일이라고 연결한다. |
| 프롬프트 템플릿 | 아니요 | 학생 화면에는 “사용자 메시지 틀”, 코드에서는 `PROMPT_TEMPLATE` | S4 또는 S12에서 “프롬프트 템플릿(사용자 메시지 틀)”을 병기한다. |
| 시스템 프롬프트 | 예 | S11 제목·본문, S12, S13, S17, 활동지 C1 | 역할·규칙·출력 형식·예외를 담는다는 설명이 있어 실질적인 정의가 존재한다. 다만 ‘서비스의 심장’ 대신 “모델의 기본 역할과 동작 규칙을 지정하는 프롬프트”라는 정의 문장을 둔다. |
| 사용자 메시지 | 예 | S12 C2, S13, S17 | “사용자 메시지 틀”은 나오지만 API의 `user` 역할 메시지와의 관계가 약하다. S6에서 “user 역할의 메시지”로 연결한다. |
| 사용자 입력 | 예 | 학습 목표, S4·S6·S8 이후 | 충분히 사용된다. S4의 ‘빈칸’보다 정식 용어가 우선 보이게 한다. |
| 자리표시자 | 아니요 | `{칸이름}`만 제시 | 활동지 C2에서 “자리표시자 `{칸이름}`”으로 병기한다. |
| 사용자 인터페이스(UI) | 일부 | S4에는 “화면”, S5에는 “화면(UI)” | UI 약어는 나오지만 ‘사용자 인터페이스’라는 한국어 풀이는 없다. S4 구조도에 “사용자 인터페이스(UI·화면)”를 한 번 제시한다. |
| API | 예 | S4~S7, S13 이후 | “프로그램이 프로그램에게 일을 시키는, 형식이 약속된 창구”라고 정의한다. 다만 ‘뒷문’은 제거하고 “기능·데이터를 요청하기 위한 규칙과 접점”으로 보완해야 한다. |
| LLM API | 예 | S5~S7 | “말을 다루는 능력을 빌려주는 창구”로 설명된다. LLM에 요청을 보내고 생성된 응답을 받는 API라고 직접 정의한다. |
| API 호출 | 예 | 학습 목표, S13 명세 등 | 학생 화면에서는 ‘API 연결·주문’이 더 두드러진다. S5 왕복 화살표에 “API 호출”을 라벨로 붙인다. |
| API 요청 | 불충분 | S6에서 “주문서(요청)” 한 번 | 제목·구조도·내부 보기에서 모두 ‘주문서’가 우선한다. “API 요청”을 주 용어로 전면 교체한다. |
| 요청 본문 | 아니요 | S6의 model/messages/temperature 구조가 사실상 요청 본문 | S6 카드 제목을 “API 요청 본문”으로 표시한다. |
| API 응답 | 불충분 | ‘응답’은 반복되나 ‘API 응답’ 표기는 약함 | S5·S6 봉투 라벨을 “API 응답”으로 바꾼다. |
| 요청/응답 | 일부 | S5~S6 | 두 용어가 한 쌍의 통신 구조로 명시적으로 정리되지는 않는다. “API 요청 → 모델 처리 → API 응답” 도식을 둔다. |
| 모델 | 예 | S6 `model`, Solar Pro 3 설명 | `model` 필드가 “누구에게 시키나”로 설명된다. “요청을 처리할 모델을 지정하는 항목”으로 바꾸면 더 정확하다. |
| `messages` | 예 | S6 | 실제 중첩 구조가 제시된다. `messages`가 역할별 메시지 목록이라는 설명을 추가한다. |
| `system` 역할 | 예 | S6 | “개발자의 지시가 앉는 자리”로 설명한다. “시스템 메시지의 역할 표지”임을 보완한다. |
| `user` 역할 | 예 | S6 | “사용자 입력이 앉는 자리”로 설명한다. 실제로는 조립된 사용자 메시지가 들어간다는 점을 명시한다. |
| `content` | 예 | S6 | 응답에서 답 문장을 꺼내는 항목으로 제시된다. 문제없음. |
| `temperature` | 예 | S6 코드, S10 온도 선택 | 영문 필드와 온도 비유가 모두 나오며 “보장이 아니라 경향”도 명시한다. 활동지 B4에도 영문을 병기한다. |
| 토큰 | 예 | S6 | 토큰 수에 따라 요금을 계산한다고 설명한다. “입력 토큰과 출력 토큰”을 구분하면 더 정확하다. |
| 토큰 과금·사용량 기반 요금 | 일부 | S6 “요금은 토큰으로 센다” | 직관적이지만 정식 표현은 아니다. “입력·출력 토큰 사용량에 따라 요금이 계산된다”로 정의한다. |
| 입력 | 예 | S3 이후, S8·S10·활동지 B | 충분히 사용된다. 문제없음. |
| 출력 | 예 | S8·S10·활동지 B | 내용·형식·길이 등을 설계한다는 설명이 있다. 문제없음. |
| 입력 폼 | 일부 | S13 기술 명세, 화면에서는 입력 칸 | “입력 폼(UI)”을 한 번 병기할 수 있다. 필수 학습 용어까지는 아니다. |
| 출력 형식 | 예 | S10~S13 | 시스템 프롬프트의 구성 요소와 활동지 항목으로 반복된다. 문제없음. |
| 예외 처리 | 예 | S19 발문, 데모 명세 | S11~S15에서는 주로 ‘예외 한 줄’이라고 부른다. S11 라벨을 “[예외 처리]”로 바꾼다. |
| 경계값·누락 입력 | 아니요 | “아슬아슬 입력”으로만 등장 | S15에서 “경계·누락 입력”으로 교체한다. |
| 기능 테스트 | 아니요 | S15에서 ‘테스트’, ‘QA’만 사용 | 활동의 실제 명칭으로 “기능 테스트”를 제시한다. |
| QA(품질 보증) | 일부 | S15에서 “QA(출시 전 품질 검사)” | 정의가 지나치게 좁다. “품질 보증(QA)의 일부인 기능 테스트”로 관계를 바로잡는다. |

| 배포·공개 | 아니요 | 실제 활동에 포함되지 않음 | 학생이 하지 않는 행위이므로 억지로 추가할 필요는 없다. 다만 ‘출시’를 쓰지 않아야 한다. |

가장 큰 결함은 세 가지다. 첫째, `API 요청`과 `코드 생성 프롬프트`가 각각 ‘주문서’와 ‘제작 의뢰서’라는 비유적 문서명으로 공식 라벨화되어 있다. 둘째, API를 ‘뒷문’으로 부르면서 정식이고 약속된 접근 경로라는 개념과 한국어 관용 의미가 충돌한다. 셋째, ‘심장’ 비유가 시스템 프롬프트에서 프롬프트 전체와 입출력 설계까지 범위를 넓혀 일관된 개념 대응이 깨진다. 이 세 계열은 병기보다 교체가 필요하다.
