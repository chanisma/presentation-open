**판정: 제안 그대로는 채택하면 안 된다.** 제시된 수업 예제의 계산 결과는 재실행으로 재현할 수 있다. 하지만 “이 수업 범위에서는 언제나 정확하다”는 주장은 너무 강하다. 입력 이력, 출력 교체, 추적, 시간 제한, 자동 점검을 어떻게 결합하는지가 빠져 있으며, 구현에 따라 **14장의 입력 두 개부터 실패할 수 있다.**

아래 평가는 제공된 코드의 정적 검토와 공식 문서 확인에 근거한다. 실제 배포 사이트·브라우저에서 실행 검증하지 않았으며, 파일은 수정하지 않았다.

**1. 재실행은 중단·재개가 아니다**

대기열은 **소비하고 버리는 큐가 아니라, 이번 실행의 전체 입력 이력과 매 재실행마다 0으로 돌아가는 읽기 위치**여야 한다.

14장에서 첫 입력 `3`을 소비한 뒤 버리고, 두 번째 입력 `10000`만 넣어 다시 실행하면 `count`가 `10000`이 된다. 입력 기록은 `["3", "10000"]`으로 보존해야 한다. 빈 문자열 `""`도 정상 입력이므로 truthy 검사로 “입력 없음”을 판단하면 안 된다.

정확성을 깨는 사례는 다음과 같다.

```python
import random
price = random.randint(1000, 2000)
print("가격:", price)
count = int(input("몇 개? "))
print(price * count)
```

사용자가 본 가격과 최종 계산에 사용한 가격이 달라질 수 있다. 출력 전체를 갈아 끼워도 **사용자가 이미 읽고 판단한 정보**는 복구되지 않는다.

```python
import time
start = time.time()
input("잠시 기다렸다가 Enter: ")
print(time.time() - start)
```

재실행 시 `start`도 다시 설정되므로 실제로 기다린 시간을 측정하지 못한다.

```python
with open("visits.txt", "a") as f:
    f.write("방문\n")
name = input("이름: ")
```

입력받을 때마다 파일 쓰기가 반복된다. 현재 엔진은 `g`만 새로 만들며 Pyodide 파일시스템·임포트된 모듈·JS 상태는 초기화하지 않는다. 네트워크 요청이나 JS를 통한 외부 변경도 되돌릴 수 없다.

예외 방식은 더 근본적인 차이를 만든다.

```python
try:
    name = input("이름: ")
except Exception:
    name = "손님"
print(name)
```

특수 예외가 `Exception`의 하위 클래스면 학생 코드가 삼킨다. 입력 UI 없이 `"손님"`으로 완료될 수 있다.

`BaseException`을 직접 상속하면 `except Exception`은 피하지만, 다음 문제는 남는다.

```python
try:
    name = input("이름: ")
finally:
    print("종료 처리")
```

실제 입력 대기 중에는 실행되지 않을 `finally`가 실행된다. `except:`나 `except BaseException:`도 특수 예외를 잡는다. **예외 계층 선택만으로 일시 정지를 구현할 수 없다.**

| 사례 | 이번 수업에서의 중요도 |
|---|---|
| 입력 두 개의 이력 보존, 빈 입력, 출력 중복 | **즉시 문제.** 14장과 활동지에 직접 해당 |
| 입력 후 코드 편집·초기화·다시 실행 시 이력 폐기 | **즉시 문제.** 오래된 답이 새 코드에 들어갈 수 있음 |
| 동일한 안내 문구 반복 | 그 자체는 문제 없음. **안내 문구를 입력 식별자로 쓰면 문제** |
| 난수·시간·파일·외부 상태 | 정해진 예제에는 없음. 자유 코드 실행기의 지원 한계로는 명시해야 함 |
| `try`·`finally` | 이번 문법 범위 밖. 이번 예제의 실패 근거는 아니지만 범용 지원 주장은 불가 |
| 긴 계산·반복 | 정해진 예제에는 작음. 학생 오타·확장 코드·공유 워커에는 현실적인 문제 |

동일한 안내 문구는 다음처럼 호출 순번으로 처리하면 된다.

```python
a = input("값: ")
b = input("값: ")
```

반대로 난수나 외부 상태 때문에 실행 경로가 바뀌면, 순번도 다른 질문에 배정될 수 있다. 프롬프트 일치 검사는 일부 이상을 감지할 뿐 정확성을 보장하지 않는다.

입력이 `n`개이면 최종 실행까지 최대 `n+1`번 실행한다. 입력 앞의 비싼 계산도 반복된다. 각 시도마다 8초를 새로 주면 총 계산 시간이 늘어나고, 세션 전체에 8초를 주면 재실행 비용 때문에 정상 코드가 탈락한다.

**2. 현재 엔진에서 반드시 바뀌는 부분**

현재는 실행 중 `postMessage`로 입력을 보내도 동기 `runPython()`이 돌고 있어 워커의 메시지 처리기가 이를 받을 수 없다. 메시지 종류 하나를 추가하는 것으로 해결되지 않는다.

| 결합 지점 | 필요한 변경 |
|---|---|
| `__pyrun_exec(src, trace_on, max_steps)` | 입력 모드·시험 입력·입력 소비 기록을 받도록 확장 |
| `b['input'] = no_input` | 실제 입력 구현으로 교체. 프롬프트 문자열 변환, 빈 입력, EOF 정책 정의 |
| `except BaseException` | 재실행을 쓴다면 특수 예외를 **그보다 먼저** 별도 처리. 일반 오류로 반환하지 않기 |
| 반환 JSON | `completed`, `waiting_input`, `error`, `cancelled` 등을 구별. `error: null`만으로 성공 판정 금지 |
| `run()`의 `timeoutMs` | 계산 시간과 사용자 입력 대기 시간을 분리 |
| 페이지 공유 `chain` | 입력 대기 중 다른 실행기가 무기한 줄 서지 않게 소유권·취소 정책 정의 |
| `destroy()` | 대기 입력과 세션을 무효화하고 이전 워커의 늦은 응답 폐기 |
| 출력 수집·추적 | 실행 중 상한 적용, 입력 이벤트와 일반 출력 분리 |
| React 감싸개·웹 컴포넌트 | `inputs`, 입력 상태, 취소·초기화 API 및 이벤트 전달 |
| `explain.js` | 새 오류 규칙 추가. 기존 `no_input` 규칙은 구형 경로 제거와 함께 정리 |

특히 다음을 놓치기 쉽다.

- **입력 대기는 완료 이벤트가 아니다.** 현재 `pyrun-run` 소비자가 출력 저장·자동 점검을 실행한다면, 중간 대기 결과를 완성된 답으로 저장할 수 있다.
- **워커 재시작은 재개가 아니다.** 대기 중 워커를 종료했다면 “실행 취소됨”으로 처리해야 한다. 입력 이력만 가지고 조용히 복구하면 외부 상태 문제가 다시 생긴다.
- **입력 중 다른 실행기의 요청을 같은 Pyodide에 실행하면 안 된다.** JSPI로 이벤트 루프가 열리더라도 Python 런타임 재진입을 허용하는 설계로 만들면 안 된다.
- **`inputs`는 문자열 배열을 기본 API로 삼아야 한다.** 줄 구분 속성은 편의 문법으로만 제공한다. 빈 목록 `[]`과 빈 문자열 한 개 `[""]`, 마지막 빈 줄을 구분해야 한다.

추적에도 별도 수정이 필요하다. 현재 `settrace`의 `line` 이벤트는 **그 줄 실행 전 상태**를 저장한다. 따라서 첫 `input` 줄의 스냅샷에는 아직 `count`가 없고, 다음 줄의 스냅샷에 `"2"`가 있다. UI가 이를 “첫 줄 실행 후”로 보여 주는지 확인해야 한다.

재실행 방식에서 특수 예외로 중단했는데 현재 코드처럼 마지막 `line: None` 스냅샷을 붙이면, **입력 대기를 프로그램 종료로 표시**할 수 있다. 대기와 종료를 구별해야 한다.

“먼저 입력을 다 받은 뒤 추적”도 공짜가 아니다. 입력 질문 자체가 앞선 계산·입력 결과에 의존할 수 있으므로 보통 코드를 한 번 실행해야 한다. 이후 추적을 위해 다시 실행하면 같은 재실행 한계가 남는다. **8장처럼 입력이 `["2"]`로 고정된 예제는 처음부터 그것을 주고 한 번 추적하면 된다.**

**3. 대안의 2026년 기준 판정**

| 방식 | 판정 | 핵심 위험 |
|---|---|---|
| 재실행 | 제한된 결정적 예제에서는 가능 | 실행 의미 변경, 부작용 반복, 예외·출력·시간 처리 복잡 |
| Worker + SAB·`Atomics.wait` | 실제 중단·재개가 가능한 성숙한 선택지 | 문서 격리와 iframe·리소스 배포 제약 |
| `setStdin` 단독 | 시험 입력에는 적합. 대화형 비동기 입력 해결책은 아님 | 동기 콜백에 Promise를 반환하는 것만으로 대기 불가 |
| 서비스 워커 + 동기 XHR | 구현 사례가 있는 우회 방법 | 제어 범위·수명·업데이트·취소 복잡성 |
| 메인 스레드 + `window.prompt` | 기술적으로 간단하지만 이 실행기에는 부적합 | UI 정지, 8초 종료 장치 상실, 모달 제한 |
| Worker + JSPI | **지원 브라우저를 정할 수 있다면 우선 검토할 방식** | Pyodide 이전과 브라우저 지원 확인 필요 |

**SAB에 관한 계획서의 전제는 수정해야 한다.** COOP·COEP를 사이트 전체에 붙일 필요는 없다. Netlify는 URL 경로별 헤더를 지원하므로 독립 활동지 HTML에만 적용할 수 있다. 다만 `/assets/pyrun/*.js`에 헤더를 붙이는 것만으로 그것을 읽는 덱 문서가 격리되지는 않는다. **실행기를 포함하는 문서와 필요한 프레임 체인**이 조건을 충족해야 한다. [Netlify 경로별 헤더 문서](https://docs.netlify.com/manage/routing/headers/)

일반적인 구성은 HTTPS에서 문서에 `COOP: same-origin`, `COEP: require-corp`를 적용하고, 실제 `crossOriginIsolated`를 확인하는 것이다. 비격리 덱 안 iframe에 실행기 HTML만 격리 헤더를 준다고 SAB가 사용 가능해지는 것은 아니다. [공유 메모리 요건](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)

배포 영향은 다음처럼 구분해야 한다.

- **독립 활동지:** 경로를 제한해 적용할 수 있다. 다른 페이지까지 반드시 영향을 받는 것은 아니다.
- **덱의 레거시 iframe·학생 미러:** 격리된 상위 문서의 COEP 요구 때문에 임베딩이 막힐 수 있다. 다른 출처의 미러는 상대 서버 설정과 권한까지 확인해야 한다.
- **같은 SPA URL의 덱:** `?deck=...`나 해시만 다르다면 경로별 헤더로 특정 덱만 분리하기 어렵다. 별도 문서 경로가 필요할 수 있다.
- **jsDelivr:** 외부 CDN이라는 이유만으로 무조건 차단되지는 않는다. 요청 모드와 CORS/CORP 응답이 관건이다. 현재 사용하는 `pyodide.js`, Wasm, 패키지 각각을 실제 배포에서 검사해야 한다.
- **COOP:** 새 탭·팝업과의 `window.opener` 관계에도 영향을 줄 수 있다.

COEP는 교차 출처 리소스와 프레임에 조건을 부과한다. `credentialless`도 만능 우회책은 아니며 인증·저장 상태와 브라우저 지원을 별도로 고려해야 한다. [COEP 동작](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Embedder-Policy), [credentialless iframe 제약](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/IFrame_credentialless)

SAB 구현에서는 메인 스레드가 UTF-8 입력과 상태를 공유 버퍼에 쓴 뒤 `Atomics.notify`하고, 워커가 `Atomics.wait`에서 깨어난다. 기다리는 워커의 일반 메시지 처리기에 입력 전달을 맡기면 안 된다. 한글은 글자 수와 바이트 수가 다르므로 버퍼 길이·초과 입력·취소 플래그도 필요하다.

**`setStdin`은 전송 방식이 아니다.** 공식 API는 문자열·바이트·EOF 등을 반환하는 동기 핸들러다. 시험 입력 배열에는 적합하지만 Promise를 반환하는 콜백만 넣어서는 기존 동기 Python 호출을 기다리게 만들 수 없다. SAB나 JSPI 같은 대기 수단과 결합해야 한다. 현재의 `b['input'] = no_input`도 제거해야 해당 경로가 사용된다. [Pyodide 표준 입력 문서](https://pyodide.org/en/stable/usage/streams.html)

**서비스 워커 방식은 가능하지만 운영 부담이 크다.** 전용 워커가 동기 XHR을 보내고, 서비스 워커가 그 요청을 잡아 메인 페이지의 입력이 올 때까지 응답을 보류한다. 서비스 워커 내부에서 동기 XHR을 실행하는 방식과는 다르다. 교육용 Papyros에도 이 경로의 구현 사례가 있다. [Papyros 입력 전송 구현 기록](https://github.com/dodona-edu/papyros/issues/1081)

다만 현재 Blob 워커의 요청이 의도한 서비스 워커에 잡히는지, 최초 방문에 제어가 확보되는지, 탭 종료·서비스 워커 교체·장시간 대기에서 어떻게 실패하는지는 검증해야 한다. 서비스 워커의 기본 범위가 `/assets/pyrun/`이면 다른 경로의 활동지까지 자동으로 제어하지 않는다. 기존 오프라인 서비스 워커와의 충돌도 생길 수 있다. 이번 수업을 위해 새로 도입하기에는 복잡하다.

**메인 스레드의 `window.prompt`는 권하지 않는다.** 동기 입력은 가능하지만 Python 무한 루프가 UI와 타이머까지 막는다. 지금의 `worker.terminate()`에 해당하는 안전장치를 잃는다. `runPythonAsync()`라는 이름만으로 CPU 계산이 메인 스레드 밖으로 옮겨지지도 않는다. iframe·백그라운드 탭의 모달 제한과 요구한 인라인 입력 UI도 맞지 않는다.

**JSPI는 이미 실제 선택지다.** Pyodide 공식 발표는 0.27.7에서 JSPI를 지원하며 Chrome 137에서 사용할 수 있다고 설명한다. `pyodide.ffi.run_sync()`로 입력 응답 Promise를 기다리고, JS에서는 `runPythonAsync()` 또는 `callPromising()`으로 진입해야 한다. 현재의 동기 `runPython()` 진입으로는 stack switching이 비활성화된다. [Pyodide JSPI 지원 설명](https://blog.pyodide.org/posts/jspi/)

따라서 “최신 Pyodide로 바꾸면 `async stdin`이 자동 지원된다”는 결론도 틀리다. 입력 브리지와 비동기 진입 경로를 구현해야 한다. **2026년 11월의 모든 Firefox·Safari 및 학교 관리 브라우저에서 기본 활성화됐는지는 이번 확인으로 확정하지 못했다.** 기능 검사와 학교 기기 검증이 필요하다.

또 최신 안정판 문서는 **module worker가 필요하며 classic worker의 `importScripts()`는 지원하지 않는다**고 명시한다. 최신판 이전은 CDN 버전 문자열만 바꾸는 작업이 아니다. [현재 워커 구동 문서](https://pyodide.org/en/stable/usage/webworker.html)

**4. 자동 점검은 대화형 실행과 분리해야 한다**

시험 실행에서 입력이 부족하면 **추가 입력 UI를 열지 말고 즉시 “시험 입력 부족”으로 종료**해야 한다. EOF로 전달한다면 `EOFError` 처리와 별개로 입력 소진 사실을 기록해야 한다. 학생 코드가 EOF를 잡는 경우도 있기 때문이다.

반대로 입력이 남는 경우는 과제 정책을 정해야 한다. 예컨대 입력 두 개가 필수인 과제에서 하나만 소비했으면, 오류 없이 종료했어도 조건을 만족하지 않는다. 다음 정보가 필요하다.

- 제공한 입력 수와 실제 소비한 입력 수
- 입력 부족 여부
- 정상 완료·오류·시간 초과·취소 여부
- 출력 생략 여부

AST의 `calls['input']`은 **소스에 적힌 호출 수**다. 실행 중 호출 횟수가 아니다. 주석을 문자열 검색하는 것보다는 낫지만, 반복·함수·분기·별칭에는 실제 호출 수와 달라진다.

6번의 “모든 입력에 10”도 무제한 공급하면 안 된다.

```python
while input("끝내려면 0: ") != "0":
    pass
```

계속 `10`을 공급하면 끝나지 않는다. 입력 공급 횟수 상한과 계산 시간 제한을 모두 두고, 실패를 정답 오류와 구분해야 한다. 자유 주제는 구조 요건과 실행 결과를 나눠 표시하고, 학생이 대표 시험 입력을 정하게 하는 편이 낫다. 문자 입력 프로그램은 `10`도 정상 문자열로 받으므로 **ValueError 유무로 문자 입력 프로그램을 판별할 수 없다.**

채점 조건에도 직접적인 허점이 있다.

- **입력 에코가 출력에 섞이면 1번은 인사하지 않아도 `"테스트"`가 보여 통과할 수 있다.**
- `"70"` 포함 검사는 `170`, `700`, 안내 문구의 `70`도 통과시킨다.
- 3번의 `"18"`, `"65.5"`도 안내 문구나 상수 출력으로 충족할 수 있다.
- **5번의 두 시험은 몫과 나머지가 모두 `(3, 2)`다.** 상수 출력이 두 시험을 모두 통과한다. 결과가 달라지는 시험을 추가해야 한다.
- 시험 결과가 학생의 마지막 수동 실행 출력·입력 이력을 덮어쓰면 제출 기록이 혼동된다.

**프로그램 stdout, 안내 문구, 입력 에코를 별도 채널로 보존**하고, 채점에는 프로그램 출력만 사용해야 한다. 숫자는 단순 부분 문자열보다 명시한 출력 형식이나 숫자 토큰으로 비교해야 한다.

**5. 키·IME·출력 제한은 별도 실패 지점이다**

Shadow DOM은 키보드 이벤트를 자동 격리하지 않는다. 덱의 캡처 단계 리스너는 자식이 `stopPropagation()`하기 전에 실행될 수 있다. 덱 쪽에서도 `event.composedPath()`로 실행기 내부 입력인지 확인하고 슬라이드 단축키를 무시해야 한다.

입력 줄에서는 다음 동작을 검증해야 한다.

- 조합 중 Enter는 제출하지 않기: `isComposing`과 조합 시작·종료 상태 확인
- 한글 확정 Enter와 제출 Enter의 중복 처리 방지
- 키 반복으로 같은 입력 두 번 전송 방지
- 화살표·Space·PageDown·Ctrl+Enter가 덱으로 새지 않기
- 제출 후 입력 잠금, 초기화 후 늦은 입력 폐기
- 학생 입력과 출력은 `innerHTML`이 아닌 텍스트로 렌더링

**현재 출력 제한은 메모리 제한이 아니다.**

```python
'out': out.getvalue()[:8000]
```

이는 실행이 끝난 뒤 반환 문자열만 자른다. `StringIO`에는 이미 전체 출력이 쌓인다. 또한 `snap()`은 매번 전체 `out.getvalue()`를 저장하므로 추적 결과는 별도로 커진다. 2만 자 제한으로 숫자만 바꿔도 이 문제는 남는다.

제한된 writer를 사용해 **쓰기 시점에 보존량을 제한**하고, 이후 출력은 버리거나 별도 실행 중단 정책을 적용해야 한다. 출력 생략과 추적 단계 생략은 다른 상태로 보고해야 한다. 추적에는 출력 전체 사본 대신 누적 길이·증분을 저장하는 방식도 고려할 만하다.

5장의 3000자는 현대 브라우저에서 보통 큰 부담이 아니다. **3000자 자체를 성능 결함이라고 볼 근거는 없다.** 다만 다음 구현은 피해야 한다.

- 글자마다 DOM 노드를 만드는 출력
- 문자 하나마다 React 렌더·스크롤·높이 측정을 반복
- 숫자 사이 공백이 없는데 일반 줄바꿈만 설정

텍스트 노드와 `white-space: pre-wrap; overflow-wrap: anywhere`를 사용하고 출력 영역 높이·스크롤을 제한하면 된다. 3000자는 현재 8000자 반환 상한에도 들어간다.

**6. 지난 자료는 `input()`이 없어도 깨질 수 있다**

“지난 자료에는 input이 없으므로 영향이 없다”는 근거는 부족하다. 같은 엔진·컴포넌트·출력 포맷을 바꾸기 때문이다.

- `num`을 `int`·`float`로 분리하면 기존 변수 카드의 CSS·분기·스냅샷이 깨질 수 있다.
- 새 대기 이벤트나 결과 상태가 기존 `pyrun-run` 저장·점검 코드를 바꿀 수 있다.
- Pyodide 이전으로 Python 버전·오류 문구·패키지·워커 로딩이 달라진다.
- 공통 헤더 변경은 입력 없는 덱의 iframe도 막을 수 있다.
- 입력 취소가 공유 워커를 종료하면 다른 실행기의 작업도 영향을 받는다.
- 입력 UI용 Enter 처리가 기존 코드 편집기의 Enter·Ctrl+Enter를 가로챌 수 있다.

구형 덱은 기존 런타임과 결과 계약을 유지하고, 새 실행기를 명시적으로 선택하게 하는 편이 회귀 범위를 줄인다.

**권고: 새 수업에는 별도 버전의 Worker + JSPI 입력 브리지를 사용한다.**

이유는 실행 스택을 실제로 보존하므로 재실행의 예외·부작용·시간 문제를 피하고, COOP·COEP나 서비스 워커를 새로 도입하지 않아도 되기 때문이다. 단, **학교 브라우저 지원 확인을 출시 조건으로 삼아야 한다.** 지원되지 않는 기기에서 조용히 재실행으로 바꾸면 기기마다 Python 의미가 달라진다. 지원 안내와 입력 사전 제공 모드를 명시적으로 제공하는 편이 낫다.

구현 순서는 다음이 적절하다.

1. **학교 기기에서 JSPI 최소 실험:** 입력 두 개, 한글, 취소, 입력 전후 무한 루프, 입력 없는 코드를 확인한다.
2. **새 런타임 버전 고정:** 해당 버전의 워커 로딩 방식과 Python 버전을 정하고 기존 엔진을 유지한다.
3. **실행 프로토콜 정의:** 세션·실행·입력 요청 ID, 상태, 취소, 입력 소비 기록, 계산 시간과 대기 시간을 구현한다.
4. **입력 브리지 구현:** 비동기 Python 진입과 `run_sync()`를 결합하고, 기다리는 런타임에 다른 작업이 재진입하지 않도록 한다.
5. **출력·시험 실행 분리:** 출력 상한을 쓰기 시점에 적용하고, 시험 입력 소진·남음·공급 횟수 제한과 채점 조건을 고친다.
6. **추적·UI 결합:** 8장의 미리 넣은 입력, 줄 실행 전후 표시, 키 격리, IME, 초기화·늦은 응답을 검증한다.
7. **회귀 검증:** 지난 덱·활동지의 실행·단계 이동·자동 점검·저장·lazy 동작과 새 수업 전체를 확인한다.

계획서에서는 우선 **“SAB는 사이트 전체 헤더가 필요하다”**, **“수업 범위에서는 언제나 정확하다”**, **“지난 자료는 input이 없어 영향이 없다”**라는 세 문장을 수정해야 한다.
