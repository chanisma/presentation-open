너는 브라우저 안 파이썬 실행 환경(Pyodide, Web Worker)을 만들어 본 프런트엔드 엔지니어다. <stdin>은 고등학교 파이썬 수업 덱 계획서와, 이미 만들어 둔 교육용 실행기 부품의 README와 엔진 코드다. 계획서의 「코드 실행기 확장 설계 (input() 지원)」 절이 검증 대상이다.

과제: 제안된 '다시 실행' 방식(input 대기열이 비면 특수 예외로 멈추고, 사용자가 입력하면 대기열에 더해 처음부터 다시 실행)의 결함을 공격하라.
반드시 다루어야 할 관점.
1. 정확성 — 다시 실행 방식이 깨지는 코드(무작위·시간·외부 상태, 실행 시간이 긴 코드, 같은 프롬프트가 반복되는 경우, 사용자가 예외를 try로 잡는 경우 except Exception이 특수 예외를 삼키는 문제 등). 수업 범위에서 실제로 문제가 되는 것과 아닌 것을 나눠라.
2. 현재 엔진 코드(settrace 기반 한 줄씩 보기, 시간 제한, 워커 재시작, no_input 규칙)와의 결합 지점 — 구체적으로 어느 부분을 바꿔야 하는가.
3. 대안 비교: SharedArrayBuffer + Atomics.wait(COOP/COEP 필요, Netlify 헤더로 /assets/pyrun 경로나 활동지 페이지에만 줄 수 있는가, 덱 iframe·학생 미러·jsdelivr CDN 로딩에 미치는 영향), Pyodide의 setStdin, 서비스 워커로 동기 XHR 가로채기 방식, 메인 스레드에서 Pyodide 실행 + window.prompt, JSPI(WebAssembly stack switching)·Pyodide 최신 버전의 비동기 input 지원. 각각의 실현성·위험을 2026년 기준으로 판정하라(확실하지 않으면 확실하지 않다고 써라).
4. 자동 점검을 시험 입력으로 실행하는 설계의 허점(입력 개수 불일치, 학생 코드가 input을 더 많이 부를 때, 무한 대기).
5. 덱 안 키 격리, 한글 IME, 출력 2만 자 상한, 5장의 3000자 줄 렌더 성능.
6. 지난 수업 자료(input 없음)를 깨뜨릴 위험.
마지막에 권고 방식 하나와 그 이유, 구현 순서를 제시하라.
출력은 한국어 마크다운으로. 칭찬은 최소한으로 하고 결함 위주로 써라. 문제가 없으면 없다고 쓰고 억지로 만들지 마라. 파일을 절대 수정하지 마라.
