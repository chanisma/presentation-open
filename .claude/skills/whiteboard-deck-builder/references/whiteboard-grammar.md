# Whiteboard Grammar — 판서 문법 상세 (슬라이드덱판)

newVideoGen `/vg-whiteboard` v2.8(rough-kit)의 문법을 이 저장소 매체로 옮긴 것.
레퍼런스 구현: `data/dev/테스트 수업 자료/화이트보드-샘플/deck.tsx` (`?deck=whiteboard-demo`).

## 0. 매체 변환 — 영상 문법을 슬라이드로 옮길 때 바뀌는 것

| 영상(vg-whiteboard) | 슬라이드덱(이 스킬) |
|---|---|
| 잉크 길이 비례 자동 시간 배분 | 요소마다 `at`·`dur`을 직접 준다(교사가 말할 시간을 안다) |
| 가라오케 알약 자막(SRT) | `<Caption>` 한 줄 — 그 장의 결론 문장 |
| Fluent 3D 쓰는 손 PNG | 생성 두들 손 (`wb-write-hand.png`) — 톤이 판서와 같아야 한다 |
| rough.js 라이브러리 | **의존성 0** 내장 생성기 (`line/rect/rrect/ellipse/poly`) |
| 씬당 실스티커 ≥ 2 | 슬라이드당 스티커 ≥ 1 (덱은 장수가 적다) |
| — | `<Build>` 축: 정리·정의는 클릭으로 |

## 1. 그리는 순서가 곧 설명의 순서

`at`은 "이때 내가 이 말을 한다"의 시각이다. 판서에서 순서를 바꾸면 설명이 무너지듯,
`at` 순서는 대본이다. 저작 전 슬라이드마다 draw order 한 줄을 먼저 적는다.

- 간격 **0.4~0.9초**. 두 획이 동시에 시작하면 "그려지는 중"이 안 읽힌다.
- 한 슬라이드 총 6~9초. 그보다 길면 학생이 기다린다 — 슬라이드를 쪼갠다.
- 제목 → 주요 오브젝트 → 관계선 → 라벨 → **빨간 주석** → 캡션이 기본 리듬이다.
  (주석이 먼저 나오면 판정이 설명을 앞지른다)

## 2. rough 생성기 — seed는 의미가 있다

```tsx
<Draw d={rect(120, 300, 420, 260, 41)} at={1.2} dur={0.7} fill={BLUE} />
<Draw d={pict.arrow(560, 430, 700, 430, 43)} at={2.0} dur={0.4} color={GRAY} />
```

- **seed는 반드시 다르게** — 같은 시드로 인접 도형을 그리면 같은 흔들림이 복사돼 티가 난다.
- `rough`(흔들림)는 기본 1.8. 강조·주석은 2.6~3.4로 거칠게, 정보 도형은 1.4~2.0.
- `passes`는 기본 2(같은 선을 두 번). 주석·취소선은 `passes: 1`이 더 날카롭다.
- `fill`은 획이 끝난 뒤 차오른다(`fillAt`으로 조정). 채색이 선보다 먼저 나오면 안 된다.

## 3. 픽토그램 — 조합은 자유, 구도 복제 금지

`pict.*`는 **알파벳**이지 템플릿이 아니다. 같은 조합(browser + arrow + docFile)을 세 장
연속 쓰면 위반이다. 알파벳을 섞어 매 장 다른 그림을 만든다.

인물·생물·복잡한 사물은 픽토그램으로 흉내내지 마라 — **생성 스티커**(image-asset-builder).
원+막대 졸라맨은 newVideoGen에서 두 번 낙제한 실패다.

## 4. 스티커 — 팝이 아니라 스케치 리빌

`<Sticker>`는 톱니 경계가 위에서 아래로 쓸리며 등장한다(킷 기본). 화이트보드의 정체성은
"한 획씩 그려지는 것"이라, 완성본이 한 번에 나타나면 이 문법이 아니다.

- `h`는 반드시 크롭 원본 비율로: `h = w / ar`. 비율표는 `_crop-meta.json`에 있다.
- 크기 위계: dominant 세로 380~520(1600×900 좌표) · 조연 220~320 · 소품 120~200.
- 슬라이드당 스티커 1~3개. 4개를 넘으면 판서가 아니라 콜라주가 된다(그건 vox의 몫).

## 5. 손글씨 `<Write>`

- `cps` 10~14가 자연스럽다. 20을 넘으면 타이핑처럼 보이고, 8 미만이면 답답하다.
- `font`: `gaegu`(한글 기본·볼드 지원) · `pen`(얇은 손글씨, 주석용) · `caveat`(라틴 전용).
- 긴 문장은 `<Write>` 여러 줄로 나눠 각각 `at`을 주는 편이 자연스럽다(줄바꿈 미지원).
- 글자별 지터는 `seed`로 결정된다 — 같은 자리에 같은 문장을 두 번 쓰면 시드를 바꿔라.

## 6. 빨강은 판정이다

빨강(`RED`)은 **주석·강조 전용**: `circleAround` · `underline` · `zigzag` 취소선 ·
`cross` · `curveArrow` 스우시 · 짧은 빨간 손글씨. 슬라이드당 1~2개.
본문 선·채색에 빨강을 쓰면 판정의 힘이 사라진다.

## 7. 쓰는 손

`<Board handSrc={HAND}>`만 주면 킷이 활성 획의 끝점을 `getPointAtLength`로 추적해
펜촉을 정렬한다. 손 이미지의 펜촉 위치가 다르면 `handTip={[x비율, y비율]}`로 보정.

- 손은 **획이 그려지는 동안에만** 보인다(Write·Sticker 구간에는 없다 — 정상).
- 손을 끄려면 `handSrc`를 주지 않으면 된다.

## 함정 (검수에서 실제로 터진 것들)

1. **컨텍스트를 매 프레임 새로 만들면 손이 죽는다** — Board는 t로 매 프레임 리렌더되므로
   Provider value를 ref에 고정해야 한다(자식 effect가 매 프레임 재실행되며 등록이 리셋됨).
   킷은 고정돼 있으니 킷을 고칠 때만 주의.
2. **`ellipse`를 직선 세그먼트로 이으면 다각형처럼 보인다** — 킷은 중점 이음 2차 베지어로
   그린다. 직접 도형을 만들 때도 같은 방식을 쓸 것.
3. **생각 풍선 안에 글자를 넣으면 그림과 겹친다** — 풍선 안은 그림, 글자는 풍선 밖.
4. **캡션 알약이 덱 크롬과 겹친다** — 기본 y=800(1600×900 기준)이 안전선. 그 아래로 내리지 마라.
5. **캡처 t와 씬 t의 어긋남** — 1쪽은 페이지 로드 시각과 씬 시작이 다르다. 캡처 스크립트가
   2쪽에서 ←로 진입해 t0를 맞춘다(수정 완료). 직접 확인할 때도 이 방식을 쓸 것.

## 자가 점검 (슬라이드마다)

1. 그리는 순서가 설명 순서와 같은가?
2. 스티커가 1개 이상 있고, 비율이 원본과 같은가?
3. 빨강이 주석에만 쓰였고 1~2개인가?
4. 인접 도형의 seed가 다른가?
5. 중간 시각(그리는 중) 캡처에서 손이 획 끝에 붙어 있나?
6. 직전 슬라이드와 구도가 다른가?
