# Lesson Deck Planner — 덱 기획 (파이프라인 앞단)

> 이 스킬은 **기획만** 한다. 슬라이드를 저작하지 않는다 — 산출물은
> `data/<그룹>/<과목>/<수업>/plan.md` 하나이고, 저작은 렌더러 스킬로 디스패치한다.
> (newVideoGen video-gen의 얇은 라우터 원칙: 하류 로직을 여기에 복제하지 않는다)

## 디자인 철학 (최우선 — newVideoGen 이식)

> **이 덱의 적은 "무난함"이다.** AI가 만드는 슬라이드는 통계적 평균으로
> 수렴해 단조로워진다. 목표는 "AI가 만든 것 같지 않은 수업 자료".
> **매 슬라이드·매 요소는 존재 이유를 증명해야 한다** — 천 번의 NO에 단
> 한 번의 YES. 빈 공간을 필러(장식 아이콘·뻔한 수치·의미 없는 카드)로
> 채우는 것은 패배 선언이다. 비어 보이면 구도를 다시 짠다.

기획 단계에서의 적용:

- **같은 구도 반복 금지** — form 다양성 게이트(3연속 금지)는 최소선이고,
같은 form이라도 슬라이드마다 구도·메타포가 달라야 한다.
- **비대칭이 기본** — 균등 분할·전부 중앙정렬 슬라이드를 계획하지 않는다.
dominant 하나 + secondaries.
- **핵심 메시지가 없는 장은 삭제 후보** — "요소는 증명 책임을 진다"의
슬라이드판.
- **비유는 정식 용어를 대체하지 못한다** — 화면 라벨·정의 문장·활동지 칸
이름·문항 선지 자리에는 정식 용어를 계획한다. 상세는 ④의 '용어 규율'.
- **설명은 듣는 사람에 맞춘다** — 어휘·비유·깊이·어조를 청중(기본값은
고등학생)에 맞게 보정하는 `eli5` 스킬이 이 저장소의 기본 설명 방식이다.
plan.md의 「ELI5 적용 원칙」 절은 필수이고 검증 게이트 10번이 점검한다.
- 씬(scene form) 저작 규칙 상세는 `.claude/rules/scene-grammar.md`
(렌더러가 필독) — 기획자는 메타포 고유성만 보장하면 된다.

```
소재(주제·ODP·PDF·기존 덱·images/)
   │
   ▼
[lesson-deck-planner]  ← 이 스킬
   ① 소재 분석  ② 아크 설계  ③ 슬라이드별 형태(form) 결정
   ④ plan.md 작성  ⑤ 검증 게이트  ⑥ 렌더러 디스패치
   │
   ▼ plan.md
react-deck-builder │ dynamic-scene-builder │ notebooklm-lesson-deck │ composite-deck-builder
   (+ live-quiz-builder, activity-sheet-builder 부가)
```

## ① 소재 분석

- 학습 목표(1~3개), 대상(학년·과목). **차시와 수업 시간은 사용자가 따로
  언급하지 않는 한 고려하지 않는다** — 아래 「차시와 시간은 계획의 변수가
  아니다」 절 참조
- 기존 자산 조사: `**assets/manifest.json`을 tags·alt·style로 검색**(asset-library
스킬의 레지스트리) + `data/<그룹>/<과목>/<수업>/images/` — 재사용 단위는 페이지가
아니라 자산(이미지·SVG)
- ⚠ 이미지 재사용은 **스타일 보수 원칙** 준수: 같은 set 최우선, 같은 style만
허용, 다른 style은 내용이 맞아도 금지 (asset-library SKILL 참조). 한 덱의
image form은 한 세트/한 스타일로 통일하고 plan.md 헤더에 set·style 명시.
- 수업 유형: 개념 수업 / 실습 수업 / 프로젝트·오리엔테이션 / 안내·홍보

### 차시와 시간은 계획의 변수가 아니다 (2026-09-15 사용자 결정)

사용자가 차시나 수업 시간을 따로 언급하지 않는 한, 계획자는 **차시와 시간을
고려하지 않는다.** 헤더에 차시 행을 두지 않고, 시간 배분을 적지 않으며, "몇
차시가 필요하다"거나 "시간이 모자란다"고 판정하거나 알리지도 않는다. 덱은
소재가 요구하는 장면을 전부 담은 하나의 자료이고, 그것을 몇 번의 수업에 걸쳐
어디까지 진행할지는 교사가 수업 현장에서 정한다. 시간 계산이 앞서면 계획은
언제나 내용을 잘라 맞추거나 차시를 쪼개는 쪽으로 기운다 — 둘 다 계획자의 일이
아니다. (같은 날 앞선 세션에서 "시간은 가늠하되 내용을 깎는 자로 쓰지 않는다"로
정했던 것을, 이 세션에서 "차시 자체를 고려하지 않는다"로 한 번 더 좁혔다 —
계획자가 "2차시 권장"을 헤더에 적어 보낸 것이 계기다.)

- **장수 목표를 세우지 않는다.** "1차시 13장"처럼 미리 정한 숫자에 맞추려고
  장을 합치거나 빼지 않는다. 필요한 장면 수는 소재가 정한다.
- **줄일 것은 장수가 아니라 한 장의 밀도다.** 설명에 필요한 맥락은 **압축**할 수
  있지만 **제외하지 않는다.** 한 장에 문장이 많으면 문장을 줄이는 것이지,
  그 장을 없애는 것이 아니다.
- **다리를 빼면 수업이 튄다.** 개념 A에서 개념 B로 넘어갈 때 학생이 아직 모르는
  것이 끼어 있으면 그 사이에 장이 하나 더 필요하다. 이 저장소의 한 덱은
  「규칙 기반 → 퍼셉트론 → 딥러닝」을 각 한 장씩 이어 붙였다가 "연결이 빈약하다,
  갑작스럽다"는 지적을 받았다(2026-09-15). 사이에 「규칙을 데이터에서 찾게 하자」와
  「하나로는 못 가른다, 층을 쌓는다」를 넣자 22장이 되었고 그것이 맞는 분량이었다.
- **사용자가 차시·시간을 언급했을 때만** 그 조건을 헤더에 적고 흐름 근거에
  반영한다. 그때도 내용을 빼서 맞추지 않는다 — 맞지 않으면 사용자에게 알리고,
  범위를 줄일지 차시를 늘릴지는 교사가 정한다.

### 덱인가 모형인가 (소재 분석 마지막 판별)

이 스킬은 덱을 기획하지만, **소재가 덱이 아니라 교구(3D 모형)를 요구하는 경우**가 있다.
아크를 짜기 전에 한 번 판별한다.


| 신호                                         | 산출물                         |
| ------------------------------------------ | --------------------------- |
| 설명할 것이 **순서**다 — 무엇을 어떤 차례로 이해시킬 것인가       | 덱 (이 스킬 계속)                 |
| 설명할 것이 **관계**다 — 이 값을 바꾸면 저것이 어떻게 되는가      | **모형** (`3d-model-builder`) |
| 학생이 볼 것이 슬라이드다                             | 덱                           |
| 학생이 **돌릴 손잡이**가 있고, 돌리면 숫자와 그림이 함께 바뀐다     | **모형**                      |
| 사용자가 "모형", "시뮬레이터", "만져 보는", "조작하며" 라고 말했다 | **모형**                      |


모형으로 판별되면 plan.md를 쓰지 말고 사용자에게 알린 뒤 `3d-model-builder`로 넘긴다 —
"이건 슬라이드보다 조작하는 교구가 맞겠습니다"까지 한 줄로 말하고 확인받는다. 덱과 모형이
**둘 다** 필요하면(개념 설명 + 체감 교구) 모형을 먼저 만들어 검증한 뒤 덱에서 그 모형을
`model` form으로 부른다 — 아래 ③ 참조.

## ② 아크 설계

**사용자가 언급한 맥락(수업 의도·순서·강조점·대상)이 흐름과 구성을 결정한다 —
어떤 참고 아크보다 우선이다.** 사용자 언급에 공백이 있으면 고정 틀로 자동
회귀하지 말고, 교육학적 근거(선행 지식 활성화, 구체→추상 순서, 예제 후 연습,
인지부하 분산, 오개념 교정, 형성평가 배치 등)로 그 수업에 맞는 흐름을 직접
판단해 설계한다. 판단 근거는 plan.md 헤더의 `흐름 근거` 줄에 한 줄로 남긴다.

검증된 참고 아크 — 출발점으로만 쓰고 수업에 맞게 자르고 재배열한다 (상세:
`../notebooklm-lesson-deck/references/master-prompt-pattern.md` — NotebookLM
전용이 아니라 **모든 렌더러 공용**):

- 개념 수업: 도입(비유·흥미) → 기본 → 심화 → 도구 → 실전 연습 → 자주 하는
실수 → 마무리(실생활 적용 + 한눈 정리)
- 실습 수업: 목표 → 시연 → 따라하기 → 도전 과제 → 공유
- 안내·홍보: 후킹 → 내용 → CTA

(단계마다 몇 장을 쓸지는 적지 않는다 — 장수는 소재가 정한다. 2026-09-15 사용자 결정)

## ③ 슬라이드별 형태(form) 결정 — 이 스킬의 존재 이유

콘텐츠 성격이 형태를 고른다. 슬라이드마다 아래 루브릭으로 form을 확정한다:

| form | 언제 (콘텐츠 성격) | 렌더 수단 |
|---|---|---|
| `image` | 비유·정서·스토리 — 도입/마무리/전환. 손그림이 텍스트보다 힘셀 때 | NotebookLM 일러스트 (±KenBurns) |
| `scene` | **시간·흐름·순환·변화가 개념의 본질**일 때 (루프, 정렬, 전파, 신경망 순전파…) | 씬 타임라인 (t의 순수 함수) |
| `walkthrough` | **소프트웨어 절차를 순서대로 하는 방법** — 사이트 조작·설치·CLI 입력·앱 사용 ("○○ 설치", "△△에서 □□ 하기") | walkthrough 씬 — 창 목업+포인터+타이핑 (software-walkthrough-builder) |
| `diorama` | **사건·여정·역사·줄거리** — 누가 무엇을 했는가가 뼈대일 때 (인물·사건이 있는 서사) | 무대(생성 배경)+배우 스프라이트+오버레이 (diorama-deck-builder) |
| `whiteboard` | ⛔ **현재 사용하지 않는다** (2026-09-06 사용자 결정 — 아래 '사용 중지 form' 참조). 같은 내용은 `build`/`scene`/`image`로 계획한다 | (whiteboard-deck-builder — 보류) |
| `collage` | **여러 주체의 관계를 넓게 펼쳐** 훑을 때 — 사회·윤리·시사 이슈 | 넓은 종이 세계 + 카메라 여행 (vox-collage-deck-builder) |
| `watercolor` | ⛔ **현재 사용하지 않는다** (2026-09-06 사용자 결정 — 아래 '사용 중지 form' 참조). 정서·마무리 장은 `image`/`scene`/`static`으로 계획한다 | (watercolor-deck-builder — 보류) |
| `static` | 비교·목록·통계·코드·구조 — 정보 밀도가 주인공 | bolt 컴포넌트 (Split/StatGrid/Terminal/CodeWindow…) |
| `build` | static인데 **담화 순서가 중요**할 때 (하나씩 공개하며 설명) | static + `<Build at={n}>` |
| `activity` | 손을 움직이는 실습·제출 | 활동지 링크 (activity-sheet-builder) |
| `model` | **원리가 변수 조작으로만 체감**되는 핵심 장 — 값을 바꾸면 그림과 숫자가 함께 바뀌어야 이해된다 (확산 단계, 어텐션 가중치, 토큰화·벡터화, V8 엔진) | 별도 3D 모형 1편 + 덱에서 호출 (`3d-model-builder`) — 아래 규칙 |
| `film` | ⚠ **사용자가 명시적으로 요청했을 때만** — 아래 옵트인 게이트 참조 | 미리 구운 mp4 (film-deck-builder) |

게이트: **같은 form 3연속 금지**(전량 image인 NotebookLM 단일 덱은 예외 —
대신 비주얼 가이드가 장마다 달라야 함). scene은 장마다 **고유 메타포** 필수.

### ⚠ `film` 옵트인 게이트 (BLOCKING)

`film`은 **자동 선택 대상이 아니다.** 콘텐츠가 아무리 어울려 보여도
(모션이 무겁다·영상이면 예쁘겠다) 먼저 제안하지 마라. 이유는 환경 의존이다 —
영상 렌더는 **OpenMontage(remotion-composer)** 라는 외부 프로젝트가 있어야
하고, 그건 이 저장소의 일부가 아니라 특정 PC에만 있다. 계획에 넣었다가 렌더할
수 없으면 plan.md 전체가 막힌다.

두 조건을 **모두** 만족할 때만 `film`을 계획한다:

1. **사용자의 명시적 요청** — "영상으로", "필름 덱", "영상 만들어서",
 "OpenMontage로", "렌더한 영상으로" 등 사용자가 영상 렌더를 직접 언급.
 *"움직이게 해줘"·"모션 넣어줘"는 해당하지 않는다* — 그건 `scene`이다.
2. **환경 확인** — 계획 확정 전 OpenMontage 존재를 실제로 확인:
  ```bash
   ls "C:/Users/User/orca/projects/creative_works/OpenMontage/remotion-composer/src/Root.tsx"
  ```

   없으면 사용자에게 **알리고 대체안으로 계획한다**(아래 강등 표).

**강등(fallback) 규칙** — `film`은 새 문법이 아니라 기존 문법의 *렌더 수단*이다.
그래서 영상이 불가능해도 같은 계획을 React 렌더러로 그대로 살릴 수 있다:


| 영상에 실으려던 문법 | 강등 대상 form                           |
| ----------- | ------------------------------------ |
| 콜라주 영상      | `collage` (vox-collage-deck-builder) |
| 디오라마 영상     | `diorama` (diorama-deck-builder)     |
| 화이트보드 영상    | `scene` (whiteboard는 현재 사용 중지)  |
| 그 외 모션      | `scene`                              |


즉 plan.md의 **내용·아크·장면 설계는 그대로 두고 form 라인만 바꾸면 된다.**
이 강등 가능성을 염두에 두고, film 블록도 원래 문법의 계획 문법(무대·배우·
카메라 등)을 함께 적어 둔다.

`film`을 계획할 때의 추가 규칙 (film-deck-builder 절대 원칙):

- **한 페이지 = 영상 1편 = 3장면(4.5초×3).** 다른 영상이 필요하면 다른 슬라이드.
- **스텝 진행 UI를 계획하지 않는다** — 스텝은 영상 안에서 자연스럽게 이어지는
단계다. 우상단 ①②③ 칩 같은 인디케이터는 두지 않는다.
- 영상과 **역할이 다른** 텍스트(수업 제목·교사 설명)가 필요하면
`page text:` 라인으로 명시 — 영상 상단 24%를 비우는 계약이 따라온다.

### `model` 규칙 — 슬라이드 한 장이 아니라 자료 한 편

`model`은 **덱 안의 슬라이드가 아니라 별도의 자기완결 HTML 자료**다(허브에 `type: doc`으로
따로 등록된다). 계획할 때 다음을 지킨다.

1. **비용을 슬라이드로 세지 마라.** 모형 한 편은 덱 한 편에 준하는 작업이다. 한 수업에
 `model`은 **최대 1개**, 그 수업의 핵심 원리에만 쓴다. 두 개가 필요해 보이면 하나는
 `scene`으로 강등한다(모션은 있지만 조작은 없는 장).
2. **환경 의존은 없다.** three.js는 `assets/vendor/three/`에 저장소가 품고 있으므로 `film`
 같은 옵트인 게이트가 필요 없다. 다만 위 1번 때문에 **사용자에게 확인은 받는다** —
 "이 장은 조작 교구로 따로 만들면 좋겠는데 진행할까요"까지.
3. **덱에서 부르는 방법 세 가지** — 계획서에 어느 것인지 적는다:
  - `iframe` (기본 · 2026-09-09 사용자 결정): 슬라이드 안에 모형의 embed 모드(`?embed=1` — 부가
    설명 없이 무대와 컨트롤러만)를 끼워 넣고, 같은 슬라이드에 전체 페이지 링크·QR을 병기한다.
    슬라이드에서 동작을 보고, 자세히 보려면 링크로 넘어간다
  - `link`: 덱 슬라이드에 클릭 가능한 링크만. 교사가 새 탭으로 띄워 시연한다
  - `standalone`: 덱에 넣지 않는다. 수업 중 아무 때나 띄우는 교구로만 둔다
4. **plan.md에 적을 네 줄** (`3d-model-builder`의 Phase 0이 그대로 소비한다):
  ```
   - slide 7 | form: model | embed: iframe
     체감 한 문장: AI는 지우개질을 배운 것이다
     주인 상태 변수: t ∈ [0,1] (단계 50 → 0)
     진짜 계산: x_t = √ᾱ·x₀ + √(1−ᾱ)·ε (코사인 스케줄)
     장난감인 부분: 목표 이미지는 수식으로 그림 / 역과정은 정과정 되짚기
     손잡이: 방향(생성·학습) · 프롬프트 · 시드 · 카메라
  ```

   `**진짜 계산`과 `장난감인 부분`을 비워 두지 마라.** 화면의 모든 숫자가 실제 계산이어야
   한다는 것이 그 스킬의 첫째 원칙이고, 근사한 부분은 화면에 명시해야 한다.
5. **UI 컨셉은 계획하지 않는다.** 색·카드 배치·룩은 저작 단계에서 소재에 맞게 정한다.
 계획서에는 위 네 줄(무엇을 체감시키고 무엇이 진짜 계산인가)만 확정한다.
6. **선행 조사**: 같은 수업의 기존 덱이 그 원리를 어디까지 다뤘는지 확인해 **자매편**으로
 설계한다. 덱이 "오늘 다루지 않는다"고 명시한 부분을 모형이 맡는 식이다.

### ⛔ 사용 중지 form — `whiteboard` · `watercolor` (2026-09-06 사용자 결정)

두 form은 **지금은 계획하지 않는다.** 콘텐츠가 아무리 잘 맞아 보여도(개념을
차근차근 쌓는 정의·분해·비교 / 정서·성찰이 주인공인 도입·마무리) 넣지 않는다.
사용자가 "화이트보드"·"판서"·"수채화" 등으로 직접 요청하더라도, 먼저 "이 form은
지금 사용 중지 상태"임을 알리고 확인을 받은 뒤에만 쓴다.

대체 규칙 — 표현 수단만 바뀔 뿐 아크와 슬라이드 배치·핵심 메시지는 그대로 유지한다:

| 사용 중지 form | 대체 |
|---|---|
| `whiteboard` (개념을 차근차근 쌓아 설명) | `build`(개념 카드를 담화 순서로 공개) · `scene`(쌓이는 순서 자체가 시간이면) · `image` |
| `watercolor` (정서·마무리·숨 고르기) | `image`(삽화 한 장) · `scene`(도입 씬의 거울상 등) · `static`(정지 마무리) |

### 라이브 문항은 form이 아니라 **발문의 타이밍**이다

`live`는 위 form 표에 없다. 슬라이드의 생김새를 정하는 것이 아니라, **수업의
어느 지점에서 학생에게 물을 것인지**를 정하는 일이기 때문이다. 화면은 이미
있는 슬라이드가 맡고, 교사는 그 슬라이드를 띄운 채 **덱 하단 네비게이터(독)의
질문 기능**으로 문항을 연다. 학생은 각자 기기에서 답하고, 교사 화면에 결과가
모인다.

그래서 계획할 때 던지는 질문은 "문항을 몇 개 넣을까"가 아니라 **"여기서 물어야
하는가"**다. 물을 자리는 대개 이렇다.

- **선행 지식을 꺼내야 할 때** — 새 개념에 들어가기 전에 학생이 이미 아는 것을
  드러내면 설명이 그 위에 얹힌다. 답의 분산 자체가 다음 설명의 재료가 되기도
  한다.
- **방금 설명한 것이 전달됐는지 확인할 때** — 교사가 짐작하는 대신 분포를 본다.
  오답이 많으면 그 자리에서 되짚는다.
- **학생의 답이 다음 장면의 재료일 때** — 학생이 먼저 판단해 본 뒤 원리를
  들으면 "내가 방금 한 일이 그것"으로 회수된다.
- **설명이 길어져 집중이 흐트러질 때** — 주기적으로 환기하는 자리. 내용을
  점검하기보다 다시 붙잡는 것이 목적이다.
- **활동·실습 직전** — 규칙이나 판단 기준을 확인하고 들어간다.
- **수업 끝** — 출구 티켓으로 무엇이 남았는지 본다.

**개수 제한은 두지 않는다.** 수업의 성격이 정한다 — 위의 자리에 해당하는
지점이 있으면 묻고, 없으면 묻지 않는다. 몇 개가 적당한지를 따로 계산하지 않는다.

표기는 그 질문과 관련된 **슬라이드 블록 안에 `- live:` 라인**으로 붙인다.
quiz.json의 `slide`는 그 슬라이드 번호가 된다. 문항이 참조할 것(사진·코드·그림)은
그 슬라이드의 형태 설계가 맡고, 문항은 질문·선지·정답만 갖는다. 표기법은
`references/plan-format.md`의 `- live:` 절.

**활동지에서 답하게 될 질문은 문항으로 내지 않는다** — 같은 것을 두 번 묻는
셈이 된다.

보조 규칙 둘:

- **부분 에셋 SVG**: scene/static 안에 figural 시각물(캐릭터·사물)이 필요하면
manifest의 2세대 SVG(`reusable: true`)를 이 덱에 맞게 재사용 → 없으면 `svg-asset-builder`(덱당 ≤5, 4조건)로
생성 요청을 plan.md에 `- svg:` 라인으로 명시. 생성 래스터는 씬 전체(image
form) 전용 — 씬의 부분 요소로 새 래스터를 만들지 않는다.
- **클릭 링크**: 수업 중 접속해야 하는 URL(사이트·활동지·폼)은 반드시 클릭
가능한 링크로 slide에 넣도록 형태 설계에 명시한다.

## ④ plan.md 작성

형식·예시는 `references/plan-format.md` (필독). 핵심 설계: 슬라이드 블록이
**하류 스킬들의 기존 계획 문법을 그대로 내장**한다 —

### 설명 방식은 ELI5가 기본이다 (2026-09-16 사용자 결정 — BLOCKING)

plan.md에는 **「ELI5 적용 원칙」 절이 반드시 들어간다.** 헤더 표와 「정식 용어」
절 다음, 슬라이드 블록 앞자리다. 같은 소재를 ELI5 없이 한 번, 적용해 한 번
기획해 비교한 결과(「인공지능은 어떻게 배울까」 v1 대 v2) 적용한 쪽이 나았고,
사용자가 이 방식을 공식 절차로 지정했다.

계획을 쓰기 전에 `eli5` 스킬을 Read 한다. 일곱 원칙(구조·어휘·비유·문장·어조·
정확성·분량)을 **그 수업 기준으로 구체화해** 절에 적고, 슬라이드 블록의 「핵심
내용」과 「발표자 노트」를 그 원칙대로 쓴다. 특히:

- 노트는 ① 무엇인가 ② 이미 아는 것에 잇는 비유 ③ 세부 ④ 그래서 나에게 무슨
  의미인가(so what) 순서로 흐른다.
- 새 용어는 나오는 즉시 한 문장 풀이가 붙는다. **한 장에 새 용어 셋 이하.**
- 단순화한 자리는 노트에 "실제로는 …"으로 한 줄 밝힌다.

대상이 학생이 아니면(교사 연수·부서 자료) 끄는 것이 아니라 **청중을 바꿔**
적용한다 — 보정 표는 `eli5` 스킬의 `references/audience-calibration.md`.

### 발표자 노트는 말과 화면을 함께 적는다 (2026-09-15 사용자 결정)

노트를 읽는 사람은 그 화면을 방금 띄운 교사다. 할 말만 적혀 있으면 화면의 어디를
가리켜야 할지, 클릭하면 무엇이 바뀌는지 알 수 없다. 그래서 노트에는 다음이
**자연스럽게 섞여** 있어야 한다.

- **지금 화면에 무엇이 있는지** — "가운데 상자가 모델이고, 안에 숫자가 여섯 개
  있습니다"
- **조작하면 무엇이 달라지는지** — "클릭 2에서 규칙이 늘어납니다", "영상은
  앞부분만 재생하세요"
- **그때 할 말** — 학생에게 그대로 해도 되는 문장으로
- **짚어야 할 오해나 주의** — "영상 제목의 「의식이 있는 뇌」는 과장입니다"

연출 지시는 괄호로 끼워 넣으면 읽기 쉽다. 학생에게 들려줄 말과 교사만 보는 운영
메모를 한 노트 안에서 잇는다. 화면 설명을 따로 떼어 「형태 설계」에만 두면, 수업
중에 그 블록을 다시 펼쳐 볼 수 없다.

### 활동·문항 배치 원칙 (2026-08-26 — 원칙만, 세칙화 금지)

활동지가 있는 수업은 **활동에 대한 설명을 모두 마친 뒤 활동지를 한 번만 연다** —
설명·활동지·설명이 번갈아 끊기는 흐름을 만들지 않는다. 라이브 문항은 중요한 개념의
확인·발문에 주로 쓰고, 활동지에서 답하게 되는 질문은 문항으로 내지 않는다.

### 용어 원칙 (2026-08-26 — 원칙만, 세칙화 금지)

비유는 개념을 여는 도구이지 개념의 이름이 아니다. 정확한 용어가 필요한 자리
(화면 라벨·정의 문장·활동지 칸 이름·문항 선지)에는 정식 용어를 계획하고, 비유는
도입·해설·발표자 노트에서 정식 용어와 함께 쓴다. 한국어에서 통용되지 않거나
다른 뜻으로 통하는 비유는 피한다. **여기서 더 잘게 규칙화하지 않는다** — 세부
판정은 adversarial-review의 ④ 용어 갈래(결과물 검증)가 맡는다.

- form: image → **비주얼 가이드** 블록 (notebooklm 4블록 문법)
- form: scene → `**metaphor: … | emotion: … | intent: …**` 라인 (dynamic-scene-builder 문법)
- form: walkthrough → scene 라인 + **절차 대본** (`창 × 행동 × 확인` 단계 목록 — software-walkthrough-builder 문법)
- form: diorama → **`stage: … | framing: …` + `actors:` + `overlays:` + `impact:`** 블록 (diorama-deck-builder 문법 — 무대 1개는 슬라이드 1~3장으로 나뉘고 척추 보드 1종을 정한다)
- form: whiteboard · watercolor → ⛔ **사용 중지** — 계획하지 않는다 ('사용 중지 form' 절의 대체 규칙)
- form: collage → **`world:` + `camera:` + `stations:` + `mg:`** 블록 (vox-collage-deck-builder 문법 — 카메라 총 이동 ≥600px, 경로 위 빈 종이 금지)
- form: static/build → **컴포넌트 제안 + 빌드 순서**
- `- live:` 라인 (슬라이드 블록 안 · form이 아니다) → **문항 종류·질문·선지·정답** (live-quiz-builder 스키마로 변환 가능, `slide`는 그 슬라이드 번호)
- form: film (옵트인) → **`film: <문법> | <편 id> (13.5s = 4.5s×3)` + `scene 1~3` 목록
  - `page text:` + `fallback form:`** (film-deck-builder 문법 — 강등 대상을 반드시 병기)

그래서 plan.md만 있으면 어떤 렌더러든 변환 없이 바로 소비한다.

   규칙으로 바꾼다. **`form: live` 슬라이드가 없는가** — 라이브는 form이 아니므로
   문항은 관련 슬라이드의 `- live:` 라인이어야 한다. 각 문항이 붙은 자리가
   '발문의 타이밍'에 해당하는지 확인한다(개수는 따지지 않는다)
8. `**model`이 있다면**: ① 한 수업에 1개 이하인가 ② 사용자에게 확인받았는가
   ③ `체감 한 문장`·`주인 상태 변수`·`진짜 계산`·`장난감인 부분`·`손잡이`·`embed`가
   모두 적혀 있는가 — 하나라도 아니면 `scene`으로 강등하거나 확인부터 받는다
9. 용어 규율: 「정식 용어」 절이 있고, 화면 라벨·정의 문장·칸 이름·문항 선지
   자리에 비유어가 정식 용어를 대체한 곳이 없다 (④의 '용어 규율')
10. **ELI5 점검** (BLOCKING — ④의 'ELI5가 기본이다'): 「ELI5 적용 원칙」 절이
   있고, 다섯 가지를 확인해 검증 게이트에 한 줄로 남겼는가 — ① 풀이 없는 용어가
   없고 한 장에 새 용어 셋 이하 ② 장마다 비유가 하나씩 있고 중복되지 않음(목록으로
   적어 확인) ③ 노트 마지막 문단이 so what으로 닫힘 ④ 한 문장에 생각 하나·"여러분"
   주어·단순화한 자리에 "실제로는 …" ⑤ 어조가 목적 → 원리 순서

| `- live:` 라인 포함 | 위 결정 + `live-quiz-builder` 부가 (문항의 `slide`는 라인이 붙은 슬라이드 번호) |
| `model` 포함 | 위 결정 + `3d-model-builder` **선행** (모형을 먼저 만들어 검수까지 끝낸 뒤 덱에서 링크·iframe으로 부른다) |
| 산출물 자체가 교구 (①의 판별에서 모형) | `3d-model-builder` 단독 — plan.md 없이 그 스킬의 Phase 0으로 넘긴다 |

스킬을 Skill tool로 호출한다. plan.md 수정 요청은 이 스킬이 계속 담당.

`film`이 포함된 계획을 요약할 때는 **환경 의존을 함께 알린다** — "이 계획의
N장은 OpenMontage 영상 렌더가 필요하고, 그 환경이 없는 PC에서는 `fallback form`
(예: collage)으로 저작됩니다"까지 말해야 사용자가 판단할 수 있다.
