# plan.md 형식 — 구조화 덱 계획 파일

저장 위치: `data/<그룹>/<과목>/<수업>/plan.md`. 이 파일이 파이프라인의 단일 진실
원천(SSOT)이다 — 렌더러 스킬은 여기 적힌 form과 형태 설계를 따르고,
내용 수정은 항상 plan.md를 먼저 고친 뒤 재저작한다.

### 헤더 다음에 오는 세 절 (순서 고정)

헤더 표 아래에 아래 세 절을 이 순서로 둔다. 슬라이드 블록은 그다음이다.

1. **「사실 관계 원칙」** — 화면에 올릴 연도·수치·인용을 출처와 함께 확인한 표.
   확인하지 못한 것은 "저작 시 재확인"으로 표시한다.
2. **「정식 용어」** — 화면 라벨·정의 문장·활동지 칸 이름·문항 선지에 쓸 용어
   목록과, 그 자리에 쓰지 않을 비유어 대조 목록.
3. **「ELI5 적용 원칙」** (필수 — 2026-09-16 사용자 결정) — `eli5` 스킬의 일곱
   원칙을 그 수업의 청중 기준으로 구체화한다. 대상이 명시되지 않으면 고등학생이
   기본값이다.

```markdown
## ELI5 적용 원칙 (이 수업 기준)

외부 ELI5 스킬(https://github.com/DreambigOu/ELI5)의 원칙을 고등학생 청중에 맞게 적용한다.

1. **구조**: 슬라이드마다 핵심 내용과 발표자 노트를 같은 순서로 짠다. ① 무엇인가
   ② 이미 아는 것에 잇는 비유 ③ 필요한 만큼만 세부 ④ 그래서 나에게 무슨 의미인가.
2. **어휘**: 정식 용어를 소개하되 나오는 즉시 한 문장으로 풀이한다. 화면에서는 용어
   옆에 작은 풀이 한 줄(칩 또는 괄호)을 둔다.
3. **비유**: 학생의 생활에서 가져온다(스마트폰·게임·SNS·학교·급식·시험). 비유는 정식
   용어를 대체하지 않는다.
4. **문장**: 한 문장에 생각 하나. 노트는 "여러분"을 주어로 학생에게 직접 말한다.
5. **어조**: 약간 편하게, 어린애 취급하지 않는다. 목적을 먼저, 원리는 그 뒤에.
6. **정확성**: 단순화는 하되 틀린 말은 하지 않는다. 단순화한 부분은 노트에
   "실제로는 …"으로 한 줄 덧붙인다.
7. **분량**: 한 장에 새 용어는 셋 이하. 넘치면 장을 없애지 않고 문장을 줄인다.
```

### 발표자 노트에 들어가야 하는 것

노트는 그 화면을 방금 띄운 교사가 읽는다. 할 말만 있으면 어디를 가리킬지
모르므로, **화면 설명과 할 말을 한 덩어리로** 적는다.

- 지금 화면에 무엇이 있는지 — "가운데 상자가 모델이고 안에 숫자가 여섯 개 있습니다"
- 클릭·재생으로 무엇이 바뀌는지 — "(클릭 2: 규칙이 늘어납니다)"
- 그때 할 말 — 학생에게 그대로 해도 되는 문장으로
- 짚어야 할 오해나 운영 주의 — "영상 제목의 「의식이 있는 뇌」는 과장입니다"

연출 지시는 괄호로 끼워 넣으면 읽기 쉽다. 화면 설명을 「형태 설계」에만 두면
수업 중에 그 블록을 다시 펼쳐 볼 수 없다.

## 2. 슬라이드 블록 (장당 1블록)

공통 뼈대 + form별 형태 설계 블록. **form 라인이 렌더러에게 보내는 라우팅
신호**이고, 형태 설계 블록은 해당 하류 스킬의 계획 문법을 그대로 쓴다.

### form: image — NotebookLM 4블록 문법 (비주얼 가이드가 핵심)

재사용이면 `- image:` 라인에 경로와 **set·style**을 표기한다 (스타일 보수
원칙 — 한 덱은 한 세트/한 스타일, asset-library SKILL 참조).

```markdown
## Slide 1 — 박수 100번 칠 수 있나요?
- form: image

**핵심 메시지:** 인간에게 지루한 반복이 컴퓨터에겐 특기다.

**핵심 내용:**
- 사람: 97, 98… 지치고 헷갈림
- 컴퓨터: 100번이든 100만 번이든 1초

**비주얼 가이드:** 화이트보드 스타일. 왼쪽에 지친 사람 손그림(이마 땀방울),
말풍선 "97… 98… 어디까지 했더라?". 오른쪽에 웃는 컴퓨터 모니터 손그림,
말풍선 "1초면 쉽지!". 중앙 위 파란 마커 제목 "반복", 사람→컴퓨터로
빨간 화살표 + "맡기자!" 손글씨.

**발표자 노트:** "여러분 지금 박수 100번 쳐 볼까요? …힘들죠." (화면 왼쪽에
지친 사람이 「97… 98… 어디까지 했더라?」 하고 있습니다. 오른쪽 컴퓨터는
「1초면 쉽지!」라고 하죠.) "이 둘 사이 빨간 화살표가 오늘 배울 일입니다.
지루한 반복을 컴퓨터에게 넘기는 법이에요."
```

### form: scene — dynamic-scene-builder 계획 라인 문법

```markdown
## Slide 5 — while의 심장 박동
- form: scene
- scene: metaphor: 심전도 모니터 | emotion: 몰입 | intent: 조건이 참인 동안 반복이 '살아 있음'을 시간으로 체감시킨다

**핵심 메시지:** while은 조건이 참인 동안 계속 뛰는 심장이다.

**핵심 내용:**
- 조건 검사 → 본문 실행 → 다시 조건 (순환)
- 조건이 거짓이 되는 순간 루프 정지

**형태 설계:** 중앙 심전도 라인이 t로 흐르며 박동마다 조건 뱃지
`count < 5` 검사 플래시(초록). 클릭 1: count 카운터 증가 연출.
클릭 2: count=5 → 뱃지 빨강, 심전도 평탄화(루프 종료). 모든 모션은
useSceneTime() t의 순수 함수 — 같은 t, 같은 화면.

**발표자 노트:** 화면 가운데 심전도 선이 박동마다 초록으로 깜빡입니다 —
그때마다 `count < 5`를 검사하는 거예요. "조건이 심장을 뛰게 합니다."
(클릭 1: 카운터가 올라갑니다) "하나씩 세고 있죠." (클릭 2: 뱃지가 빨강으로
바뀌고 선이 평탄해집니다) "거짓이 되는 순간 — 멈춰요."
```

### form: static / build — 컴포넌트 제안 + 빌드 순서

```markdown
## Slide 7 — while vs for, 언제 무엇을?
- form: build

**핵심 메시지:** 횟수를 알면 for, 조건만 알면 while.

**핵심 내용:**
- for: 반복 횟수가 정해진 경우 (range)
- while: 조건이 만족되는 동안 (횟수 미정)
- 잘못 고르면? 코드가 길어지거나 무한 루프

**형태 설계:** Comparison 컴포넌트 좌 for / 우 while, 각 셀에 CodeWindow
4줄 예제. Build at=1: for 열, at=2: while 열, at=3: 하단 판단 기준 한 줄
("횟수를 아는가?") 강조 배지.

**발표자 노트:** 화면에 for와 while 코드가 좌우로 놓입니다. (클릭 1: 왼쪽
for 열) "횟수가 정해졌을 때는 이걸 씁니다." (클릭 2: 오른쪽 while 열)
"조건만 알 때는 이쪽이에요." (클릭 3: 아래 판단 기준 배지) "딱 하나만
기억하세요 — 횟수를 아느냐."
```

### `- live:` 라인 — 문항은 슬라이드가 아니라 슬라이드에 붙는다 (2026-09-06)

라이브 문항을 별도 슬라이드로 만들지 않는다. 질문과 관련된 슬라이드 블록에
`- live:` 라인을 붙이고, `**문항 명세:**` 블록으로 상세를 적는다. 문항이 참조할
것(코드·사진·그림)은 그 슬라이드의 형태 설계가 화면에 두고, 문항은 질문·선지·
정답만 갖는다. quiz.json의 `slide`는 이 슬라이드 번호가 된다.

```markdown
## Slide 6 — while 루프 한 바퀴
- form: build
- live: choice · "이 while 루프는 몇 번 실행될까?" · 선지 ["3번", "4번", "5번", "무한"] · 정답 1

**핵심 메시지:** 조건이 거짓이 되는 순간 루프는 멈춘다.

**핵심 내용:**
- i=0; while i<4: print(i); i+=1 — 화면의 CodeWindow가 문항의 참조 코드다

**형태 설계:** CodeWindow 4줄 + Build at=1: 실행 흐름 화살표. 라이브 문항은 at=1이
끝난 뒤 이 화면을 띄운 채 진행한다.

**문항 명세:**
- kind: choice · 정답: 1 (4번) · reveal 시 오답 패턴 해설: "i<4에서 0,1,2,3 — 4는 미포함"

**발표자 노트:** 코드 설명 → "제출해 주세요" → 분포 공개 → 정답 공개 → 다음 장.
```

### form: film — film-deck-builder 문법 (⚠ 사용자 명시 요청 시에만)

`film`은 자동 선택 대상이 아니다 — 사용자가 영상 렌더를 직접 요청했고
OpenMontage 환경을 확인한 경우에만 쓴다 (SKILL.md의 옵트인 게이트 참조).

**한 페이지 = 영상 1편 = 3장면(4.5초×3 = 13.5초).** 다른 영상이 필요하면
다른 슬라이드다. 스텝 진행 UI(①②③ 칩)는 계획하지 않는다 — 스텝은 영상 안에서
자연스럽게 이어지는 단계다.

`fallback form:`은 **필수**다. 영상 렌더가 불가능한 PC에서 같은 계획을 React로
살리는 강등 대상이고, 장면 설계는 그대로 재사용된다.

```markdown
## Slide 4 — 바다를 건너는 길
- form: film
- film: diorama | journey (13.5s = 4.5s × 3)
- fallback form: diorama (diorama-deck-builder — 무대·배우 설계 그대로 사용)

**핵심 메시지:** 라우터는 전체 지도를 모른다 — 다음 한 걸음만 안다.

**핵심 내용:**
- 갈림길마다 다음 관문만 결정 (홉)
- 대륙 사이는 위성이 아니라 해저 케이블
- 수많은 관문을 지나 목적지 서버 도착

**장면 설계:**
- scene 1 (0~4.5s) 라우터 갈림길 — 패킷이 달려와 멈추고, 안내 로봇이 오른쪽을
  가리킨다. 라벨칩 "라우터", 말풍선 "다음 길만 알려줄게!"
- scene 2 (4.5~9s) 해저 케이블 — 지도 무대 위로 항로가 그려지고 그 위를 패킷이
  건넌다. 스탬프 "해저 케이블" 슬램
- scene 3 (9~13.5s) 서버 도착 — 서버 랙 캐릭터가 맞이한다. 라벨칩 "목적지 서버"

**page text:** 킥커 "패킷의 여행 · 2편" / 제목 "바다를 건너는 길"
캡션(장면마다 갈림): ① 라우터는 전체 지도를 모른다 — 다음 한 걸음만 안다.
② 대륙 사이를 잇는 건 위성이 아니라 바다 밑 케이블이다.
③ 수많은 관문을 지나, 조각들이 목적지 서버에 닿는다.
→ 무대 상단 25%는 비운 구도로 생성 (텍스트 밴드 자리)

**자산:** 무대 stage-crossroad·stage-ocean·stage-server (신규 생성),
스프라이트 packet-run/idle·router-robot·server-rack (assets/sprites/패킷-필름)

**발표자 노트:** "우리가 보낸 메시지는 지도를 보고 가는 게 아니에요. 갈림길마다
'다음은 저쪽' 하나씩만 듣고 가는 겁니다."
```
